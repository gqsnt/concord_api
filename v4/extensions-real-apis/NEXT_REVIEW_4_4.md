## 4. Developer problems confirmed across independent work

Clustered by cause and boundary; "independent" means separately authored SDKs or the
maintenance/caller exercises, not copied code.

1. **Response metadata and transport-error conversion at the native boundary** (TERRA-2, SOL-8,
   ASTRA-5; SDK FRICTION GitHub F1/F2, Stripe F4, Shopify F3, Salesforce transport; GitHub
   maintenance). Four independently written SDKs split `Prepared`, execute, capture the head and
   decode; all convert a known transport failure through `Decoder::finish(Err(e)).await`, typed as
   possibly successful (GitHub `unreachable!`, Stripe a fabricated status-0 success). An outside
   extension (GitHub maintenance) also loses the endpoint label. Strongest repeated evidence in
   this review.
2. **Repeated declarations** (TERRA-3, TERRA-4): Kubernetes' seven list parameters on 13
   endpoints; Stripe's three-state account override on 19 endpoints. Mostly copied within one SDK;
   the burden is maintenance, not wrong requests.
3. **Generic code over generated operations** (TERRA-5): Kubernetes and Stripe each wrote a trait
   plus macro over generated requests; GitHub used function pointers instead.
4. **Extension contexts** (TERRA-1): the GitHub context mirrors path/header composition (~90
   lines); an outside operation costs ~145 lines against ~25 declared; Kubernetes' context is
   closed to other crates.
5. **Pagination consumer gaps** (OPUS-3/4/7/8): `Items` drops page metadata (GitHub F9, Stripe
   F6); restart composes `independent` + `manifest_jobs` with two report shapes and two budget
   interpretations (SF-B vs the independent DX-03 caller); the drain/error-stash loop repeats ~13
   times; several scheduler members have no provider consumer yet.
6. **Schema evolution in SDK models** (maintenance exercises, TERRA-6): field additions break
   exhaustive literals; CSV row structs and column lists, GraphQL selections and decode types are
   coupled only by documentation; serde's missing-field name is withheld from ordinary diagnostics.

Counter-evidence (what worked):

- The DSL declared every operation of the five providers without new grammar.
  `concord-core` needed no change for streaming or pagination: the only core-side change in this
  phase is the SOL-4 macro fix. Since `v4.2.0`, published crate sources changed only additively.
- In five of five maintenance exercises old call sites compiled unchanged (literal-style callers
  excepted, as documented). The Salesforce dialect switch needed zero SDK lines.
- Both independent callers succeeded from public docs. One found "the whole-job future is the
  correct concurrency unit"; the other reported no compiler errors.
- Stress: 256/512 MiB reads at constant library retention and 11–12 MB process RSS.
- Opus traced the pagination scheduler and found no scheduling, ordering, budget or
  cancellation defect.

## 5. Recommendations for the next release (ranked)

Each item names its evidence, decision criterion and falsifier; sketches are illustrative and not
current API.

**R1 — Synchronous transport-error conversion (targeted addition; adopt).**
Evidence: §4.1 (four SDKs, one outside extension, three strands). Before (`examples/github-sdk/src/meta.rs`):
`let Err(e) = decoder.finish(Err(error)).await else { unreachable!() };`. After:
`let e = decoder.transport_error(error);` — `Decoder::transport_error(&self, reqwest::Error) ->
Error`, keeping the endpoint label and URL removal of the existing route. Cost: a few lines in
`concord-core`, additive, no dependency, no runtime cost. Alternatives: an SDK-owned helper (each
SDK still needs the async detour); making `Error::from_transport` public without endpoint
metadata (loses the label). Falsifier: an existing public synchronous conversion with the endpoint
label (none exists).

**R2 — Head-observing send (bounded prototype before adoption).**
Evidence: §4.1. Sketch: `prepared.send_observing(|head| select(head)).await -> Result<(T, M),
Observed<M>>`, with the caller choosing what to keep (no metadata policy in core: the 4.3 M1
objection stands). Decision criterion: a four-provider prototype (GitHub, Stripe, Salesforce,
Shopify) removes the repeated lifecycle code and handles Shopify's *refusing* head check without a
second hook; otherwise keep the native recipe plus R1. Falsifier: the prototype must duplicate as
much code to preserve error ownership and unread refusals.

**R3 — Pagination additions shaped by consumers (targeted).**
`Items::page_meta()` (OPUS-3; GitHub and Stripe); a seeded `manifest_jobs` (re-runs and
continued discovery under one budget and one report; OPUS-4, reverses decision PAG-03 on consumer
evidence); optional `Sequential::drain` (OPUS-7). Mark members without a provider consumer
(`first_page_then`, sparse checkpoints, `failure_limit`) provisional in the README until one
exists (OPUS-8), and tie that to the separate publication decision. Falsifier for the seed: a
consumer needing different options for re-runs and discovery (neither existing consumer does).

**R4 — Codec polish before the new formats are published (targeted).**
CSV writer media option (Salesforce documents `text/csv` without `header=`; Salesforce F3); a
strict line-ending mode (F5); a bounded known-length encode route for providers requiring
`Content-Length` (F4); one `MediaPolicy` shape across `csv` and `jsonl` (today two different
types share the name); a structured, content-free missing-field name in decode errors (maintenance
exercises); boxing `CodecError`'s payload (Salesforce F7). Each is additive or touches API not yet
released. Falsifier per item: no second consumer or provider requirement by implementation time.

**R5 — DSL opt-ins (separately bounded prototypes, not release scope).**
Parameter groups that expand to endpoint-owned values (TERRA-3) and per-request inherited override
groups (TERRA-4) as one prototype; an opt-in `Prepare` trait for generated requests (TERRA-5); an
opt-in scope native-request builder for extensions (TERRA-1). Decision criteria: exact wire order,
sensitivity, generated-name collisions and diagnostics preserved, and compile cost measured against
the 4.3 generated-input experiment's numbers (+27% expansion, +16% clean compile at 480 endpoints).
The wholesale generated-input-record design stays rejected.

**R6 — Guidance (done now).** AUTHOR_GUIDE §11 now covers the `Clone` exception and SDK record
evolution.

**Not recommended:** a pagination statement in the DSL or core (the five adapters differ in key,
binding, snapshot and loop checks; contract §2); a crate-level resume-binding hook (the factory
already sees the key); checkpoint persistence in the crate; a reusable bracket-form codec until a
second provider with the same convention exists (TERRA-7: recipe only).

## 6. Disagreements and open questions

- **Generated trait vs function pointers** (TERRA-5 vs Opus's cross-check): Terra proposes an
  opt-in `Prepare` trait; Opus expects GitHub's `fn(Op) -> Result<Prepared<R>>` pattern to make
  it unnecessary for pagination. Left to the R5 prototype.
- **Item checkpoint form**: GitHub F10 asked for `next_with_checkpoint`; Opus prefers
  `Items::page_meta` and verification inside the factory. R3 adopts `page_meta`; checkpoint-after-
  emit remains open.
- **OPUS-5** (serial providers cannot use `manifest_jobs`): blocked by missing evidence; no
  workflow asked for it.

## 7. What changed since the 4.3 conclusions

- **M1 (metadata convenience in core, rejected in 4.3):** 4.3 had one SDK; now four independently
  written SDKs and an outside extension repeat the same lifecycle. This supports R1 now and an R2
  prototype. M1's core objection still holds: the library must not choose metadata or error
  policy.
- **X1 (core context primitive, rejected in 4.3):** new evidence (GitHub context mirroring,
  ~145-line outside operation, closed Kubernetes context) justifies an opt-in prototype (R5). It
  does not justify adoption.
- **G1 (generated inputs, not adopted):** still not adopted. TERRA-6 shows that the SDKs' own
  input records, not generated ones, are where evolution hurts. The narrower parameter groups (R5)
  are a different mechanism and must meet the G1 cost baseline.

## 8. Release conclusion and semver

**Targeted fixes and additions are justified, with a concrete scope:** the defects of §3 (done),
R1, R3 and R4. R2 and R5 stay outside the release until their prototypes meet the stated criteria.

All delivered public changes since `v4.2.0` are additive: a new crate, new features and modules,
new methods. The macro fix changes no accepted program. A release with this scope is a
**semver-minor** release of the four existing crates, plus the first release of
`concord-pagination` with provisional members marked. The owner chooses the version number: 4.3
was never published, so the next minor could be numbered 4.3.0 or 4.4.0. Publication, tagging and
merging the extension pull request are separate decisions; none was taken here.
