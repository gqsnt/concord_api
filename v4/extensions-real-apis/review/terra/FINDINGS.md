# TERRA — DSL and operation authoring review

Reviewed detached `0dd65501`; 4.4 is the review label, not a release-version recommendation. The caller task and its chronology are in `TASK_NOTES.md`; final source and executable test are in `task/`. Reproduction commands below use `CARGO_TARGET_DIR=review/terra/target` at the repository root; the scratch task uses `CARGO_TARGET_DIR=../target` from `review/terra/task`. All tests ran offline with loopback only. The findings concern demonstrated work, not a claim that an unsupported proposed syntax exists. Proposed snippets below are sketches for evaluation, not current API.

## TERRA-1 — A downstream operation cannot reuse generated scope composition as a typed operation

**Task:** extend a configured SDK without re-entering credentials, headers, scope path and transport, then use its pagination and decoder. **Location:** `examples/github-sdk/src/context.rs:216`, `:224`, `:387`; `examples/github-sdk/src/paging.rs:219`; `review/terra/task/src/lib.rs:12`; Kubernetes counterexample `examples/kubernetes-sdk/src/context.rs:25` and `checks/maintenance-kubernetes/MAINTENANCE.md:273`. **Classification:** developer friction. **Severity:** medium. **Evidence:** reproduced for the external GitHub native extension; source-inspected for the signature mismatch and Kubernetes's context.

**Observed vs expected:** `cd review/terra/task && CARGO_TARGET_DIR=../target cargo test --offline` passes with the correct two requests and inherited headers, but the SDK's `LinkPages::new` requires a generated `Op` and function returning `Prepared<R>`; `RepoContext::request` returns `reqwest::Request`. The caller must write a separate page factory, execute, inspect the response and construct `Decoder`, losing generated endpoint identity (the corrected task does retain Concord error conversion). Expected: the new route can reuse configured composition and its typed response path without mirroring or preparing a different endpoint as a seed. GitHub's own context copies path joining, header construction and credentials already in its declaration; its agreement test (`examples/github-sdk/tests/operations.rs:396`) works. The independent Kubernetes maintainer's extension probe had to configure a second client because its SDK offers no native extension boundary; this is not the same code copied from GitHub. Shopify/Salesforce/Stripe contexts serve different provider purposes; the evidence does not establish that all five implement identical native mirrors.

**Smallest credible change:** first document a recommended SDK extension adapter accepting a native request plus `Decoder`, and improve Kubernetes's public context; those are useful without a core change. Prototype an **opt-in** generated scope native request builder that reuses resolved path/query/header composition, sends no invented endpoint label and never seeds another operation. Before: `repo.request(GET, &["issues", "events"])` plus a parallel native page adapter. Potential after: `repo.handle().native_request(GET, &["issues", "events"])` and an adapter accepting `(request, Decoder::<Vec<Event>>::new::<Json>())`. This still needs an SDK page adapter, same-origin/continuation policy and explicit decoder; it does not magically make native operations `Prepared`. A genuinely different alternative is an explicit shareable request context independent of generated handles, but it introduces a second representation and potential divergence.

**Cost/compatibility:** additive only if opt-in and generated names are collision-checked; namespace changes can break existing code. Unlabeled build/transport errors, optional inherited queries, header overrides and secret redaction need explicit semantics; malformed segments must fail before sending. Expect per-enabled-scope macro output and compile work, no new dependency and no network cost, but no measurement yet. **Disposition:** propose for next release as a measured opt-in experiment, not an unconditional primitive. The 4.3 X1 rejection (`v4/dx-4.3/DECISIONS.md:219`) identified these unresolved issues and is not disproved merely by the successful task. **Falsifier:** an existing public API that constructs this arbitrary extension from a scope with identical composed state and typed decoding without manual mirroring, or evidence that such a prototype cannot preserve the stated redaction and inheritance contracts at acceptable cost.

## TERRA-2 — Response-head observation repeats transport and decode plumbing

**Task:** retain rate limits, request IDs, served version or pagination links alongside typed results. **Locations:** `examples/github-sdk/src/meta.rs:219`, `examples/stripe-sdk/src/send.rs:452`, `examples/salesforce-sdk/src/transport.rs:39`, `examples/shopify-sdk/src/context.rs:148`, `crates/concord-core/src/prepared.rs:258`. **Classification:** developer friction. **Severity:** medium. **Evidence:** source-inspected; relevant status/metadata tests reproduced by `cargo test --offline -p concord-example-github-sdk --test operations` (9 pass) and `cargo test --offline -p concord-example-stripe-sdk --test wire` (8 pass).

**Observed vs expected:** `send()` yields the value, so four independently authored SDK slices split `Prepared`, execute once, handle transport conversion, capture or check the head and decode. The provider-specific selected headers and error interpretation differ; the shared lifecycle is nevertheless repeated. Shopify's served-version check must be able to refuse before body decoding, unlike merely retaining a head. Salesforce's helper discards usage on error, GitHub/Stripe keep selected metadata, illustrating why identical policy must not be assumed. Current flow works; expected is less repeated lifecycle code while preserving endpoint labels, unread responses on status/head refusal, transport redaction and provider control.

**Smallest credible change:** evaluate an additive low-level observing send with caller-owned projection, e.g. before `into_parts(); execute(); capture(&response); decoder.decode(response)`; after `prepared.send_observing(|head| capture_selected(head)).await` returning metadata both on success and on post-head errors. A separate pre-decode fallible head hook would be needed for Shopify; do not silently claim a simple infallible observer solves that task. An SDK-owned shared helper remains an alternative and avoids core policy. Do not return a full header map in `Debug`, expose raw URLs, or consume a refused response. The earlier M1 rejection (`v4/dx-4.3/DECISIONS.md:195`) correctly objects to baking in metadata and error policy; this proposal keeps selection with the caller but still needs a concrete design and tests.

**Cost/compatibility:** an additive core method may collide with user inherent methods if emitted on generated types; prefer `Prepared`, check compatibility, and retain existing API. No dependency; small runtime call/owned projection per request, plus generic monomorphization and compile cost not measured. It affects all four integrations but provider validation remains theirs. **Disposition:** propose for next release only after a four-provider prototype proves reduction without constraining Shopify refusal or error ownership. **Falsifier:** a single existing public helper already covers all four lifecycles with no repeated execution/conversion, or a prototype must duplicate as much logic to preserve these semantics.

## TERRA-3 — Shared endpoint parameter sets have to be redeclared

**Task:** add a Kubernetes resource family without drifting list/watch semantics or redaction. **Locations:** `examples/kubernetes-sdk/src/api.rs:80`, `:141`, `:288`, `:316`; independent staged edits `checks/maintenance-kubernetes/MAINTENANCE.md:85`, `:245`. GitHub's repeated `per_page` is at `examples/github-sdk/src/api.rs:78`, `:106`, and Stripe's override is covered separately below. **Classification:** developer friction. **Severity:** medium. **Evidence:** reproduced existing declarations with `cargo test --offline -p concord-example-kubernetes-sdk --test declaration` (8 pass); repeated source and maintenance diff inspected.

**Observed vs expected:** Ingress list and namespaced list each repeat the same seven query declarations; each watch repeats five plus watch/Accept blocks. The independent change reports 24 copied parameter lines and 6 copied body lines for the new family; in the current tree there are 13 list and 6 watch blocks. The resulting wire and sensitive-token tests pass; the concern is maintaining repeated declarations, not a demonstrated incorrect request. Scope inheritance alone is not equivalent: pagination tokens and selectors must be adjustable on each request, not fixed for every child of a scope. Expected: define the common group once while preserving each endpoint's own setters, defaults, ordering and sensitivity.

**Smallest credible change:** an opt-in declaration-time parameter group, expanded exactly as endpoint-owned values, e.g. before `GET ingresses(query("labelSelector") label_selector?: LabelSelector, ... seven values ...)`; after illustrative `GET ingresses(...ListParameters) -> IngressList`. The group must preserve docs/spans, initializer timing, per-endpoint independent state, name collision diagnostics, attributes, original query order and endpoint-specific additions. An SDK-maintained source-generation macro/build script is a different representation and keeps core smaller, but today `api!` parses its own grammar and standard macro expansion inside its token input cannot be presumed; demonstrate it before recommending it. Independent maintenance confirmed the repetition; within Kubernetes many copies are explicitly copied from the original, not independent discoveries. GitHub/Stripe show separately authored repetitions but not identical parameter semantics.

**Cost/compatibility:** opt-in is source-additive only if new grammar does not reinterpret valid declarations; expanded requests remain the same public types/methods and runtime work. Parser, diagnostics, rustdoc provenance and compile expansion increase; exact cost unknown, no dependency required. **Disposition:** propose a small measured prototype for next release; do not replace per-endpoint inputs with scope state. **Falsifier:** a public existing mechanism removes these copies while retaining per-request state, exact wire order and sensitive handling, or a prototype fails these invariants or exceeds a stated compile budget.

## TERRA-4 — Per-request inherited header overrides repeat at every endpoint

**Task:** choose the platform account, an inherited account or another connected account per Stripe request. **Locations:** `examples/stripe-sdk/src/lib.rs:187`, `:205`, `:255`, `:266`; `examples/stripe-sdk/src/context.rs:175`; `docs/AUTHOR_GUIDE.md` §4.6. **Classification:** developer friction. **Severity:** medium. **Evidence:** reproduced `cargo test --offline -p concord-example-stripe-sdk --test wire` (8 pass); 19 occurrences and helper source inspected.

**Observed vs expected:** every one of 19 endpoints declares a sensitive `account_override?: Option<HeaderValue>` and `override ... = each account_override else inherit`, then an SDK macro implements an ergonomic `OnAccount` trait. Wire tests show the three states work, including inherited headers; this is a maintenance cost rather than a functional bug. It is one provider's policy replicated within its own declaration, not independently authored copies across providers. Expected: declare the shared rule once while callers still choose separately for every request.

**Smallest credible change:** explore an explicitly inherited *endpoint-local* declaration group, distinct from setting a scope value: before each endpoint has the two lines; after a client-level opt-in rule such as `per_request account_override ...` supplies the same generated setter and override to descendants. Keep absence/inherit, present `None`/omit, present `Some`/replace, sensitivity and same-name collision diagnostics exact; generated endpoint handles remain independently configurable. A request-editing helper is the genuinely different alternative and avoids DSL expansion but moves validation/identity to the native boundary and is less discoverable.

**Cost/compatibility:** new syntax must be opt-in and must not add setters to existing endpoints without request; it adds generated fields/methods only where used, no dependency or mandatory per-call overhead, unmeasured compile and memory cost. Provider's account-ID conversion and account binding remain SDK policy. **Disposition:** propose for next release, potentially unified with TERRA-3's parameter groups; only after measuring and testing three-state semantics and sensitivity. **Falsifier:** an existing declaration constructs all three per-request states across descendants without per-endpoint repetition, or a proposed group cannot retain those semantics without additional boilerplate.

## TERRA-5 — Generic adapters require handwritten traits over generated requests

**Task:** write one pagination/watch adapter for many operations, then register a new family. **Locations:** `examples/kubernetes-sdk/src/list.rs:74`, `:110`, `src/watch.rs:146`, `:173`; `examples/stripe-sdk/src/pages.rs:91`, `:109`; `examples/github-sdk/src/paging.rs:219`. **Classification:** developer friction. **Severity:** medium. **Evidence:** source-inspected, and Kubernetes/Stripe tests above reproduce the working adapters; `checks/maintenance-kubernetes/MAINTENANCE.md:273` records a separate downstream compile probe.

**Observed vs expected:** inherent `prepare`/`send` and setters have similar names but no generic trait. Kubernetes and Stripe independently wrap operations in provider-defined traits and macros; adding Ingress needs registration for list and watch, while the downstream probe had to handwrite its own implementation because the SDK macro is private. GitHub's adapter instead accepts `fn(Op) -> Result<Prepared<R>, Error>` per type. Expected: less per-operation forwarding while retaining provider-specific item types, cursor invariants and typed errors. A common `Prepare` trait alone would remove only the prepare forwarding/function pointer, not the provider's setters or its binding/consistency logic.

**Smallest credible change:** offer an opt-in `Prepare` trait with an associated output and `prepare(self)` for generated request types, implemented through the existing generated code. Before: `LinkPages::new(repo, id, None, op, OpType::prepare)`; illustrative after: `LinkPages::new(repo, id, None, op)` with `Op: Prepare`. Kubernetes still needs a `ListOperation` or explicit parameter-group-derived interface; Stripe still needs cursor typing. A provider-owned macro exported for downstream use or ordinary closures is a different, no-core alternative. A more powerful opt-in generated group trait should be evaluated separately rather than promising arbitrary common setters from structural similarity.

**Cost/compatibility:** opt-in avoids changing every endpoint, but trait method ambiguity, coherence, namespace collisions and generic `Send` constraints need compile tests. One impl per enabled operation adds expansion/type checking, no network cost or dependency; quantify on large SDKs. **Disposition:** propose a narrowly scoped experiment for next release, contingent on measured reduction across both SDKs. **Falsifier:** an existing public common trait already handles generic preparation, or an opt-in trait saves only a function pointer while creating equal or greater type/diagnostic burden.

## TERRA-6 — Stored filter records duplicate declarations and have separate evolution rules

**Task:** save/pass GitHub issue filters and add a new optional filter compatibly. **Locations:** `examples/github-sdk/src/api.rs:82`, `src/filters.rs:12`, `src/context.rs:326`; `checks/maintenance-github/MAINTENANCE.md:85`, `:123`; 4.3 prototype `v4/dx-4.3/experiments/generated-inputs/EVALUATION.md:136`. **Classification:** compatibility risk. **Severity:** medium. **Evidence:** source-inspected and independently staged maintenance observations; current filter wire test reproduced with GitHub operations test above. I did not re-run the staged old/new checkout or prototype measurements.

**Observed vs expected:** new `issue_type` was added to the declaration, the public `IssueFilter`, and the exhaustive wrapper's destructure/mapping. Declaration alone compiles while the record omits the new parameter. Adding a public record field breaks downstream exhaustive literals/patterns (`E0063`/`E0027` in the maintenance record), although `..Default::default()` consumers worked and generated optional setters stayed compatible. This is the SDK's hand-authored representation and Rust's struct evolution rule, not a defect in Concord's generated setter compatibility promise. Expected: an SDK can offer storable typed inputs with clearly documented evolution and a reliable way to avoid silent mapping omissions.

**Smallest credible fix:** document the distinction in SDK author guidance and prefer private fields plus constructors/builders for a new stable filter type; use a single source of truth or exhaustive mapping guard with tests for new options. Before `IssueFilter { state: Some(...), ..Default::default() }`; after a new API such as `IssueFilter::new().state(...)`, retaining old public record until a breaking release. This addresses future record evolution but cannot automatically catch a declaration-only addition. An opt-in typed input representation or rebind operation could address storage/mapping more directly, but must be prototyped rather than sold as free.

**Cost/compatibility:** making existing fields private or `#[non_exhaustive]` breaks current struct literals; additive replacement temporarily duplicates APIs. No runtime/network or dependency cost beyond any builder implementation. The prior unconditional generated-record prototype caused valid-name collisions and exposed field presence kinds as breaking API; measured 480 endpoints grew expansion 113,045 to 143,845 lines (+27%), bytes +36%, no-incremental median compile 2.60 to 3.01 s (+16%) (`EVALUATION.md:150`). These are historical experiment measurements, not new benchmarks or a runtime claim. An opt-in, collision-safe narrower record/rebind must measure both cost and evolution semantics; it cannot be assumed to solve shared parameter groups. **Disposition:** fix guidance now; reject unconditional 4.3 prototype as-is with this evidence. **Falsifier:** a reproducible unchanged exhaustive downstream literal compiles after adding a public field, or an additive existing representation provides typed storage, exhaustive mapping and compatible evolution without the measured costs.

## TERRA-7 — Built-in flat form cannot represent Stripe's nested body

**Task:** add/update a nested Stripe form field while preserving omit versus empty. **Locations:** `examples/compat/tests/forms.rs:8`, `examples/stripe-sdk/src/form.rs:21`, `:36`, `examples/stripe-sdk/tests/form.rs:36`; staged independent change `checks/maintenance-stripe/MAINTENANCE.md:67`. **Classification:** developer friction. **Severity:** medium. **Evidence:** reproduced `cargo test --offline -p concord-example-compat --test forms` (1 pass: flat accepted, nested built-in rejected before send, custom bracket format accepted) and `cargo test --offline -p concord-example-stripe-sdk --test form` (7 pass).

**Observed vs expected:** `Form` rejects a nested map/struct, while Stripe needs bracketed keys, indexed object sequences, repeated scalar arrays and explicit empty/unset. The SDK's custom `Encode` implementation supports them; the independent maintainer added `invoice_settings` without changing that encoder, demonstrating reuse once the provider policy exists. Expected: authors of another API with *the same* convention can reuse a tested optional encoder rather than implement a serde serializer. No independent second provider in this tree establishes that its conventions are identical; Stripe's omission/clearing and array spelling are provider policy.

**Smallest credible change:** publish a documented optional bracket-form recipe or reusable extras codec with explicit policies for map nesting, array indexing, null/empty and ordering; before `request StripeForm;` with a provider-owned serializer; after illustrative `request BracketForm<StripePolicy>;` only if the policy reproduces the exact current tests. A custom `Encode` is a genuinely different supported representation and may be preferable for a single provider. Do not change the meaning of existing `Form` or imply all bracket conventions match.

**Cost/compatibility:** new optional module/feature is additive; increases maintained serializer code, test matrix and possibly an optional encoding dependency; finite bodies already allocate and cost depends on implementation. No current endpoint or wire change unless opted in. **Disposition:** propose for next release only with a second independently verified consumer; otherwise maintain recipe and Stripe implementation. **Falsifier:** the stock Form accepts the reproduced nested value with exact Stripe bytes, or a second consumer demonstrates incompatible rules that cannot be expressed without a provider-specific serializer.

## Counter-evidence, diagnostics and overall judgment

- Nested scopes, required positional values, optional `maybe_*` setters, sensitivity and headers are effective: `examples/github-sdk/tests/operations.rs:62` covers routes, `:483` single-segment path encoding, and `:515` token rendering; nine tests passed locally. `examples/kubernetes-sdk/tests/declaration.rs` verifies namespace isolation, selectors and continued-token redaction (eight passed). No correctness defect in these mechanisms is established by this review.
- The `?` presence marker, initialized defaults, and inherit/omit/replace distinction are explicit in `docs/AUTHOR_GUIDE.md` §§2 and 4.6. `checks/maintenance-github/MAINTENANCE.md:130` shows exhaustive destructuring produces a useful E0027, though Rust's `..` escape can silently suppress that guard. My task's compiler messages correctly pointed to unavailable `Response::json` and missing test server status; full verbatim transcripts are in task notes/logs. These were ordinary integration mistakes, not evidence for a DSL diagnostic defect.
- The staged Salesforce CSV maintenance (`checks/maintenance-salesforce/MAINTENANCE.md:141`) and Stripe nested-field exercise show that carefully designed provider formats and models can absorb changes without changing the declaration or encoder. Shopify's GraphQL document/model coupling (`checks/maintenance-shopify/MAINTENANCE.md:287`) is provider/schema representation policy, not evidence that Concord should generate GraphQL. Salesforce's per-record-type endpoints (`examples/salesforce-sdk/FRICTION.md:17`) show a generic-output cost, but a native `Decoder` is available with a loss of endpoint identity; an endpoint-generic syntax is a larger, unmeasured opportunity, not a separate finding here.
- The independent CSV caller notes (`checks/dx03-csv-runtime/NOTES.md:23`) report no compiler errors and clear ownership; its first environment could not bind loopback, so its initial integration result is not treated as a pass. The other independent caller (`checks/dx03-fanout-sink/NOTES.md:465`) successfully used SDK pagination and typed errors, with limits documented there. Fixture manifests and stress data concern format/traversal evidence rather than DSL generation: the supplied `stress-256-54f96ab.json` measures streaming at source `54f96ab`, not macro expansion or 0dd65501 build cost, so it cannot substantiate a generated-code performance claim.
- The 4.3 generated-record experiment provides real counter-evidence to a wholesale representation change. No performance regression of the present DSL is asserted here; all proposed generation costs are unmeasured apart from the explicitly historical prototype. Provider URL validation, retry, redirect, pagination binding and credential policies remain SDK/application responsibilities.

**Judgment:** the DSL is capable and its native escape boundary is functional. The largest demonstrable authoring burden is compositional: extension contexts, lifecycle plumbing, repeated per-request declarations and provider-generic adapters. Address guidance and SDK-local safeguards immediately; validate opt-in primitives against compatibility, diagnostic quality and measured expansion before selecting a release surface. Seven findings: six developer-friction findings and one compatibility risk, all medium severity; none is claimed as a correctness defect.
