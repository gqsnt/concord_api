# SOL — Concord post-implementation review 4.4

Reviewed detached commit `0dd655018892a8cae21479f1cd249d2c875f6c83`, Rust 1.99.1, Linux, offline Cargo and loopback HTTP only. **4.4 is the review label.** This report does not prescribe the package/release version (the checkout declares 4.2.0).

The required external caller task succeeded before author conclusions were opened. See [TASK_NOTES.md](TASK_NOTES.md) for the reading boundary, the verbatim initial compiler error, and results. Its runnable consumer is [task/src/lib.rs](task/src/lib.rs): direct `Csv<NoHeader, Delimiter<b'|'>>`, an alias for headerful semicolon CSV, JSON Lines in `Yield` mode, and opaque-cursor item checkpoint/resume all work.

## Judgment and priorities

The composition boundaries are sound for the exercised provider slices. I found no reproduced HTTP chunk-boundary corruption, pagination window/budget violation, loss of an unread refused response, or leak through the main Concord error renderers. There are three concrete correctness defects, one resource limit defect, one compatibility risk, two documentation gaps, and two developer-friction findings below. None is high severity. The ordinary caller task and existing suites do not exercise the uncommon serializers, empty sources, or higher-ranked type spelling that expose the implementation defects.

Fix the small implementation and documentation defects before treating this review as closed. SOL-1 needs an encoder design decision; document the current requirement for stable serialization immediately if its implementation fix must wait. Preserve the existing native escape hatch, add a focused convenience API for its repeated transport/head plumbing in a future release, and qualify the SDK evolution promises. A broad replacement of the DSL or pagination architecture is not supported by this evidence.

The top three by practical priority are **SOL-1** (silently mismatched CSV schema), **SOL-2** (executor starvation through a valid byte source), and **SOL-9** (the documented additive declaration edit can break cloning callers). SOL-3 is a particularly small redaction fix.

## Reproduction convention

Commands for the new consumer/probes run from `review/sol/task/`, with `CARGO_TARGET_DIR=../target`. Five assertions of the desired invariant are deliberately `#[ignore]` so the normal consumer test remains green. Run an individual one with:

## SOL-1 — CSV validates a different serialization from the one it writes

- **Affected task:** write a finite or lazy CSV table with a custom `Serialize` implementation, including a conditionally shaped row. **Classification:** correctness defect. **Severity:** medium. **Evidence:** reproduced.
- **Locations:** `crates/concord-extras/src/csv/write.rs:397` calls `shape(row, expect)` and validates its names, then `write.rs:406` calls `writer.serialize(row)` again. The first pass really invokes user code at `crates/concord-extras/src/csv/names.rs:102`. Consumer: `review/sol/task/tests/defects.rs:37` and `:49`.
- **Reproduction:** run `csv_does_not_emit_a_header_for_different_fields`. A safe `Cell`-backed serializer emits field `id` on its first invocation and field `other` on the second, with the same width. **Observed:** two invocations and `Ok(b"id\r\n7\r\n")`; the value was serialized under `other`, but is labelled `id` in the emitted table. **Expected:** serialize a consistent snapshot, or refuse the mismatch in the actual writing pass. The module promises to compare every row's field names, including conditional serializers (`csv/mod.rs`, Writing). No public precondition requires a pure/idempotent serializer.
- **Recurrence:** one shared library encoder, used by finite `Vec`/`Rows`, `RawTable` and lazy `StreamRows`; not several independent SDK defects and not duplicated test code. No current provider row in this review was observed changing shape between invocations; ordinary derived serializers are counter-evidence to frequency, not to the reproduction.
- **Smallest credible fix:** validate the names/width during the serialization actually forwarded to the CSV writer, discarding that staged row on mismatch. A forwarding serializer can retain the current first-pass inference and check the second pass. A genuinely different representation is one-pass capture of names **and scalar values**, then write that captured record; an explicit schema/row encoder is another, larger alternative. A third unchecked serialization is not a fix.
- **Impact:** no public signature change is necessary; derived SDK rows retain their bytes. A forwarding check adds per-field work without another user `Serialize` call; one-pass capture trades temporary per-record storage for eliminating double execution. No new dependency is required. Finite and upload routes must use the same fix. Stateful serializers may now fail instead of producing mislabelled data, an appropriate behavioral correction.
- **Disposition:** **fix now**; if deferred, explicitly document the stable-serialization precondition as a temporary limitation. **Falsifier:** the same serializer is snapshotted once into a self-consistent record or the actual second-pass schema is rejected before its row is emitted. A derived-only test cannot falsify this finding.

## SOL-2 — Empty chunks bypass cooperative work accounting

- **Affected task:** feed any incremental reader from a custom always-ready byte source, e.g. an adapter that sometimes has no bytes to contribute. **Classification:** performance-resource limit. **Severity:** medium. **Evidence:** reproduced for JSON Lines; common cause source-inspected for CSV and consecutive JSON values.
- **Locations:** the public contract explicitly permits empty chunks at `crates/concord-extras/src/stream/source.rs:14`; `stream/driver.rs:82` loops and `:84` immediately continues on each empty chunk. No work counter or cooperative yield occurs in that loop. Consumer: `review/sol/task/tests/defects.rs:60` and `:79`.
- **Reproduction:** run `empty_chunks_yield_with_bounded_source_polls`. The source returns 100,000 ready empty chunks, then `b"1\n"`. Poll `next()` exactly once with a manual waker. **Observed:** `Ready(Some(Ok(1)))`, **100,001 source calls in one poll**. **Expected:** after a bounded number of empty-source polls, wake and return `Pending`, preserving progress. An indefinitely empty ready source would never return from that poll; this last statement is inferred from the exact loop, not tested with a hanging process.
- **Recurrence:** all three readers share `Driver::refill`; no independent SDK copy is involved. I did **not** reproduce a remote reqwest response generating this empty-chunk pattern. Normal network streams and the supplied stress generator do not establish immunity for the explicitly supported custom-source route.
- **Smallest credible fix:** count empty source polls inside `refill` and use the existing `yield_now` after a finite threshold. A different representation would expose `poll_next_chunk` and make source work one step in the reader's poll budget, but that is unnecessary for this fix.
- **Impact:** additive scheduling behavior, no public API/dependency change, constant counter cost; slightly more cooperative yields only for unusual empty runs. CSV, JSONL and watch-source adapters benefit; no change to valid record bytes, byte totals or EOF semantics. Empty chunks must remain distinct from EOF.
- **Disposition:** **fix now**. **Falsifier:** one poll of the unchanged 100,000-empty-chunk source returns `Pending` after bounded work, while subsequent polls still yield the record exactly once. Byte-only accounting that still counts empties as zero does not falsify it.

## SOL-3 — `Chunks::Debug` exposes complete response content

- **Affected task:** log a public in-memory source, or a returned `into_source()` value, while investigating a decode failure containing confidential data. **Classification:** correctness defect (diagnostic redaction inconsistency). **Severity:** low. **Evidence:** reproduced.
- **Locations:** `crates/concord-extras/src/stream/source.rs:33` derives `Debug` over `VecDeque<Bytes>`. The stream module's diagnostic policy at `stream/mod.rs:27` describes content-free `Display`/`Debug`. Consumer: `review/sol/task/tests/defects.rs:30`.
- **Reproduction:** run `chunks_debug_does_not_print_body`. **Observed:** `Chunks { chunks: [b"TOP_SECRET_BODY"], fail_at_end: None }`. **Expected:** chunk count/byte count and optional failure state, without chunk contents. This is not a leak through `ReadError`, and not a claim that reqwest's native `Debug` is covered by Concord's policy. The facade's older, narrower guarantee enumerates generated types/errors; this finding concerns the new module's public source helper and its broader diagnostic description.
- **Recurrence:** one shared source type; no SDK uses a separately copied implementation. This is mainly an in-memory/diagnostic exposure; no live response logging leak was demonstrated.
- **Smallest credible fix:** manual `Debug` reporting counts and whether a failure is configured, matching `RawRecord` and `StreamRecords`. An alternative is to designate this helper explicitly as unredacted in rustdoc, but that leaves an avoidable exception in the streaming API.
- **Impact:** debug text changes (potential snapshot updates), no type/signature/dependency change. Count computation is O(number of chunks) if total bytes are shown, O(1) for count alone; no body allocation needed. All format tests/adapters using `Chunks` are affected diagnostically only.
- **Disposition:** **fix now**. **Falsifier:** formatting the same value no longer contains the marker. An explicit design decision restricting the module guarantee to errors and documenting this helper as unredacted would instead justify reclassifying this as a documentation gap; it would not remove the observed exposure.

## SOL-4 — The generated `Clone` binder collides with a valid payload lifetime

- **Affected task:** declare a custom-format body whose directly written Rust type has a higher-ranked lifetime named `'__concord`. **Classification:** correctness defect. **Severity:** low. **Evidence:** reproduced, including a passing control.
- **Locations:** `crates/concord-macros/src/emit.rs:1424` prefixes each concrete payload type with `for<'__concord>`. Consumer: `review/sol/task/compile/lifetime_collision.rs:10`; passing control: `compile/lifetime_control.rs` (same type with the bound lifetime renamed).
- **Reproduction:** `CARGO_TARGET_DIR=../target cargo check --offline --features compile-probes --bin lifetime_collision`. **Observed:** E0496, `lifetime name '__concord shadows a lifetime name that is already in scope`. The body type `for<'__concord> fn(&'__concord str)` is legal Rust and `Clone`; the custom `Encode` implementation accepts it. **Expected:** this declaration compiles as does `--bin lifetime_control`. Both use an explicitly typed function pointer, so closure coercion is not the cause. See [lifetime-collision.log](lifetime-collision.log) and [lifetime-control.log](lifetime-control.log).
- **Recurrence:** one macro generator; none of the five SDKs writes this uncommon payload spelling. It is not an independently recurring provider bug. A type alias or renaming the user's bound lifetime works around it.
- **Smallest credible fix:** choose a binder name absent from all relevant payload lifetime tokens (preserving spans); add this case to hygiene checks. A more substantial representation is a request with a generic internal payload carrier, giving genuinely conditional `Clone` without the unused HRTB trick; that would require a compatibility design and is not needed here.
- **Impact:** compile-time only; no runtime, wire or dependency cost, no intended public-name change. The existing conditional-Clone canaries must continue passing. The HRTB workaround's future compiler stability remains a separate, already acknowledged risk (`checks/clone-compat/src/lib.rs:3`); this finding is a failure on the supported compiler today.
- **Disposition:** **fix now**. **Falsifier:** the exact unaliased collision probe compiles and clones on Rust 1.99.1 without renaming its user lifetime, with negative Clone canaries still failing appropriately.

## SOL-5 — Public Yield documentation misclassifies a malformed final line

- **Affected task:** count skipped versus terminal JSONL errors, especially deciding whether a completed download may be accepted. **Classification:** documentation gap. **Severity:** low. **Evidence:** reproduced.
- **Locations:** `crates/concord-extras/src/jsonl/policy.rs:205` says lines delimited by line feeds **or true end of input** are isolated; the implementation at `jsonl/lines.rs:558` makes **every bad final line without LF terminal**, including a type mismatch. Consumer: `review/sol/task/tests/defects.rs:100`. The earlier JSONL-04 decision in `v4/extensions-real-apis/DECISIONS.md` also describes EOF-line recovery; it is historical evidence, not the caller contract.
- **Reproduction:** run `final_delimited_by_eof_bad_line_matches_yield_docs`: input `1\nnot-json`, `Yield`. **Observed:** row 1, then `Format`, `is_terminal() == true`. **Expected from public enum docs:** an isolated nonterminal bad final line. The conservative implementation is defensible: a final line may be truncated. I recommend fixing the docs, not relaxing this protection.
- **Recurrence:** one library policy used by the Shopify bulk reader. Shopify's original `FRICTION.md:F7` describes the earlier absence of a terminal flag; **that defect has been addressed** by `ReadError::is_terminal`, and is not re-reported here. No current workflow false-completion defect was reproduced.
- **Smallest credible fix:** say that only LF-terminated bad lines are recoverable; valid final lines without LF remain accepted. Include this case in the reader overview and distinguish transport EOF from an LF terminator. A separate “recover even a bad final line” option would be a genuinely different policy, but no need for it was established.
- **Impact:** documentation only; no API, runtime, compile or dependency cost; helps every `Yield` caller, directly relevant to Shopify export completion decisions.
- **Disposition:** **fix now**. **Falsifier:** the public docs consistently describe the terminal final-line exception, or an explicit changed policy actually returns a nonterminal error for the repro. Merely adding `is_terminal()` examples elsewhere does not reconcile the contradictory enum documentation.

## SOL-6 — Discovery-failure outcome guarantee needs a caller-stop qualification

- **Affected task:** consume manifest jobs in `OnError::Continue`, observe a discovery failure, then stop pending jobs with `finish()` and classify the report. **Classification:** documentation gap. **Severity:** low. **Evidence:** reproduced.
- **Locations:** `crates/concord-pagination/src/jobs.rs:73` promises `Outcome::DiscoveryFailed` “either way”; `jobs.rs:356` separately documents `Stopped` when `finish` drops work, implemented at `:364`. Consumer: `review/sol/task/tests/defects.rs:115`.
- **Reproduction:** run `finish_preserves_discovery_failure_outcome`. Manifest 1 produces one permanently pending job and a next key; manifest 2 fails; `next()` yields `JobsError::Discovery`; immediately call `finish()`. **Observed:** `outcome=Stopped`, `discovery.failed=Some(At(..))`, one cancelled job. **Expected from the unconditional failure paragraph:** `DiscoveryFailed`. The cause is retained correctly and no job/budget invariant is violated; this is conflicting guidance about precedence, not lost failure identity.
- **Recurrence:** the single traversal implementation. Salesforce and the independent fanout caller use this API, but I found no copied report-classification defect in their tested loops; they normally drain it.
- **Smallest credible fix:** qualify the discovery-failure paragraph: `DiscoveryFailed` after draining known work; an early `finish` can report `Stopped`, and `discovery.failed` remains the authoritative discovery cause. Add an example of this branch. A different representation is orthogonal termination and discovery-status fields rather than one flat outcome; the report already approximates that, so a redesign is not justified by this small gap.
- **Impact:** documentation/test only, no API, runtime, compile or dependency cost. Changing outcome precedence instead would be observable for existing callers and should be a deliberate compatibility decision.
- **Disposition:** **fix now** (docs). **Falsifier:** both rustdoc paragraphs state consistent precedence, or the implementation deliberately preserves discovery-failure precedence and the changed behavior is documented/tested.

## SOL-7 — The iterator-to-stream convenience adapter unnecessarily requires `Unpin`

- **Affected task:** lazily upload serializable owned rows which are `!Unpin` (or use a `!Unpin` owned iterator). **Classification:** developer friction. **Severity:** low. **Evidence:** reproduced.
- **Locations:** `crates/concord-extras/src/stream/upload.rs:288` implements `Stream` only for `I: Iterator + Unpin`, though the iterator is private and never structurally pinned. `jsonl/writer.rs:140` accepts a stream without requiring `Unpin`, and `RecordBody` pins that stream in a box. Consumer: `review/sol/task/compile/from_iter_pinned.rs:17` (the upload call; see the full file for the serialized row).
- **Reproduction:** `CARGO_TARGET_DIR=../target cargo check --offline --features compile-probes --bin from_iter_pinned`. A row with `#[serde(skip)] PhantomPinned` is `Serialize`, `Send`, owned and `'static`. **Observed:** E0277: `PhantomPinned cannot be unpinned` through `Vec::IntoIter<Result<Row, Infallible>>`, preventing `FromIter` from being a `Stream`. **Expected:** the convenience wrapper can move/advance its privately owned iterator without pin-projecting it. Pinning the **outer** `FromIter` does not satisfy its existing conditional `Stream` impl; the compiler's suggested `Box::pin` alone is not the fix. Full output: [from-iter-pinned.log](from-iter-pinned.log).
- **Recurrence:** one foundation adapter, used by CSV and JSONL. CSV-13 in `DECISIONS.md` independently recorded this limitation; the current SDK rows happen to be `Unpin`, so it is not a reproduced SDK failure.
- **Smallest credible fix:** implement `Unpin` for `FromIter<I>` unconditionally (the private iterator is not structurally pinned) and remove `I: Unpin` from its `Stream` impl. A different representation is to store `Box<I>` and advance it through a movable outer pointer, with an extra allocation. Neither requires unsafe code. A caller can write its own stream adapter today, an unnecessary workaround for this helper.
- **Impact:** widens accepted inputs, no wire/runtime change with the direct fix, no dependency; an added auto-trait implementation is observable to exotic auto-trait-based callers and should be checked under the compatibility policy. Both lazy CSV and JSONL gain the same support.
- **Disposition:** **fix now**. **Falsifier:** the same direct `from_iter(vec![Ok(row)])` upload compiles without removing `PhantomPinned`, adding an allocation or changing the consumer's row type.

## SOL-8 — Repeated native send plumbing encodes an impossible success branch

- **Affected task:** retain selected response headers alongside a typed body, or inspect a successful head before decoding, while preserving endpoint-labelled redacted transport errors. **Classification:** developer friction. **Severity:** medium. **Evidence:** source-inspected across independently written SDKs; their loopback tests were rerun successfully. This is not a current incorrect-success claim.
- **Exact locations:** `examples/github-sdk/src/meta.rs:223` extracts the triple, executes, converts errors with an async `finish(Err(e))`, and needs `unreachable!` at `:228`; `examples/stripe-sdk/src/send.rs:453` repeats the sequence and has an impossible **successful response with status 0** branch at `:459`; `examples/salesforce-sdk/src/transport.rs:42` repeats it with `Ok((value,None))`; `examples/shopify-sdk/src/context.rs:152` repeats it for its served-version check. The constraining public API is `crates/concord-core/src/prepared.rs:291`: `finish` returns `Result<T, Error>`, though `Err(reqwest_error)` can only become `Err(Error)`, and the synchronous constructor is private (`concord-core/src/error.rs:85`).
- **Reproduction/observation:** inspect those four functions and rerun the SDK tests listed in `integration-tests.log`. All sends work, but each author has to unpack/execute/reassemble handling just to keep the head; all perform an async call typed as possibly successful to convert a known failure. **Expected:** a small public synchronous transport-error conversion on the decoder, retaining its endpoint, should return `Error` directly. A head-observation convenience should keep the canonical execute/decode behavior. `docs/RECIPES.md:63` teaches the current workaround accurately; documenting it has not eliminated the repeated consumer code.
- **Recurrence:** distinct provider implementations and distinct responses to the impossible branch (`unreachable!`, fabricated empty metadata, generic propagation) support recurrence beyond copied code. The `FRICTION.md` files for GitHub F1/F2, Stripe F4 and Shopify F3 describe the same boundary. The non-author GitHub maintenance exercise at `checks/maintenance-github/MAINTENANCE.md:243` separately observes endpoint labels lost by a newly constructed decoder. Kubernetes' bounded API-error reader is related but is **not** counted as another identical successful-head wrapper.
- **Smallest credible fix:** additive `Decoder::transport_error(&self, reqwest::Error) -> Error`, plus an example replacing the impossible branches. For the larger repeated task, propose a head-observing send/finish method returning caller-owned selected metadata on success and on failure after a head arrives. A genuinely different representation would return an accepted-head/body continuation before decoding; it exposes more lifecycle states and needs separate design. Do not make the library parse provider headers or preserve arbitrary bodies automatically.
- **Impact:** additive API, no required dependency, no additional HTTP attempt or body buffering; a generic head callback adds ordinary monomorphization. GitHub, Stripe, Shopify and Salesforce wrappers shrink; API-error document limits remain SDK policy. Preserve the current `into_parts` route for URL edits and custom streaming.
- **Disposition:** **propose for next release**; this repetition is not grounds to block the working integrations. **Falsifier:** an existing public endpoint-preserving synchronous conversion and head-observing send route can replace these branches without bespoke request execution, or the four cited implementations actually delegate to one reusable helper (they currently do not).

## SOL-9 — “Add an optional value: unchanged” omits loss of generated `Clone`

- **Affected task:** maintain a public SDK endpoint while keeping existing pagination templates or other callers that clone its request. **Classification:** compatibility risk. **Severity:** medium. **Evidence:** reproduced before/after compile result.
- **Locations:** `docs/AUTHOR_GUIDE.md:1380` says adding an optional/initialized value leaves calling code unchanged; `:1387` makes the same statement for an optional body. The generated Clone bound covers **every declared value**, even an absent optional one, at `crates/concord-macros/src/emit.rs:1426`. The caller guide correctly says Clone is conditional at `docs/CALLER_GUIDE.md:294`, but the evolution table does not state the exception. Consumers: `review/sol/task/compile/clone_before.rs:12` and `compile/clone_after.rs:12`.
- **Reproduction:** individually check `--features compile-probes --bin clone_before` (passes) and `--bin clone_after` (fails). The only declaration difference is `GET list()` → `GET list(query filter?: Filter)`, where `Filter: Display` is move-only. Calling code is identical and never sets `filter`: `let request = api.list(); request.clone().prepare(); request.prepare();`. **Observed:** after the additive edit, E0599 says `ApiList: Clone` requires `Filter: Clone`. **Expected from the table:** existing code compiles unchanged. See [clone-before.log](clone-before.log), [clone-after.log](clone-after.log). This is an actual compatibility failure under the documented edit, not a forecast that rustc will reject the unused-binder workaround.
- **Recurrence:** one macro rule; not a copied SDK implementation. The current five SDKs generally choose cloneable request values, and the staged additions in the maintenance exercises passed their frozen call sites. Those successes do not cover a move-only addition or all downstream request-trait bounds. Kubernetes `ListOperation` and several pagination-template adapters require Clone, so their compatibility depends on keeping these fields cloneable.
- **Smallest credible fix:** qualify the table and SDK maintenance guidance: parameter-list calls can stay the same while Clone/Send/Sync and other inferred properties change; preserve relevant traits when making supposedly additive edits. Recommend checking representative downstream trait bounds, not just `.send()`. Retain the deliberate conditional Clone behavior. A different representation is an explicit parameter object/borrowed request template whose duplication semantics are part of the SDK API, rather than an implicit trait depending on every declaration field; that is a larger future design, not a quick fix.
- **Impact:** documentation and compatibility-check policy change now, no dependency/runtime cost. For affected SDKs, deriving Clone on a suitably cloneable new value preserves source compatibility; an inherently one-shot value needs an explicit breaking-change decision or a new endpoint method. Do not assume cloning an actual one-shot body can be made safe. The existing stable Clone canaries passed (`clone-canaries.log`); no nightly toolchain was used or claimed.
- **Disposition:** **fix now** (guidance), with any representation change proposed separately for a future release. **Falsifier:** the documented compatibility claim is properly qualified, or the unchanged after-consumer compiles under a representation that can soundly retain the promised Clone behavior for absent move-only values. Passing only a non-cloning caller is insufficient.

## Evidence interpretation and deliberately unpromoted concerns

The author friction records were read only after the task, then compared with source and the independently staged maintenance notes. I did not count the same copied test or shared codec as independent recurrence. The SDKs' repeated filter/parameter records, the loss of page metadata in `.items()`, the need to checkpoint before a parent item whose child may fail, and closed downstream SDK extension registries are real maintenance costs in those records. They merit separate ergonomic design work, but I did not turn each into an additional unverified correctness finding.
