# Revised next plan for Concord desirability

**Review proposal, 7 November 2026.** Based on `concord-ecosystem-sdk50` at `c1b75b95387baf77cee9d93cf809d7ca7a64fd8f`. This is a proposed experiment sequence. It does not execute or expand any merge, push, release, deletion, or publication grant in the original pack.

## Objective

Improve complete author, caller, maintainer, and reviewer tasks while keeping the request contract visible, provider behavior explicit, and the simple path proportionate. Preserve automatic evaluation. Record human attraction and sustained adoption as unmeasured.

The detailed rules are in `Desirability_Contract.md`; the next executable experiment specification is `First_Experiment.md`. This plan deliberately distinguishes finishing the current campaign from choosing the next product change.

## A. Close truthful records and repair the measurement contract

Keep the original F-phase recovery, exact-source review, and verification procedures under their existing authority. Use real current state; the reviewed SHA is a source anchor, not a command to reset a newer branch.

Reconcile README, product charter, migration notes, changelog and capability status. Current source already has separate codecs/auth/retry/pagination/rate-limit crates, `SendWith`, operation identity, parameter groups, result templates and bounded response helpers. Do not plan them as absent. Preserve genuine pilot/accepted distinctions.

Before constructing the full I1-I5 measurement system:

1. Make complete task outcomes primary; demote generated share, wrappers, lines, hunks and words to diagnostics.
2. Separate prepared requests, SDK policy behavior/public results, and observed configured-transport requests.
3. Separate Concord-owned formatting, SDK-owned formatting, and native/application output boundaries.
4. Fix transform-aware canary exercise controls, including Basic auth, signing secrets and refused connections.
5. Validate each important instrument against a deliberately passing and failing case.
6. Use win/loss/inconclusive/keep-current outcomes. Call repeatedly consulted tasks validation; reserve final confirmation tasks.

**Exit:** the instrument definitions cannot reward an incorrect request, deleted provider validation, secret-key transmission, or moving the same work to callers.

## B. Run a docs-only caller-contract pilot

Run H04 on the current signatures without waiting for H01-H03. Compare current documentation against accurate hierarchy, concrete public result/error information, explicit base versus path, and the policy boundary of `prepare()`.

Witnesses: Cloudflare, Sentry, Kraken. Controls: Nager, Xero, Strava. Use the fixed sample and scoring in `First_Experiment.md`; these thresholds are proposed pilot decisions, not measured effects or universal statistical thresholds.

Keep behavior and API fixed. Compile submitted calls and check their intended request and result with independent fixtures. Do not let a server that answers solely by request order hide a wrong URL. Preserve first attempts and repairs.

**Exit:** a task-based result with per-SDK and per-provider evidence. Expand a winning candidate to affected generated documentation and existing required gates. Preserve a narrower deterministic correction even if a broad statistical pilot is inconclusive, with that narrower basis explicitly recorded.

## C. Compare small API hypotheses independently

### C1. Explicit policy completeness

Use the Strava omitted-edit witness: a newly added endpoint must not silently inherit inappropriate scope, quota or write-uncertainty behavior. Add unlike policy cases, such as POST reads and payment idempotency.

Compare an explicit SDK-local exhaustive mapping/trait approach with one narrow optional macro design. Keep classification meanings SDK-owned. The simple no-policy control must gain no required ceremony. Missing coverage should fail at an early, understandable stage; valid exceptions remain expressible.

This is not a proposal to put universal retry, authentication or quota semantics in Concord.

### C2. Ordinary Rust input inference

Compare current `IntoValue<T>` arguments against exact types for body/record arguments where target-driven inference matters. Test realistic `Default::default()`, `.parse()`, `.into()`, newtype, `None`, string-literal, borrowed-header and non-Clone-body calls.

Measure correct first calls, required type annotations, repair from diagnostics, and ownership/borrowing costs. Do not infer success from the absence of an internal type name. Preserve current convenience where it is useful.

### C3. Useful public construction and controls

Classify current wrappers by purpose before experimenting. Use Mastodon, Xero and an issued/dynamic-host SDK. Keep QuickBooks coordinated context replacement and credential rotation as contrary cases.

Compare current facades with a coherent author-controlled construction/visibility rule. A wrapper may remain the best answer. Measure valid ordinary construction and exclusion of invalid host/tenant/credential combinations, plus ability to perform supported changes.

### C4. Public results and reusable carriers

Split the old H02:

- **Carrier experiment:** a small optional value-plus-metadata shape, against current aliases and existing `decode_with_meta`/`Received` capabilities.
- **Provider-document experiment:** common mechanics for reading or carrying an error document, with SDK-owned classification and typed semantics preserved.

Use simple HTTP failures, Kraken envelopes, Cloudflare diagnostics and partial GraphQL data. Count caller matching changes and metadata preservation. Do not force domain-specific response names into a universal `value` field merely to reduce type count.

**Exit for each C experiment:** a complete pilot on unlike witnesses, a contrary case, and a simple control; independent review; explicit benefit and cost. Only surviving candidates receive full affected-SDK migration and broad verification.

## D. Pursue bounded helper work

These can proceed independently when they have a clear task and counterexample:

| Candidate | Intended benefit | Required contrary case |
| --- | --- | --- |
| Traversal start/resume operation | Avoid duplicated pages/pages-from concepts | Mailgun eager validation and bound continuation context |
| Page accepted, continuation failed | Preserve valid delivered records and explicit failure | Kubernetes snapshot, Elasticsearch partial response, Discord ordering |
| Transport recipe/helper | Name the configuration assumed by delivery/replay guarantees | Same-origin redirects; opaque supplied client cannot be certified |
| Optional SDK redaction helper | Centralize repetitive formatting without losing diagnosis | Encoded credentials, SDK Display, intentionally visible fields |
| Existing capability adoption | Remove repeated mechanics already served by public APIs | Provider-specific errors, metadata, retry/run behavior |
| Capability status reconciliation | Make current adoption/status claims truthful | A pilot's presence in source is not acceptance |

A shared helper should absorb a repeated mechanism while leaving different provider meanings visible. Preserve negative evidence and keep the current design when it solves the task with lower total burden.

## E. Validate the combined result and stop

Migrate all affected SDKs for accepted changes, update public documentation and migration notes, run the existing broad verification under the current execution environment, and record the exact source/CI identities. Do not transfer results between commits.

Freeze the candidate and run fresh final confirmation tasks. If those tasks change the design, retain the failed outcome and obtain new confirmation. Produce a retrospective organized by concept and actor: task, candidate, evidence, decision, costs, remaining SDK responsibilities and unmeasured claims.

Stop when no worthwhile supported task improvement remains in the bounded queue, the agreed resource budget is reached, or the owner pauses work. Do not use a raw count reaching zero as proof that desirability is complete. Preserve release authority separately from experiment acceptance.
