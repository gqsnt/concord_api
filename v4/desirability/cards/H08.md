# H08 An omitted operation classification is caught when the SDK is built

Family: POLICY
Status: PRE-REGISTERED on `concord-desirability` before any implementation; base = the head that
carries this card (H04 accepted). Thresholds below are frozen; no candidate exists yet.
Decision path: design hypothesis (PLAN_AMENDMENT_A1 §3); pilot, then migrate.

## Problem (measured / recorded)
- Adding an endpoint to an SDK whose send policy treats operations differently (scope, quota
  window, retry and write-uncertainty class, signing, paging) requires a second, separate edit:
  the policy's classification. Survey at the base (`reviews/h08-design-survey.md`): in none of the
  seven I4 e4 SDKs does a forgotten classification fail the SDK build. Strava's `Class::of` is an
  `==` chain over `Operation`s with a silent default (a new POST is charged to the read windows,
  gets no write scope and no uncertainty); Sentry refuses an operation missing from its `keys()`
  name table at run time and decides paging by the table position (silent default); Kraken
  refuses an unlisted (method, path) at run time; GitHub's listing id is a free string in a table
  (silent default); Kubernetes, Mastodon and Notion fail only at the caller's compile.
- Concord core cannot do better today without changing public types: `Operation` is not
  matchable (no const identity), and a `SendWith<T>` impl cannot require a per-endpoint bound
  (E0276). The only per-endpoint check at SDK build is `P: SendWith<Out>` on the output type.
- I4 baseline (B = `734991e9`): agents classified all 7 e4 tasks correctly (ceiling); the sealed
  e4 omission controls are detected only by the hidden oracle at run time for Strava, Sentry,
  Kraken, GitHub and Notion, at the caller's compile for Kubernetes and Mastodon.
- Owner charter (A2): Concord should act like a compiler for the API; the adopted review (C1, R06)
  names the Strava omitted-edit witness and asks for unlike policy cases.

## Comparator
- **Baseline:** current SDK code (hand-written classification; the best documented workaround is
  a run-time allow-list such as Sentry's).
- **Alternative A (SDK-local, today's core):** the class rides in the declared output type
  (a transparent wrapper with a class marker; the policy implements `SendWith` only for classified
  outputs), so an endpoint declared without a class fails `P: SendWith<Out>` at SDK build.
  Prototyped on Strava only, to measure its cost (public types change).
- **Alternative B (one narrow opt-in macro mechanism):** an opt-in client statement makes `api!`
  generate a per-client operation enum (one variant per endpoint, `#[cfg]` carried) and delivers
  the endpoint's variant to the send policy, so a policy written as a `match` without a wildcard
  arm fails at SDK build (E0004, naming the missing variant) when an endpoint is added. Nothing is
  generated without the statement. Exact syntax and delivery are the implementer's, within: one new
  DSL statement, at most one new public trait or type in core, no change for SDKs that do not opt
  in. Classification meaning stays SDK-owned (the enum identifies; the SDK's match decides).

## Witnesses, contrary case, controls
| SDK | Role | What must hold |
|---|---|---|
| Strava | witness (silent default) | scope, quota window, uncertainty decided by an exhaustive match; omission → SDK build |
| Sentry | witness (run-time refusal + positional paging flag) | support, bucket and paging decided exhaustively; omission → SDK build |
| Kraken | witness (path-keyed signing allow-list) | signed/public decided per operation, not per URL path (fixes the base-path refusal too); omission → SDK build |
| Cloudflare | contrary case (method-based read/create is correct) | not required to adopt; unchanged; its generated public surface unchanged |
| Nager | simple control (policy keyed on output type) | no ceremony: byte-identical public surface, no new statement |
| GitHub, Kubernetes | no-policy controls | unchanged unless they opt in; no new required item |

## Outcomes (A1 §2.2) and instruments
Primary — **change one provider fact: the stage that detects an omitted classification.**
Deterministic H08 omission harness (sealed, outside the repository, built after the candidate is
frozen by a lane the implementer never sees): per witness and arm, (i) the I4 e4 sibling task and
(ii) one new omission scenario (another endpoint whose classification differs from its nearest
sibling's), each with a reference patch (fully classified, passes its oracle) and an omission patch
(the same minus the classification). Stage ∈ {SDK build, caller compile, run-time refusal, wrong
behaviour caught only by a behaviour test, never}; plus whether the first diagnostic names the
missing endpoint. Validated like I4 (reference passes, omission detected at the recorded stage).

Secondary — **no loss on ordinary maintenance:** I4 e4 agent tasks for Strava, Sentry and Kraken,
Codex `gpt-6.1-sol` xhigh, 3 fresh repetitions per witness and arm (18 runs), paired; oracle pass
and classification correctness; hunks and agent time as diagnostics.

Costs (gates where bounded): rustdoc public-view JSON diff per SDK (public items added/changed);
SDK lines added/removed for adoption; concept count; `benches/scale/ab.sh` compile time and
expanded size per endpoint within +5%; `alloc-count` not increased; full gate and CI Linux/Windows
on the exact candidate; independent review.

## Decision (thresholds frozen here; pilot triage rules, not statistics)
- **WIN (B):** in ≥ 2 of 3 witnesses both seeded omissions move to SDK build with a first
  diagnostic naming the missing endpoint, and no witness scenario moves to a later stage than
  baseline; Cloudflare, Nager, GitHub and Kubernetes need no change and their public rustdoc JSON
  is identical apart from docs; I4 e4 agent runs: candidate oracle passes ≥ baseline passes for each
  witness (paired, 3 reps); concept budget ≤ 1 DSL statement + ≤ 1 public core item, and the
  mechanism removes a hand-written classification table or `==` chain from ≥ 3 SDKs (A7) in the
  full migration; guardrails and gates pass.
- **A instead of B:** only if A meets the same detection condition on Strava and B fails a gate or
  the concept budget; A's public-type changes are reported either way.
- **KEEP_CURRENT:** neither alternative moves omissions earlier in ≥ 2 witnesses, or the cost
  (ceremony for non-adopters, public type churn) exceeds the bounds.
- **LOSS:** a gate failure; a witness scenario detected later than baseline; any control gains
  required ceremony; an agent oracle regression in ≥ 2 of 9 paired witness runs.
- **INCONCLUSIVE:** exactly one witness improves; agent results disagree across witnesses; a
  harness or oracle cannot be built for a scenario.
- A WIN on the pilot leads to full migration: every SDK whose policy classifies operations by
  name, path or table adopts the mechanism (list fixed during migration and reviewed), then the
  broad gate and CI, before ACCEPT.

## Concept budget
≤ 1 new DSL statement, ≤ 1 new public trait/type in concord-core; a developer must remember one
rule ("an opted-in policy matches every operation, no wildcard"). Lint support may be suggested,
not required.

## Kill conditions
Defaults (DECISION_RULE) + any required change for an SDK that does not opt in; any change to an
existing public signature outside opted-in SDKs; a wildcard arm needed to compile a witness.
