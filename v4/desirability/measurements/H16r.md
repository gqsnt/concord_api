## The one clause that fails
The card's WIN requires, for each provider, that no witness SDK falls by more than 2 item-runs.
**Codex OpenAI falls by 3** (13 → 10), all on item `openai/w1` (binary file content, no Accept set by the SDK
or Concord): the candidate arm reports `accept` = reqwest's default `*/*` in all 5 repetitions; the baseline
arm missed the same field in 2 of 5 (a guessed format value). Claude misses it once in the candidate arm.

What the failure is: the question asks for "the request the server receives" and
restricts `headers` to those the SDK and Concord set, while the key scores `accept` as the Accept the SDK and
Concord set (none here). The candidate's generated header note and OpenAI's SDK-local note both state, truly,
that reqwest fills a missing `accept` with `*/*` at execution; read with the "server receives" wording, that
answer is defensible. This is an interaction between a true candidate statement and an ambiguous scored field of
the instrument (`score.py` compares `accept` directly with the filtered truth). The frozen scores and the failed
guard stand unchanged.

## Outcome mapping (proposed; the combined review checks it)
- WIN: **no** — the per-SDK guard fails (Codex OpenAI −3 > 2). All other WIN clauses hold.
- KEEP_CURRENT (card: pooled rise < 16 or only one provider rises): does not hold (+19, both rise).
- LOSS (card: control/contrary fall beyond ±1, non-doc change, gate failure): does not hold.
- INCONCLUSIVE (card: exposure check fails or ceiling): does not hold literally.
No card clause matches, and a failed WIN does not by itself imply KEEP_CURRENT (A1 §3 superseded DECISION_RULE
A3/A4, so A4 does not make it a LOSS either). The basis for the outcome: the deciding failure is a
verdict-relevant ambiguity of the instrument's question/oracle boundary (A3 §1; A1 §3 instrument validity),
so the result is **INCONCLUSIVE**. It never counts as a win, closes nothing (the REQUEST family stays open;
"not accepted" for stop rule 3), and candidate `02bc13b6` is kept unchanged.
