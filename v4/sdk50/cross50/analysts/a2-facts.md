The strongest finding is that **typed input access and exhaustive policy coverage are different problems**. Eleven SDKs recover declared inputs from requests; twelve classify behavior through HTTP methods. The `b34-values` experiment addresses some input recovery, but does not ensure that a new endpoint receives the required policy rules.

I would prioritize existing-API cleanup and documentation, then evaluate narrow typed policy access. The evidence does **not** justify adopting a general facts API solely to reduce code.

**Most valuable findings**

1. **The declaration-to-policy gap is real, but getters alone cannot close it.** Current [`Endpoint<T>`](/home/canarit/projects/Concord_SDK50_Ecosystem_Handoff/work/integration/crates/concord-core/src/prepared.rs:187) exposes only `prepare` and `operation`; [`SendWith<T>`](/home/canarit/projects/Concord_SDK50_Ecosystem_Handoff/work/integration/crates/concord-core/src/prepared.rs:235) accepts an arbitrary endpoint implementing that interface. Concrete generated getters would not be callable through this bound.

2. **Method predicates silently classify future endpoints in twelve SDKs.** These predicates govern different guarantees: replay, uncertainty, authentication requirements, or create-specific validation. They should not become one Concord-wide “write” rule. Strava’s maintenance experiment is particularly strong evidence: omitted quota, scope and uncertainty rules compiled; tests detected them (`strava-sdk/MAINTENANCE.md:116–147`).

3. **Some apparently redundant request inspection protects final-wire guarantees.** Adyen’s encoded-segment comparison, Xero’s tenant-header check, signing, and continuation binding cannot generally be replaced by original-value equality. The experiment actually encountered this distinction.

4. **Output-independent identity is already implemented.** The emitter generates inherent `Handle::operation()` and delegates the trait method to it (`crates/concord-macros/src/emit.rs:1713–1716,1735–1741`). Several SDKs still use the older output-dependent spelling. This is cleanup and documentation work, not a missing Concord capability.

5. **Several maintenance notes describe historical costs.** Square’s identity spelling is now fixed; Sentry derives capacity from `keys().len()`; Discord now declares one `Anchor: QueryPairs` rather than separate public cursor setters. Their remaining policy-context problems are still present.

The experiment’s most consequential boundaries are:

- **No exhaustive contract:** deleting a binding or adding an untagged write still compiles (`:106–114`).
- **No final-contribution guarantee:** a later override/removal or different wire placement can invalidate the interpretation of a bound value (`:114`).
- **Optional lookup weakens required local access:** Xero’s required reads use `expect`; A’s getters express required presence directly (`:110`).
- **Encoded equality matters:** the first Adyen port accepted original `a/b`, while the existing test required rejection after sending `a%2Fb`. The retained port added an explicit character restriction (`:116`).
- **API cost is material:** B added `Fact`, its associated type and `Endpoint::fact`, with **156 added / 4 removed runtime/compiler production lines**. It added callable surface even on unannotated endpoints (`:86–100`).

Thus B demonstrates useful policy access and removal of PayPal’s second inventory. It does not demonstrate that optional facts are the simplest general representation.

**What Concord could remove or shrink**

- **Remove stale documentation burdens immediately.** Square’s output-dependent identity complaint is resolved; Sentry’s independent capacity literal is resolved; Discord’s separate cursor-setter/wrapper descriptions are historical. Also revise `prepared.rs:183–186`: the statement about adding no generated namespace method now needs to acknowledge inherent `operation()`.

- **Shrink concrete identity ceremony using the existing API.** Besides the six SDKs above, Zendesk can compare the update operation’s identity instead of maintaining `"Zendesk.ticket.update"` (`src/policy.rs:120`). This removes a duplicated name, though it likely saves no physical lines.

- **Do not add automatic getters everywhere.** The experiment already shows unused method growth and sensitivity/body exclusions. Opt-in local readers have better evidence than a blanket expansion.

- **Treat `Operation::is_endpoint()` as a low-priority public-surface audit candidate.** No SDK production use was found. Core equality uses it internally (`crates/concord-core/src/response.rs:77–80,98–103`), so its implementation remains useful. This sweep cannot establish whether external consumers permit making it private.

- **Generated terminal methods are hidden in some integrations.** Registry’s private declarations use the custom executor rather than generated `send()` (`FRICTION.md:112–117`). Spotify’s authorization endpoint exists only to prepare a browser URL (`FRICTION.md:114–121`). An opt-out could shrink generated items, but adding syntax for unused private methods has no demonstrated source-size payoff.

- **Do not remove method identity, native request inspection, `Endpoint<T>`, or replay permission controls.** They are actively used. The evidence supports distinguishing their responsibilities more clearly, not collapsing them.

- **Do not add mutable version state merely to remove a constant duplicate.** Square’s two version spellings are real duplication (`src/lib.rs:30,53`), but converting the fixed header into a generated settable value changes the API guarantee. No new Concord feature is justified by these two lines alone.

**What remains undecided**

- Whether policy declarations should have a **mandatory typed classification**, optional facts, or endpoint-selected SDK policy adapters. Only the first can potentially reject missing coverage; its compatibility and declaration cost remain untested.
- Whether fact bindings describe original values or final surviving wire contributions.
- How explicit sensitive access should be named and bounded.
