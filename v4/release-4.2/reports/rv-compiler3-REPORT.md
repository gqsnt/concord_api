## Blocking finding: expression fragments that also parse as types are treated as safe to ungroup

**Location:** `crates/concord-macros/src/syntax.rs::bare_fragment` (lines 1274–1280), `regroup` (1301–1303), and its callers `parse_initializer` and `parse_type` (1258–1270). `&VALUE` is a valid expression fragment but also parses syntactically as the type `&VALUE`; the latter fact does not establish that its expression precedence is safe. The fragment is returned without explicit grouping and the proc-macro round trip exposes the unary borrow to the following method call.

**Reproducer and actual result:** `probes/src/bin/fragment_silent.rs` defines `Foo: Copy`, a static `VALUE: Foo`, and a `Meaning` trait whose implementations for `Foo` and `&Foo` return `"owned"` and `"borrowed"`, respectively. Both a plain Rust macro and a Concord declaration forward `$e:expr = &VALUE` and use `$e.meaning()`. The plain Rust function evaluates to `"borrowed"`; the generated Concord initializer selects the owned implementation and the prepared request has `n=owned`. The fixture asserts `n=borrowed`, so it exits 101 after printing:

```text
rust=borrowed concord=n=owned
```

The corresponding real rustdoc displays `Initially &VALUE.meaning()`, consistent with the erroneous generated result but not the declaration's Rust fragment semantics. `fragment_ref.rs` independently forwards `&VALUE` to `$e.len()` for a `usize` initializer: the equivalent Rust function compiles, while Concord reports E0277 because the emitted expression has type `&usize`.

**Type-position variant:** `probes/src/bin/fragment_const.rs` forwards `$e = &DATA` into `[u8; $e.len()]`. The equivalent ordinary Rust macro defines `[u8; 3]`; Concord instead reports E0308, expected `usize`, found `&usize`, at the array length. This goes through `parse_type` as well as the shared regrouping logic. Logs are `probes/logs/fragment_{silent,ref,const}.log`, with a real rustdoc log in `fragment_silent_doc.log`.

**Expected / impact:** The invisible expression fragment must retain the grouping Rust gives it: `(&VALUE).meaning()` and `(&DATA).len()`. Generated code instead behaves like `&VALUE.meaning()` and `&DATA.len()`. This can silently change a request's query bytes, not just diagnostic appearance; other contexts may fail to compile or change a declared const-generic type.

**Strongest counterargument:** This behavior also exists on `aae6218`; the correction fixes the specifically reported arithmetic case, and the reference/method-resolution example is a narrower Rust edge case. Nevertheless the re-review explicitly requires forwarded expressions and initializers to behave like the same Rust declaration, and the counterexample is a valid public API use with an observed runtime change. Archived `aae6218` controls independently print the same `rust=borrowed concord=n=owned` and report the same array-length error (`fragment_silent_aae.log`, `fragment_const_aae.log`). The finding does not depend on calling it a newly introduced regression.

**Requested regression:** Preserve expression grouping based on expression context rather than assuming that anything parseable as a type is safe to ungroup. Retain the runtime borrowed-versus-owned example, the array/const-position example, and their equivalent ordinary Rust controls. Test nested forwards, references, method calls, trait objects and opaque fragments in macro inputs together; assert actual bytes/types and rustdoc, not just token snapshots. Ensure a fix does not destroy fragment opacity inside downstream macros.
