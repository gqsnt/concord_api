## 2. Nested optional state

Use `T = i32` and an initialized comparison `x?: Option<i32> = Some(3)`.

| Call | Uninitialized declaration valid? | Initialized declaration valid? | Result |
|---|---|---|---|
| `set_x(None)` | yes | yes | `Some(None)`: present Rust `None` payload |
| `set_x(Some(7))` | yes | yes | `Some(Some(7))` |
| `replace_x(None)` | yes | yes | outer absence, `None` |
| `replace_x(Some(None))` | yes | yes | `Some(None)` |
| `set_x_if_some(None)` | yes | yes | preserve the selected slot exactly |
| `omit_x()` | yes | yes | outer absence, `None` |
| `reset_x()` | **no generated method** | yes | restore retained `Some(Some(3))` without reevaluation |

An initializer of inner `None` would reset to `Some(None)`. An explicit atom
adapter/representation decides the wire encoding of inner `None`; the outer
absence alone selects omission. My initial `reset_x` prediction for an
uninitialized slot was wrong.

Source: the same value-control matrix and §6.2 initialization boundary.

## 3. Explicit repetition

Keep `tags: Vec<String>` and write `query { append "tag" = each tags; }`.
An empty vector contributes no occurrence, one element contributes one, and
two elements contribute two in order. Existing inherited `tag` occurrences
survive because this is append. The statement does not change the Rust type.

Source: `docs/requests_and_values.md#query-and-header-programs`, §6.1 and §8.

## 4. Inheritance and optional patches

Assume an inherited `k=parent` and an optional local source `x`.

| Operation | Present local `x` | Absent local `x` |
|---|---|---|
| plain `"k" = x` over inherited writer | compile error | same compile error; static writers are checked before presence |
| plain `"new" = x` with no earlier writer | introduces local occurrence | emits no occurrence |
| `replace "k" = x` | replaces every old `k` occurrence, at the local position | removes old `k`, emits nothing |
| `when_present "k" = x` | replaces every old `k` occurrence | keeps inherited `k` |
| `append "k" = x` | appends local occurrence(s) | keeps inherited `k` |
| `remove "k"` | removes the named key | same; no value input |
| `query replace { ... }` / header equivalent | clears all inherited family occurrences, then applies local direct placements and block | same family reset; each local optional still controls its own emissions |
| `query off;` / header equivalent | clears inherited family and emits no local family entries at that owner | same; descendants may introduce new entries |

A present empty `each` sequence under `when_present` suppresses the inherited
key and emits zero values; absence preserves it. Query keys are case-sensitive;
header names are case-insensitive. Suppressed writers are not encoded. The
initial answer incorrectly gave plain assignment replacement authority.

Source: `docs/requests_and_values.md#query-and-header-programs` and §8.

## 6. Local overrides and fences

An endpoint selects one body/result representation with inline `via`; it does
not replace a sibling or the other direction. A scope's request/response
default affects descendants in that direction until replaced or fenced.
`explicit` removes inherited defaults; a deeper scope default or endpoint
inline choice supplies a new selection.

In the selected `overrides` scope add:

```rust
POST added(body input: String) -> String;
```

In the selected `fenced` scope add:

```rust
POST added(body input: String via Text) -> String via Text;
```

Removing the body `via Text` below the request fence produces `[C3-REP]`
naming body `input`, the authored endpoint, and `request explicit` at the
scope, with `request R;` or `body input: T via R` as recovery. Removing the
result choice produces `[C3-REP]` naming the endpoint and response fence with
`response R;` or `-> T via R` as recovery. These exact diagnostics were read
from the maintained request/response fence `.stderr` fixtures, not run locally.

Source: §9, the selected declaration, and
`crates/concord/tests/ui/fail/syntax/{request,response}_fence_requires_inline_representation.{rs,stderr}`.

## 8. Bounded traversal

All three arguments count **pages**, not items.

| Terminal | Before natural completion at bound | Zero |
|---|---|---|
| `collect_prefix(u32)` | successful `Prefix<T>` with bounded items and `PageBound`/`NextRequestKnown` summary | empty prefix; `PageBound`/`Unknown`; no operation ID or work |

`Done` on the final permitted page reports `Exhausted` without an extra fetch.

## 9. Byte and item streams

Both handles are acquired only after accepted-head validation and opening;
successful `.await` is acquisition, not body completion. `ByteStream::next()`
yields `Option<Result<Bytes, ApiError>>`, while `ItemStream<T>::next()` yields
`Option<Result<T, ApiError>>`. The item stream frames/decodes complete records;
the byte stream does not infer records and reports zero delivered records.

Transport failure applies to both; framing/decode failure additionally applies
to record streams. A terminal failure yields one error and then `None`, retains
`Failed` in the summary, preserves `ResponseObserved` and original correlation,
and never reconnects/retries after handoff. External cancellation terminates
with `Cancelled`; early handle drop is cancellation, never EOF. `finish()`
records `Application` without draining unless an existing terminal state must
be preserved. Dropping only a pending `next()` future is cancel-safe and later
reads resume bounded state; dropping a started page fetch instead cancels the
traversal. My initial answer did not distinguish dropped read futures from
dropped handles.

Source: `docs/streams.md`, particularly `#summaries-and-terminal-states` and
`#cancel-safe-reads`.

receive read-only, bounded facts and cannot mutate/veto/retry; built-in debug
has no header names or values. Request plans explicitly expose sanitized URLs
and ordered public headers; sensitive values are redacted but ordinary public
data may still be present. `ApiResponse::url()` is credential-sanitized and

## Final syntax clarification

The `= Some(3)` notation in the task-2 working answer describes the retained
payload, not valid inline DSL initializer syntax. The public stable-value
grammar requires a literal or Rust path, so the reproducible declaration is
`x?: Option<i32> = INITIAL_X`, with ordinary Rust
`const INITIAL_X: Option<i32> = Some(3);`. The compiled exercise and final fixture
sheet use that constant form. This clarification does not change the predicted
stored state or transition.

Specification §8.1 also makes the same-owner restriction explicit: `query off`
cannot coexist with a direct query placement at that owner (and likewise for
headers); use a replacement block. A deeper owner may still introduce entries,
as the new behavioral exercise demonstrates.
