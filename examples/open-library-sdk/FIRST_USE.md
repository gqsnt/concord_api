# Fresh consumer: Open Library SDK21

## Predictions

Recorded before writing or running the consumer code. I read the SDK README and generated rustdoc, and the official [Search API](https://openlibrary.org/dev/docs/api/search) and [Authors API](https://openlibrary.org/dev/docs/api/authors) on 2026-11-07. Live provider calls: **NOT_RUN**. These are predictions about the SDK against loopback fixtures, not claims about live behavior.

- Work workflow: construct an `OpenLibrary` with a no-proxy, no-redirect reqwest client and a loopback base; call `search().works("the lord of the rings").set_page(2).set_limit(2).send()`. Expect GET `/search.json` with URL-encoded `q`, `page=2`, `limit=2`, no request body or credentials, and transport-generated Host and possibly Accept headers. Expect a `WorkSearch` containing `docs`, count/start metadata when present; choose the first hit, call `id()` and then `works().get(id).send()`: GET `/works/OL27448W.json`, no query or credentials, returning a `Work`. A missing description/subjects should be `None`, not a crash. An empty page is success with no selection and no subsequent work request; no automatic traversal or reliable total-based completion is promised.
- Author workflow: `search().authors("j k rowling").send()` should GET `/search/authors.json?q=j+k+rowling` (or equivalent percent encoding), with the same headers and no pagination or credentials, returning an `AuthorSearch` and metadata. Select a hit by `id()` and call `author(id).works().set_limit(2).set_offset(0).send()`, GET `/authors/OL23919A/works.json?limit=2&offset=0`, returning one `AuthorWorks` batch. Another explicit offset call can preserve the first batch if the next fails; empty batch is a caller-observed stopping condition, not a snapshot guarantee.
- Both: non-2xx including 429 should be `Error::Http` with status and headers retained and an opaque bounded error-document result; no invented provider code and no retries. Malformed JSON, missing/wrong collection envelopes, incorrect media or body limits should surface as `Error::Concord`, retaining status after the response head; invalid/missing selected IDs should fail locally without I/O. Transport errors can happen before or during a body. No SDK credentials exist; query terms are sensitive in request/SDK error Debug, but success values, native request accessors and explicitly unredacted error documents can expose them. The caller owns what is logged and any credential/identification headers.

## First working call

The first consumer test run compiled and passed both workflows on 2026-11-07. It took the README's client/scope/endpoint calls, `NonZeroU32` for page and limit, `hit.id()` for the selected key, and a caller-supplied reqwest client pointed at a loopback `TestServer` with proxies and redirects disabled. The test-server rustdoc supplied `start`, `Reply::json`, request recording, decoded query pairs and shutdown. No SDK trait imports, generated endpoint types, native request escape, or SDK source lookup were needed. Every request was to loopback; live provider calls remain **NOT_RUN**.

## Friction incidents in order

1. The README makes the one-page boundary clear, but completion is an application decision: `num_found` and `size` are metadata rather than a trustworthy completion signal, and an author batch followed by a failed offset call requires the caller to retain the first batch and the continuation. No SDK completeness or partial-result type was discovered or assumed. This is appropriate to the declared bounded slice, but requires caller bookkeeping; a reusable pagination capability could carry page metadata, continuation and partial failures without changing the fixed client → scope → endpoint hierarchy. That is a proposed shared change, not an edit or a claim that this SDK requires it.
2. The initial test compiled and passed but the workspace `missing_docs` lint warned that the integration-test crate lacked a crate-level doc comment. Added the comment. This was test harness/lint friction, not an SDK failure.
3. A strict Clippy run flagged the test's redundant `first().is_none()` after `is_empty()`; removed the redundant assertion. This was caller test code, not a misleading SDK diagnostic.

The URL-encoding spelling and generated `Accept` value were not explicit in my initial prediction. No unexpected generated name, unneeded SDK import/type, SDK compiler diagnostic, or source lookup was encountered. `NonZeroU32` was required by the public example and enforces the documented nonzero inputs; it is extra caller syntax but was not an unneeded type. Reading the `testserver` rustdoc was necessary to discover its fixture API; its source was not read.

## Predictions versus observations

- Work: GET search carried the exact decoded `q`, `page=2`, `limit=2`; selected canonical key became GET `/works/OL27448W.json` without query. A work missing description and subjects decoded to `None`. Search page 3 decoded empty with count/start preserved and caused no work lookup; malformed `docs: {}` on page 4 produced `Error::Concord` with status 200. The selected work remained available after that later failure. The fixture made four requests, one for each explicit send. This matches the predicted single-page behavior; an empty observed page is a stopping choice, not proof of a stable collection.
- Author: GET author search had only `q`; the selected bare author key led to `/authors/OL23919A/works.json` with `limit=2&offset=0`. Count, start, exactness, author name/work count, batch size and entries were available. One entry with no title decoded successfully. A subsequent offset 2 returned 429, preserving the first two entries in the caller, status 429, `retry-after: 7` and the opaque JSON through the explicitly unredacted accessor. No automatic retry occurred (three explicit requests total), and the caller did not claim completion.
- Headers: all seven observed requests carried `Accept: application/json`, the caller's `User-Agent: first-use-fixture/1.0`, and the loopback `Host`; none had Authorization or a request body. The initial prediction allowed an Accept header but did not predict its value. Decoded query values, rather than one specific equivalent wire encoding or ordering, are asserted.
- Secrecy: generated work-search request Debug did not contain the query; SDK error Debug and Display did not expose the echoed fixture token, whereas the explicitly unredacted document did. This is a bounded check, not proof about every possible secret or log path.
- Not exercised by these fresh-consumer tests: transport interruption, malformed JSON syntax, incorrect media type, body limits, invalid IDs, non-429 statuses, default work pagination, author batch end, or the `prepare()` bypass. Their documented behavior was a prediction, not a fresh-use observation. Existing package tests also ran in the full package gate, but are not attributed to this fresh consumer.
