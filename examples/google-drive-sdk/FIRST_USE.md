# Independent first use

## Predictions, before writing tests

### A: list, retrieve and multipart upload
`files.list` sends GET `/drive/v3/files` with `spaces=drive`, projection and optional query; a continuation token causes another GET. A terminal page gives a complete collection; a failed page gives an error with the accepted prefix, not successful exhaustion. `files.get` sends GET `/drive/v3/files/{id}` and returns metadata. Multipart create sends POST `/upload/drive/v3/files?uploadType=multipart`, with a `multipart/related` body containing JSON metadata followed by the exact media bytes. Success returns created file metadata. A Drive error document should expose its code/message/reasons with HTTP metadata.

### B: resume and changes
Get a start token, initiate a resumable upload using POST `/upload/drive/v3/files?uploadType=resumable`, then use the returned Location for PUT requests. A 308 with Range acknowledges the prefix; after interruption restore the checkpoint and send an empty probe with `Content-Range: bytes */total`; send only the remaining bytes. A 200/201 with file metadata signals completion. A lost response requires probing before another send, and a 404 means expired session. Changes GETs use the saved page token; continuation pages have `nextPageToken` and the final page has `newStartPageToken` for the next poll. A truncated body or failed page must not be reported as a complete batch.

## Trace

1. First entry point: `examples/google-drive-sdk/README.md`, including construction, both workflow examples and completion/error contracts. Generated SDK rustdoc using `cargo doc -p concord-sdk-google-drive --no-deps` and Concord rustdoc with `--features csv,jsonl`; also read the pagination README and the testserver API. Consulted Google Drive's [upload guide](https://developers.google.com/workspace/drive/api/guides/manage-uploads), [files.list reference](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list), and [changes guide](https://developers.google.com/workspace/drive/api/guides/manage-changes).
2. Fixtures in this consumer are hand-authored synthetic documents based on those official descriptions, not copied documented examples. The byte-sensitive synthetic media is hand-authored at `fixtures/first-use-media.bin`; multipart framing expectations are constructed in the test from the advertised boundary. Existing `.gitattributes` keeps `fixtures/** -text`.
3. First compile reported two non-ASCII raw byte string literals, `failed.as_str()` unavailable because the failed position is `Resume<PageToken>`, and `as_deref()` unavailable because the provider reason is a `String`. Corrected the literals and used the documented resume variant and string type. The compiler pointed at SDK source in its diagnostic; I did not open the source or SDK tests.
4. Working path A: the loopback fake returned two list pages, metadata, a multipart result and a subsequent get. The test checked decoded query parameters, bearer header, both MIME parts and exact binary media. A separate 403 on page two retained the first item, failed position, provider reason and HTTP status. Working path B: saved a changes token, initiated a session, sent one aligned chunk, simulated a lost response after accepting the next, serialized/restored the checkpoint, probed the accepted prefix, sent only seven remaining bytes, then consumed two changes pages and retained the next polling token. Additional cases checked an expired session and a response body cut off during a changes page, followed by `Ended` rather than successful exhaustion.
5. Interventions: none involving SDK source or existing SDK tests; no native transport escape or other provider SDK example was used. All requests ran against `concord_example_testserver`, with synthetic authentication. No live provider calls were made.
6. Concrete friction observed:
   - Recovery is application orchestration: reproduce with `resume_interrupted_upload_and_poll_changes`. The caller must persist a checkpoint, restore, probe, calculate the source slice from `acknowledged()`, and decide what to do after an uncertain write. The public API supports the path, but there is no source-reader/resume loop; the README explicitly places these decisions on the application.
   - Changes polling requires page-level handling to preserve the next polling token. Reproduce with the same test: `pages.last().meta.new_start_page_token` is needed after complete collection, whereas item flattening discards this boundary. The caller must coordinate committing the batch and token.
   - A failed listing position is `Resume<PageToken>`, not `PageToken`: `failed.as_str()` produced E0599; matching `Resume::At(token)` exposes the token. The pagination README documents `Resume`, but this extra layer was not apparent from the workflow example.
7. Final verification: `CARGO_BUILD_JOBS=5 CARGO_TARGET_DIR=/home/canarit/projects/Concord_Consolidation_SDK20_Handoff/work/target-b cargo test --locked -p concord-sdk-google-drive --test first_use` passed 5 tests.
