# First-pass facts and friction

1. **Easy — Concord.** The declaration at `src/lib.rs:182` generates the endpoint, path-segment encoding, query serialization, JSON Accept header and request preparation. Reproduce with `tests/protocol.rs:18`: `br/x` stays a single encoded segment, `date` is encoded, the body is empty and `format=json` is sent. The first assertion expected the fixed query before the endpoint arguments; the observed target placed it last, and the test was corrected at `tests/protocol.rs:31`. Query order is not a provider requirement.
2. **Typed errors and response heads — Concord / SDK adapter.** A normal typed send checks status; this SDK needs both status and a provider document, including an error envelope under a 200 status. The `SendPolicy` at `src/lib.rs:204` explicitly prepares and receives, captures the head, branches on status, checks JSON media type, limits and decodes the error body separately, and maps successful decoding errors with saved metadata. Reproduce with `tests/protocol.rs:43` and `tests/protocol.rs:63`. The public `Received`, `ResponseMeta`, `bytes_limited` and `decode_limited` APIs make this possible, but the response classification and non-success decode path are repeated adapter work. The `examples/frankfurter-sdk/src/lib.rs` source supplied the receive/head/error handling pattern.
3. **Pagination adaptation — Concord / SDK adapter.** Concord does not infer a continuation from metadata; the adapter at `src/lib.rs:327` clones request context, rebuilds each generated operation, checks the returned page against the requested page and converts page counts into a `Page` continuation while retaining metadata. Reproduce with `tests/workflows.rs:36` and the mismatch in `tests/protocol.rs:98`. `concord-pagination` supplies lazy traversal, cap, resume and incomplete-prefix behavior as shown at `tests/workflows.rs:75`, but connecting it to the declared operation is manual library-facing code. This is a deliberate library boundary, not a patched library.
4. **Array shape and nullable fields — provider / SDK.** `src/lib.rs:96` models the success tuple and error tuple and `src/lib.rs:35` requires a present but nullable value; `src/lib.rs:48` accepts number or string metadata. Reproduce with `tests/workflows.rs:36` and the missing-value case at `tests/protocol.rs:63`. Concord's generic JSON decoder handles the serde types, but the SDK has to model the envelope and optional-versus-null distinction itself.
5. **Documentation evidence — provider docs.** The two requested official pages document JSON selection and the array in an indicator description, but their sample invalid response is XML and they do not provide a country-observation JSON body. The fixture translations at `fixtures/error.json` and `fixtures/year.json` are synthetic assumptions, not copied provider responses. See `PROVENANCE.md` for exact sources; no live call was made.
6. **Caller completion — application.** `tests/workflows.rs:96` must inspect `Incomplete` rather than treating a cap as a complete result; `tests/workflows.rs:147` resumes the same query at a page. The caller must retain identical query context and handle source changes between pages; the API does not provide a snapshot guarantee here. The crate documents page-level buffering and that item streaming drops per-page metadata in `README.md`.
