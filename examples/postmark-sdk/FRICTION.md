# Concord friction and decisions

Example-assisted. Consulted `examples/ntfy-sdk/src/lib.rs` for declaration, sensitive headers, and a policy attached to generated `send()`; `examples/ntfy-sdk/src/error.rs` for bounded error-document handling and safe formatting; `examples/ntfy-sdk/Cargo.toml` for workspace dependencies and lint conventions. Consulted `examples/testserver/src/lib.rs` for the requested loopback fixture server, request recording, delayed and truncated replies. No other example SDK files were consulted.

- **Ambiguous sends.** `Prepared::receive` performs one execution but `SendWith<T>` is generic across endpoints. The SDK checks the prepared HTTP method and maps POST transport and successful-response decode failures to `UnknownOutcome`; builds stay `Request`. This is provider semantics, not a generic rule for all POSTs. A small Concord improvement would expose explicit declaration metadata/tags for operation semantics to policies, avoiding the method check. The native prepared-request inspection is used only for this policy decision, with Concord still executing and decoding.
- **Error responses.** A status does not automatically decode the provider's error JSON. The policy manually selects bounded `Received::document`, preserves status on bad bodies, extracts integer `Retry-After`, and hides provider text in formatted errors. The provider owns the error schema and redaction choices; generic bounded reads already exist. A small improvement would be a reusable status-to-document policy helper, without putting Postmark semantics in core.
- **HTTP client retry and redirects.** Concord executes once, but the caller's reqwest client can retry or follow redirects independently. The SDK supplies a builder disabling both; callers can still pass a differently configured client or bypass the policy. Transport configuration remains caller-owned; a small improvement would be an opt-in transport configuration recipe or standard safe client builder, not an implicit global default.
- **Pagination.** Search is a single count/offset request. `concord-pagination` supports bounded traversal, but the requested workflow asks for one caller-selected page, so a traversal adapter adds machinery without benefit. Count and offset bounds are Postmark's; the provider validates them. No generic change needed for this slice.
- **Auth.** `concord-auth` offers authentication mechanisms and signing flows; a sensitive static server-token header in the declaration already fits. No adapter or generic change needed.
- **Retry and rate limiting.** `concord-retry` and `concord-ratelimit` support generic retry/limiting, but automatic resend is unsafe, and the slice needs only to expose 429 and Retry-After rather than assume a rate policy. Caller-controlled throttling is possible outside the SDK. No generic change needed.
- **Codecs.** `concord-codecs` JSON through the `concord` facade supplies encoding, strict media checks, decoding, and declared finite-body limits; no custom codec needed. Error text parsing requires explicitly selecting JSON and the error limit as above.
- **Models.** The SDK retains message details and event-specific data in a JSON map because Postmark events have heterogeneous detail shapes; this is provider modeling and preserves unknown fields. More typed optional email fields and filters are outside this small slice. No generic change needed.
