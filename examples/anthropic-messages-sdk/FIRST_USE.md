### Workflow 1: create and inspect blocks

Calls: `Anthropic::new(http_client()?, AnthropicConfig { api_key: ... })`,
`.with_base_url(server.url())?`, `MessageRequest::user("claude-opus-5-5", 128,
"Describe a quiet café in one sentence.")?`, then
`api.messages().create(request).send().await`.

Wire prediction: exactly one `POST /v1/messages`, no query parameters;
`x-api-key` contains the configured fictional key; `anthropic-version` is
`API_VERSION` (`2026-10-21`); `content-type: application/json`;
`accept: application/json`. JSON contains `model`, `max_tokens`, and
`messages: [{"role":"user","content":"Describe a quiet café in one sentence."}]`.
It has no `stream` field. HTTP supplies Host and framing headers.

Return: `Result<Response<Message>, Error>`; `value` has ordered content blocks,
`as_text()`/`block_type()` support inspection, unknown blocks remain uninterpreted.
`request_id()` and `meta` expose response metadata. `Message.kind` maps JSON `type`.
`usage` and individual counters are optional.

Failure prediction: invalid model/token/message-list input fails locally with
`InvalidRequest`; an illegal key header fails with Concord `Build`, delivery
`NotSent`. Non-2xx produces `Error::Api` with status, provider type/message,
request ID (header before body) and optional retry delay. An unreadable error
document still preserves status with `document_error()`. A malformed successful
JSON message gives Concord `Decode`; wrong media type gives `Metadata`;
oversize/truncated bodies give `Limit`/`Transport`. No automatic resend.
There is no pagination: one response is the result, not a page cursor.

Secrets: client/request/error debug output must not expose the API key;
server error messages require deliberate access and are omitted from error
Display/Debug. Message data itself is not redacted.

### Workflow 2: consume a stream through message_stop

Calls: reuse the same client and text request shape, but call
`api.messages().stream(request.streaming()).send().await`, retain the response
head, and repeatedly `next().await` with a per-event deadline. Read text via
`event.text_delta()`, inspect state and partial results, observe `MessageStop`,
then `Ok(None)`, and consume `final_message().await`.

Wire prediction: exactly one `POST /v1/messages`, no query; same auth, version
and JSON Content-Type as create; `accept: text/event-stream`; same JSON request
plus `"stream": true`. No continuation/restart request is implicit.

Return: `Response<MessageStream>` after successful status and SSE head validation,
before the body is consumed. Events arrive incrementally. `message_start`, block
start/deltas/stop, pings, message deltas and `message_stop` retain their order.
Counters from successive message deltas replace the counters they carry rather
than being summed. `end_turn` alone does not complete a message. `MessageStop`
sets state `Complete`; only then does `next()` return `Ok(None)` and a final
`Message` become available. There is no pagination; `message_stop` is the end.

Failure prediction: non-2xx before streaming is `Error::Api`; an incorrect 2xx
Content-Type is Concord `Metadata`. After HTTP 200, an SSE `error` becomes
`Error::Incomplete` / `ErrorEvent`, and clean EOF before `message_stop` becomes
`EndOfStream`, even if `end_turn` already arrived. Malformed JSON becomes
`InvalidEvent`; truncated SSE can be `MalformedStream`, transport failure
`Transport`, invalid order `Protocol`, oversized event `EventTooLarge`.
Partial text, open blocks, usage, request ID and accepted-event count remain
inspectable. A later `next()` gives `AlreadyFailed`; `final_message()` cannot
return a successful message. The server must see one request per explicit send.

Secrets: stream/partial/error Display/Debug omit generated text and provider
error messages; intentional accessors return partial content and provider message.
StreamEvent/Message Debug can contain application data. No key should appear
in errors. No automatic restart is safe or expected.
