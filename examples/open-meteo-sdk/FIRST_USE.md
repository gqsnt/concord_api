# Independent first use

## Predictions before implementation

A. For Berlin, `forecast(&query, ResponseFormat::Json)` should send one GET to `/v1/forecast` with latitude, longitude, hourly variables, timezone, forecast_days and `format=json`, plus `Accept: application/json`. An `Ok` should contain response metadata and a JSON forecast with units, timestamps and nullable values. Success requires full validated EOF; an HTTP 400 JSON problem should be `Error::Provider` with status, headers and decoded reason, while malformed successful data or an interrupted body should fail without partial data. There is no paging or retry.

B. Choosing `ResponseFormat::Csv` at runtime should send the same GET with `format=csv` and `Accept: text/csv`; the returned `Csv` should retain location fields, unit-bearing columns, parsed rows and original bytes. The call buffers and validates all rows before `Ok`: a bad late row or early end should be an error, not a partial result. Rows are then iterated in memory.

## Ordered trace

1. First entry point: SDK README construction and the two workflow examples, followed by generated `cargo doc -p concord-sdk-open-meteo --no-deps` rustdoc for domain and error fields. Consulted root Concord README and official [forecast docs](https://open-meteo.com/en/docs) and [OpenAPI description](https://github.com/open-meteo/open-meteo/blob/main/openapi/forecast.yml). Read `examples/testserver/src/lib.rs` for the local server API; it is test support, not SDK source. No existing provider SDK supplied this consumer's solution.
2. Fixtures below are independently hand-authored, based on the official JSON response/error shape and the SDK README's CSV two-table description; short samples, nulls, column reordering, quoting, and errors are synthetic test cases. They are not captured provider responses or conformance evidence. No live provider calls.
3. Implemented both workflows from those public entry points. The first `cargo test --locked -p concord-sdk-open-meteo --test first_use` compiled without compiler diagnostics and passed six tests. No SDK source or existing SDK tests were read, and no native transport escape, handwritten operation name, or library workaround was needed. The only support-code read was the loopback test server API. A formatting check then reported formatting differences in the new test file; `rustfmt` was applied to that file only.
4. Working path: construct `ForecastQuery`, configure `OpenMeteo::with_base_url`, call `forecast` with a runtime `ResponseFormat`, and match `ForecastData`. The fake recorded one GET per call, the expected base prefix, six query parameters and format-specific Accept. JSON exposed arrays and units; CSV exposed reordered values, null, quoted unknown cells and exact CRLF bytes. HTTP 400 retained its parsed problem and metadata; a non-JSON 503 retained its head and a document error; bad JSON arrays, wrong media and a late bad CSV cell failed. A chunked CSV connection dropped after all otherwise valid fixture bytes returned `Error::Concord` with the 200 head, demonstrating that bytes alone are not successful completion.
5. Friction observed: CSV rows are available only after a fully buffered and validated download, capped at 4 MiB, with no partial rows on failure. Reproduce with `csv_connection_cut_after_valid_bytes_is_not_completion` and `malformed_late_csv_row_fails_the_whole_forecast`: both return errors, so an application requiring incremental processing cannot use this public forecast path for it. This is a documented SDK limitation, not an inferred Concord defect. Also, the README explains the two CSV tables but gives no literal wire example or points to an individual fixture; building an independent fake required constructing the envelope from that description. Reproduce using `fixtures/first_use_forecast.csv` and `runtime_csv_yields_rows_units_and_original_bytes`; the synthetic file is an assumption tested against the SDK, not proof of provider wire conformance.
