# Changelog

This page lists what changed in each release of Concord. The five crates (`concord-api`, `concord-core`, `concord-macros`, `concord-extras`, `concord-testkit`) share one version and this single changelog.

## Unreleased

Upgrading from 5.0.0-rc.1: the changes that stop a program from compiling come first, each with what to write instead, then the changes that compile and behave differently.

### Breaking changes

- **The test kit's `concord_testkit::script::Request::url()` returns `&reqwest::Url`, not `&str`.** It is the same type as `url()` on the request that a transport receives. Compare its text with `request.url().as_str()`: `assert_eq!(sent.url().as_str(), "https://api.test/v1/tasks")`. The compiler's own message, ``can't compare `concord::reqwest::Url` with `str` `` (E0277), points at `PartialEq<Url>`, which leads to parsing a `Url`; `.as_str()` is the fix ([a script](docs/guide/testing.md#a-script-a-transport-with-virtual-time)).
- **The shipped pagers return a `concord::page::Paging<C>`, not a closure.** `by_offset`, `by_offset_limit`, `by_page`, `by_cursor`, `by_link` and `by_next_url` return a value that implements the new trait `concord::page::Pager`; `paginate by_cursor(…);` in a description compiles as before. Code that calls one as a function gets `` expected function, found `Paging<…>` `` (E0618): write `let mut pager = by_cursor(…);` and `pager.next_call(call, page)`, with `use concord::page::Pager;`. Code that returns one as `impl Fn(…)`, passes it where a function is expected or boxes it as `Box<dyn Fn(…)>` returns `Paging<C>` or `impl Pager<C>`, takes `impl Pager<C>`, or boxes it as `Box<dyn Pager<C>>`. Under `use concord::page::*;`, a method of your own named `next_call` on a closure can become ambiguous (E0034): call it by its trait. Each case, with its message, is in [upgrading from the release before](docs/guide/pages.md#upgrading-from-the-release-before).
- **`concord::page::Slot` has a third required method, `input()`**, which says which input of the endpoint a slot names: a `concord::page::InputId`, its position among the inputs. The slots that `api!` generates implement it. A slot of your own that wraps another returns the `input()` of the slot it wraps (`fn input(&self) -> InputId { self.0.input() }`); one over a call type of your own numbers its inputs with `InputId::new(n)`. `or_when_set` knows an input by it, so two inputs that share storage or take no room are two inputs, and a slot that forwards to one is that one.
- **`concord::Http` no longer lets `reqwest` resend a request on its own.** `concord::Http` is the default transport of every client. `Http::new()` and `Http::with(f)` set `reqwest::retry::never()` after `f`, as they already turned redirects off, so a `builder.retry(…)` written in `f` is replaced. Before, `reqwest` sent a request whose body is in memory or empty again, up to twice and whatever its method, after an HTTP/2 `REFUSED_STREAM` reset or a `GOAWAY` with `NO_ERROR`. Now a `GET` with no retry policy can fail with `Connect` after such a refusal; with `Retry::standard()`, the engine retries it as a counted attempt, within the call's `timeout`. A `reqwest::Client` of your own, passed to `with_transport`, behaves as before ([what can send a request twice](docs/guide/retries.md#what-can-send-a-request-twice)).
- **`SigV4::sign` refuses a request to an origin other than the one that the signer was made for**, with `SignError::WrongOrigin`, before it reads the credentials or the clock. This compiles as before and fails only when it runs. An adapter that signs for several origins and checks them itself calls the new `SigV4::sign_any_origin(request, region)`. The middleware is unchanged.
- **`concord::page::IntoNext` is implemented only by `Option<C>` and `Result<Option<C>, Fail<C::Problem>>`, for the call `C`.** An implementation of your own, such as `impl IntoNext<LocalCall> for Option<()>`, compiled before and now fails with E0277. A pager returns the next call itself: turn your own value into it inside the pager, and return `Option<C>` or `Result<Option<C>, Fail<_>>`.
- **`concord::transfer::TransferError::EmptyQuery` is removed.** `transfer::at` accepts a URL whose query is a lone `?` or only `&`, and sends it as written, as `at_url` now does; a `match` arm that names the variant no longer compiles, and can be deleted.
- **The test kit's `script::Cut` can no longer be written as a value**: only the script makes one. Code that finds it with `downcast_ref::<Cut>()` is unchanged. `script::UploadState` and `server::BodyState` are `#[non_exhaustive]`: a `match` on them needs a `_` arm.
- **Error texts that changed.** A test that compares the text of these errors needs the new one:
  - `SignError` texts start in lower case and have no final period: `the request leaves the signing origin`, `the request body is a stream and cannot be hashed`, and the eight others ([the messages](docs/reference/messages.md)).
  - `LimitError::InvalidPolicy` prints `the limit policy is invalid` (was `limit policy is invalid; check its bounds, keys and windows`), and `LimitError::TooManyKeys` prints `limit keys exceed max_keys` (was `limit key bound reached; configure max_keys`).
  - An offset of the call that is not a number of items (a negative one) has a `reason()` of its own, `the offset of the call is not a number of items`; `the offset cannot grow any further` is kept for a valid offset whose next value cannot be held.
  - At compile time, the help of message 7 (an input named after its scope) proposes a name that is free at every node that receives the input, and the entry that keeps its key on the wire, where it used to rename the input with `_id`.

### Changes that compile and behave differently

- **A next-page URL with an empty query is sent as given.** A URL from a pager or given to `at_url` that ends in `?` or `?&&` keeps it; before, `/slice?` went out as `/slice`, which can be another page. It is also no longer taken for the request just sent ([C2.6](docs/reference/contracts.md#c2-building-a-request)).
- **An offset that the call did not set counts as 0** in `by_offset`, `by_offset_limit` and `by_offset_total`, whatever the `Default` of its type; the type of the offset no longer needs `Default`. In `by_offset` and `by_offset_limit`, an offset that cannot be read as an unsigned number of items (a negative one) is now a Mismatch also on an empty or a short page, where the pages used to end quietly.
- **With a `Paging`, a page that says that more items follow and gives no next page is a Mismatch**, never the end: `has_more` returns `true`, or the offset is below the total of `by_offset_total`, and there is no cursor, no URL or no item. The page that arrived is returned first, and `reason()` is `the page says that more items follow, and gives no next page`. A pager of your own that ended quietly in that case and is rewritten with `has_more` ends with this error instead ([more items, but nothing to continue with](docs/guide/pages.md#more-items-but-nothing-to-continue-with-is-an-error)).
- **With a `Paging`, a call that sets two distinct inputs given to `or_when_set` is a Mismatch**, `the call chooses two moves: it sets two inputs that each choose one`. The call that fetched each page is checked, before any gate and whatever that page says, so the error follows the first page when the caller set both inputs, or a later page when a move set the second. An input given to two `or_when_set` is one choice, and the first written moves.
- **`max_hold` counts from when the limit receives the request**, the time that your key and cost functions take included; before, a slow function could let a request leave late. A request that needs no wait still leaves at once, whatever `max_hold` is.
- **A record stream checks the call's `timeout` before it yields to the executor, when a poll has spent its work budget.** A poll of a `RecordStream` frames at most 16 KiB and 64 chunks; when input that is always ready, such as comments or skipped records, spends that budget, the stream ends with the call's timeout error once the deadline has passed, instead of reading on. This holds for `Sse` and `JsonLines`, mapped or not.
- **One key of a `Limit` retains at most 1,050,128 bytes** on 64-bit Linux, up from 1,049,984: the bound of what the key's entry retains, before the spare slots of the table and the allocator's own overhead.

### Added

- **Pagers.** The trait `concord::page::Pager<C>`, with one method, `next_call`, is implemented for a closure `|call, page| …` that returns the next call, for `Paging<C>`, `Box<Paging<C>>` and `Box<dyn Pager<C>>`. A `Paging` adds what a page states and how the list ends: `has_more`, `stop_on_short_page`, `stop_on_short_page_of`, `only_when_set`, `or_when_set` and `map_next`. They are decided in one fixed order of steps, whatever the order of the calls: the call, the gates, the statements, the move, the short-page rules, the edits. Within a step, the order written still counts: statements are read in that order, the first `or_when_set` given an input is the one that moves, and the edits of `map_next` run in that order; `Paging::from_fn` and `Paging::from_pager` wrap a pager of your own, and `into_fn` turns a `Paging` into a closure. The new `by_offset_total(start, total)` stops at the total that a page reports. `paginate` takes any pager written as a call or a path, alone or at each tail of a plain block, `if` or `match` ([pages](docs/guide/pages.md)).
- **Typed streams of records.** `Sse::try_map(f)` and `JsonLines::try_map(f)`, finished by `until_last_record()` or `until_end_of_body()`, read a `RecordStream<T, client::Error>` whose errors are the client's own. The mapping returns a `Result<Step<T>, RecordFail<P>>`. `Step::Next` yields a value and `Step::Skip` none; `Step::Last` yields a last value and `Step::End` yields none; either one ends the stream, under both endings. A body that ends cleanly with neither is the end of the stream under `until_end_of_body()`, and an error under `until_last_record()`. A `RecordFail` is `RecordFail::problem(p)`, a Refused error with the API's problem; `RecordFail::mismatch("…")`, with a fixed reason; or a decoding failure through `?` on `SseEvent::json` or `JsonLine::json`. After its error, `try_next()` returns `Ok(None)`. Until an ending is chosen, the value of `try_map` is a `TryMap`, which is not a reader: the compiler then names the bound `EndOfRecords`, with the two methods to write. An endpoint whose stream names another problem type than the client's does not compile. `RecordStream` has a second type parameter, its error, `RecordError` by default, so `RecordStream<T>` means what it meant. A reader of records of your own makes the same errors with `ByteStream::into_records`, `RecordBody` and `RecordFault`, and keeps the call's timeout with `check_deadline`; a stream type of your own takes part with `concord::error::CarriesProblem`, which `Option`, `Result` and `Box` of such a type implement too ([a typed stream](docs/guide/responses-and-errors.md#a-typed-stream)).
- **A body decoded in an arm.** `Json::decode(bytes)` decodes JSON already in memory and returns the reader's `ReadError`; `.map_err(Fail::from_read)` makes it the failure of an arm or a pager, so an API that reports its errors inside a `200` keeps the location of a fault, as under `read Json;` ([the API's own error](docs/guide/responses-and-errors.md#the-apis-own-error)).
- **A request that was not sent.** `TransportError::not_sent()` lets a transport or a middleware state that no byte of a request was written, and `Error::request_not_sent()` reports it for the call. `concord::Http` states it for a failure of its connector, its connect timeout included.
- **Credentials.** `Renewed::rejected_when(f)` and `Rotating::rejected_when(f)`, with `concord::auth::Seen` (`status()`, `headers()`, `body()`), renew a token that the API rejects inside a `200`, as Slack does ([a token rejected inside a `200`](docs/guide/credentials.md#a-token-rejected-inside-a-200)). `RenewalError::not_sent(cause)` and `RenewalError::from_call(error)` give `RenewalError::NotSent` for an exchange that never left: `Rotating` then keeps the refresh token, and the next call exchanges it again ([an exchange that was not sent](docs/guide/credentials.md#an-exchange-that-was-not-sent)).
- **Rate limits.** `Bucket::max_in_flight(n)` caps the requests of each key of a bucket, beside `Limit::max_in_flight` for the whole limit ([a cap on the calls in flight](docs/guide/limits.md#a-cap-on-the-calls-in-flight)). `remaining_rfc3339(limit, remaining, reset)` reads a reset written as an RFC 3339 date, counted from the response's own `Date` when it has a valid one; a later response that reports less left for the same or a later reset lowers what is left at once, a reset whose refill was given is never refilled again while the key is kept, and a reset more than fifty years ahead teaches nothing. `Seen::until_rfc3339(text)` reads such a date in a `learn` function of your own ([a reset written as a date](docs/guide/limits.md#a-reset-written-as-a-date)). The feature `limit` now depends on `time`.
- **Retries.** `Retry::max_retry_after(longest)` sets the ceiling on the waits that a `Retry-After` or a `when` rule asks for: 60 seconds by default, as before. A longer requested wait means no further attempt. The random part of each wait keeps its own ceiling. A wait that Tokio's timer cannot keep ends the attempts with the last outcome.
- **Generated code.** `Endpoint::NAME` is the stable name of an endpoint (`"riot.matches.ids"`), shown on each endpoint type's page. Calls, clients and handles are `Unpin`, whatever their inputs hold. `docs/reference/reserved-names.json` lists the names that a description cannot use, for a program that writes descriptions.

### Fixed

- **Generated code keeps the names of your module out of its own.** It no longer calls methods of the core by method syntax in your scope, so a trait of yours with a method of the same name can no longer change a request or break the client, and a client named `Diagnostic` compiles.

### Documentation

- The limits page states how a learned list is checked: it is used whole or not at all, and a capacity that it reports replaces a declared one only for a window of the same period. For an API whose periods depend on the key, such as Riot, declare no window and let the limit learn them ([what holds for every limit](docs/guide/limits.md#what-holds-for-every-limit)).
- The troubleshooting page has a row for clippy's `result_large_err` on a function given to `try_map`, and `Fail::from_read` says that a header that does not parse is a `concord::mismatch("…")`.
- The crates page lists every crate in Concord's public signatures, with the major version that the surface is tied to, and the settings that `concord::Http` inherits from `reqwest` ([what the public surface is tied to](docs/reference/crates.md#what-the-public-surface-is-tied-to)).

## 5.0.0-rc.1

The first release candidate of Concord 5. It is not on crates.io yet: add it as a Git dependency (`concord-api = { git = "https://github.com/gqsnt/concord_api" }`).

Concord 5 turns one nested description of an HTTP API into a typed client built on `reqwest`. You write the API as a tree in `concord::api!`: a base, scopes, endpoints, and where each input goes on the wire. The macro generates a client type, one method for each endpoint, and one error type. The macro has no built-in format: `json`, `Json` and the pagers are ordinary Rust items, and your own can take their place. Retries are off until you turn them on, and never repeat a request that may not be repeated; a secret never appears in an error or a log; a call never waits forever on a silent server; and a test needs no network. See [Concord in ten minutes](docs/guide/tour.md).

- **Generated calls.** Each client has a `Call<E>`, where `E` is the endpoint's type. In type annotations and function signatures that name the call for `riot::matches::Ids`, write `riot::Call<riot::matches::Ids>`. Put inherent methods for that call in `impl riot::Call<riot::matches::Ids>`. In another crate, implement your trait for `riot::Call<riot::matches::Ids>`. A `Drop` implementation for one endpoint needs a wrapper around the call. Rename any scope or endpoint named `endpoint` directly under the client because its module reserves `Endpoint`. Use `E: riot::Endpoint` and `E::Value` to write one function for any call of the client. The endpoint type's page lists its options and what a send returns. The `Call` page lists the shared methods. See [Call a client](docs/guide/calling.md#the-public-api-of-a-client).

Optional features of `concord-api`: `gzip` and `deflate` make `reqwest`'s decoders available to `concord::Http`, which still decompresses only when `Http::with` turns it on, and `socks` makes SOCKS proxies available ([compression, proxies and TLS](docs/guide/calling.md#compression-proxies-and-tls)).

Beside the core, `concord` also ships four values, each built on the public traits of the core and each described in [the contracts](docs/reference/contracts.md#c11-a-credential-that-is-renewed-limits-records-a-returned-url), C11:

- `concord::auth::Renewed` (feature `auth`): a token that expires, renewed once for all the calls that wait for it and sent only to the origin of its base; and `concord::auth::after_401`, a retry rule for one more attempt after a `401`.
- `concord::limit::Limit` (feature `limit`): rate limits: a wait after a `429` with `Retry-After` (or, with `without_retry_after`, a wait that you choose after one without it), a cap on the calls in flight, and buckets with windows known in advance or learned from the headers of responses.
- `concord::read::JsonLines` and `concord::read::Sse`: readers of records into a `RecordStream`, each record held to a bound that has no default.
- `concord::transfer::at`: the call of a second description, sent to a URL that the API returned, once the URL is checked.

Two more values, and request body writers, are described in [the contracts](docs/reference/contracts.md#c12-body-writers-a-refresh-token-that-rotates-signing), C12:

- `concord::auth::Rotating` (feature `rotating`): a refresh token that the server replaces at each exchange. Each new pair is saved before either token is used, and a pair that the store could not keep is handed back to the application, never dropped. Its `RotationDriver` is a future that the application polls: Concord starts no task.
- `concord::sign` (feature `sign`): `SigV4`, AWS Signature Version 4, as a middleware that signs each attempt and as `SigV4::sign` for one request; `body_bytes` and `check_origin` for a provider's own proof.

- **Nested forms.** `bracket_form(value)` and `bracket_pairs(value)` (feature `form`) use bracketed maps and indexed lists.
- **Gzip requests.** `gzip(body)` (feature `gzip-body`) compresses buffered bytes and keeps their content type; the description sets the encoding header.
- **MIME multipart.** `multipart_mixed(parts)` and `multipart_related(parts)` (feature `multipart`) write buffered or repeatable parts with their own headers.
- **JSON records.** `json_lines(records, max_bytes)` (feature `json`) writes LF after every record and bounds the whole request body.

The core's `Body` has four items for body writers and large uploads, described in [the contracts](docs/reference/contracts.md#c12-body-writers-a-refresh-token-that-rotates-signing), C12.11 to C12.14:

- `Body::get_content_type()`: the content type that a body carries, whole, for a writer that wraps another body; `gzip` uses it.
- `Body::repeatable(make)`: a body whose stream is opened again, from its first byte, for each attempt, so that a large upload can be retried under the usual rules of retry. An edit sees a placeholder in place of such a body, and a failure of the body is the failure of its attempt. A `Body::stream` is still sent once.
- `Body::map_stream(map)`: a writer of your own around the stream of a body, run once for each opening; the multipart writers use it for a repeatable part.
- `Body::is_repeatable()`: whether a body can supply its stream again for another attempt, without opening anything.

The guide also has recipes that need no new item: a key made once per write, a documented download redirect, a large upload sent again with a new stream, binary frames, a multipart response and its batch, several hosts, and a provider's own HMAC proof.

### Coming from Concord 4

Concord 5 is a new design, not an upgrade in place: a description written for Concord 4 does not compile and must be rewritten. The package is now `concord-api`, used as `concord` in code. The main changes:

| Concord 4 | Concord 5 |
|---|---|
| Placement words in the signature | A plain signature; where each input goes is stated in the block |
| Four kinds of values, with a `?` mark | Two: required, or optional with a mark on the name (`count?: u32`) |
| `set_x`, `maybe_x` | `.x(v)` |
| Four keywords for exceptions | `override` and `remove` |
| `base` is fixed text, and may hold a path | A scheme, a host, an optional port and an optional path prefix; a placeholder in the host, or a whole base from an input of type `concord::Base` |
| No size limit unless one is set | 10 MiB by default |
| The caller brings the `reqwest` client | `concord::Http` by default; the caller may bring one with `with_transport` |
| An error exposes the unread `reqwest` response | A Refused error or a Mismatch keeps the status, the headers and at most 64 KiB of the body |
| A status with a meaning of its own needs a hand-written format | `status { }` arms in the description |
| No way to test without a socket | `with_transport(fake(...))`: a function that replaces the network |
| No logging | One `tracing` event, `retry`, with names and no values |
| Separate crates for auth, retry and pagination | `idempotent` and `paginate` in the description, `with_retry` on the client; a credential is a `Secret` input placed in `headers` or `query`; a signature is a `middleware`; a token that is renewed is `concord::auth::Renewed`, a middleware |
