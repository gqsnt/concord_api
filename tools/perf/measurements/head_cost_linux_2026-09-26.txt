Probe method (head_cost.rs): every category runs 1000 untimed warm-up operations (execution: 50), then one
counted batch of 2000 operations (execution: 200) under allocation-counter (a counting global allocator;
current thread only, which is where planning and the current-thread execution runtime run), then 9 timed
batches (execution: 5). "allocations/op" and "bytes/op" are allocation count and allocated bytes per
operation; "net allocations per batch" is allocations minus deallocations in the counted batch (negative
where inputs prepared outside the counted region are consumed and freed inside it; 0 = nothing retained);
"median/min ns/op" are over the timed batches. The counting allocator is active during the timed batches
in both versions. The four planned heads are printed first; they are identical in both versions.
The execution row uses the probe's own loopback responder (TCP_NODELAY, one write per response): the shared
concord-test-support scripted server writes a response head in several small writes without TCP_NODELAY
(crates/concord-test-support/src/server.rs `write_head`), which stalls every keep-alive response on a
~40 ms delayed ACK; this is why the existing bench's loopback execution categories below take ~44 ms per
request in both versions and cannot resolve client-side overhead.

Execution-time note: the loopback round trip is bimodal on this 2-CPU shared host (a ~23-25 us and a
~55-60 us mode, both seen in both versions; v2.1 runs 1-3 happened to fall in the slow mode). In runs 4-6,
where both versions were in the fast mode, the median of medians is 23778 ns (v2.1) versus 24249 ns (v3),
+2.0%. No execution-time conclusion beyond "within a few percent" is drawn.

Attribution (partial; not individually profiled):
- request binding +1 allocation (32 B): the generated `__concord_bind` creates the bound owner projection
  (`self.__owner.__bind(client)`, shared by `Arc`) that section 16.3 requires in every executable bound
  request (crates/concord-macros/src/emit/endpoint.rs); v2.1 bound without allocating. This is the whole
  +62 ns of the binding row.
- construction +1 allocation (24-32 B): v3 scope handles/intents hold typed shared snapshot storage
  (section 4.5 snapshot law); not isolated further.
- planning +3 to +9 allocations (+4-18% bytes, +7-11% time): v3 plans evaluate the two-phase symbolic
  patch program (PATCH-01/03: select surviving occurrences, then encode) through the owner projection and
  carry additional disclosed facts (body description, response accept, absence status, runtime-binding
  facts, and for rate-limited heads a value-free RatePlanSummary with per-policy schema descriptors and
  the limiter enforcement label, section 12.5). The rate-policy head has the largest byte delta (+715 B),
  consistent with the new schema descriptor. Which of these accounts for each allocation was not
  measured; this is a remaining gap against section 28.4's "separate newly added functionality from
  regression in an unchanged hot path".
- The existing bench (below) agrees in direction: cold 100-iteration "safe public planning" 212-240 us
  (v2.1) versus 340-385 us (v3), "request binding" 13.7-13.8 us versus 21.1-21.3 us, "generated endpoint
  construction" 10.1-10.5 us versus 12.9-13.0 us; v3 is faster for "generic specification selection"
  (84-91 us versus 52-54 us); the loopback execution categories are all ~44 ms per request (delayed-ACK
  stall of the shared test server, see above) and do not resolve client overhead.
