Method (head_first_use.rs): `head_first_use <category>` measures, in one fresh process and with no warm-up, the
first operation of one category; everything the category needs (the client, inputs, the request being planned,
the runtime and loopback responder) is prepared before the measured region, and the region is exactly the
operation and the drop of its result, as in head_cost:
  client-build          HeadApi::builder()...build() (not a head_cost row; included because it is the first thing
                        an application does)
  direct-construction   client.records(..).search(..)
  unbound-construction  HeadApi::unbound().records(..).show(..)
  binding               client.request(unbound_endpoint)
  plan-show             client.plan(&unbound_endpoint)
  plan-search           search.plan()
  plan-protected        protected.plan()
  plan-limited          limited.plan()   (rate policy)
  execution             runtime.block_on(exec.bounded().into_future()) on ExecApi, including opening the loopback
                        connection (TCP_NODELAY responder as in head_cost)
  sequence              all of the above in this order in ONE fresh process, each category's first operation
                        measured as it comes (later categories see the lazy state earlier ones initialized)
Allocation count, allocated bytes, peak live bytes (allocation-counter's maximum of bytes held at once during the
region) and net allocations (allocations minus deallocations in the region; > 0 = retained after the operation)
are counted with allocation-counter on the current thread. Bytes are allocation traffic, not resident memory.

Protocol: 20 samples per version and category, one fresh process per sample and category (isolated mode) plus 20
fresh `sequence` processes per version; within each sample the versions alternate, v2.1 first on odd samples
and v3 first on even samples. 400 processes, every one exited 0.

Preliminary block (discarded, disclosed): the same protocol ran once at be5b95c, whose execution row built the
operation future outside the measured region (v3 161 allocations / 73,940 B, v2.1 93 / 61,103 B; the boxed
future was not counted). 89b2cbc moved `into_future()` inside the region to match head_cost; every other row gave
the same counts and bytes in both blocks. Only the 89b2cbc block is reported below.
