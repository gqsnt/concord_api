# DSL, clients, scopes, and request shaping

> Audience: Basic  
> Covers: the `api!` macro, client construction, scopes, endpoints, hosts, paths, queries, and headers

Concord is DSL-first for ordinary use. This page describes the structural language generated by `api!` and how values become a logical request without exposing native transport objects.

## DSL basics

### Shape of an API declaration

```rust
api! {
    client CatalogApi {
        base "https://catalog.example.com/";
        var tenant: String;

        GET Item(id: u64) -> Json<Item> {
            path ["items", ep.id];
        }
    }
}
```

A macro invocation may define several clients. Client names must be unique. Generated child names are normalized to snake case, so names that normalize to the same Rust method are rejected.

### Client order

A client body follows this structural order:

```text
base
var declarations
credentials block
retry selection
host
path
query
headers
auth
timeout
rate_limit
rate_limit_observer
scopes and endpoints
```

Most entries are optional, but `base` is required and comes first. Each layer—client, scope, endpoint—may contain at most one host/path/query/header/timeout/rate-limit declaration in the supported order. Authentication may contain several local placements in one contiguous group.

### Values and namespaces

Public request-shaping expressions use three namespaces:

- `vars.name` for immutable client values.
- `scope.name` for the current scope's parameters.
- `ep.name` for endpoint parameters.

Secrets and credential material are never public-expression values. They are referenced only inside the credentials and authentication DSL.

```rust
path ["tenants", vars.tenant, "items", ep.id];
query { "locale" = scope.locale; }
headers { "X-Region" = scope.region; }
```

`fmt[...]` concatenates displayable public values without introducing arbitrary Rust execution:

```rust
path [fmt["item-", ep.id]];
```

### Methods and aliases

Standard HTTP verbs are written directly. Extension methods use `METHOD("TOKEN")`:

```rust
METHOD("PROPFIND") Resource(id: String) as fetch -> Text;
```

The alias becomes the generated method name while the endpoint type keeps its declaration identity.

### Bodies and responses

The final endpoint parameter may be named `body`:

```rust
POST Create(body: Json<CreateInput>) -> Json<Item>;
PUT Upload(body: Stream<OctetStream>) -> NoContent;
```

The body type must implement `RequestBodySpec`; the response type must implement `ResponseBodySpec`. The macro stores Rust types rather than a closed category enum.

### Inheritance

Client configuration flows into scopes and endpoints. Layer-specific operations decide whether a child appends, replaces, removes, disables, or adds to inherited state. Rate limits are different: lexical client, scope, and endpoint rules always add in order and cannot be disabled by descendants.

### Compile-time errors

The macro reports structural errors: unsupported order, duplicate names, invalid references, malformed routes, forbidden auth/header collisions, invalid pagination bindings, and invalid rate-limit grammar. Ordinary Rust type checking reports missing trait implementations, wrong body inputs, inaccessible pagination fields, and incompatible types.

For exact syntax, use the [DSL reference](../reference/dsl.md#dsl-reference).

## Client configuration

The generated builder collects required values, secrets, providers, HTTP configuration, and runtime configuration. Configuration closures are applied before the client is built and become an immutable runtime snapshot.

```rust
use concord_core::prelude::DebugLevel;
use std::num::NonZeroUsize;
use std::time::Duration;

let client = Api::builder()
    .tenant("tenant-a".to_owned())
    .api_key("secret")
    .http(|http| {
        http
            .https_only(true)
            .connect_timeout(Duration::from_secs(5))
            .read_timeout(Duration::from_secs(15))
            .retry_off()
    })
    .runtime(|runtime| {
        runtime
            .request_body_limit(NonZeroUsize::new(8 * 1024 * 1024).unwrap())
            .response_body_limit(NonZeroUsize::new(8 * 1024 * 1024).unwrap())
            .debug(DebugLevel::Basic)
    })
    .build()?;
```

### Generated constructors

A generated client exposes:

- `Client::builder()` and `ClientBuilder::new()`.
- `Client::new(...)` when all required construction inputs can be supplied positionally.
- named setter methods for client values, secrets, and custom providers.
- `.http(|builder| ...)` and `.runtime(|builder| ...)` exactly once each.
- `.build()` returning `Result<Client, ClientBuildError>`.

`new(...)` orders required public client values first, then secrets, then custom providers. The builder is preferable when optional values or configuration closures are involved.

### HTTP configuration

`HttpConfigBuilder` supports:

- connection and read timeouts;
- pool idle timeout and idle connection count;
- TCP keepalive and no-delay;
- HTTPS-only enforcement;
- HTTP/1-only or HTTP/2 prior knowledge;
- one validated proxy origin;
- application retry off or Reqwest default retry;
- provider retry selection;
- custom root certificates and client identity PEM under `default-tls`;
- disabling enabled decompression formats;
- dangerous custom retry under its feature.

Application traffic defaults to retry off. Provider traffic uses a separate managed client and reviewed provider retry policy.

### Runtime configuration

`RuntimeConfigBuilder` owns finite limits, hooks, debug defaults, limiter selection, and cooldown caps. See [Limits and defaults](../reference/features-limits-and-errors.md#limits-and-defaults) for exact defaults.

### Clone and build behavior

- Cloning a built client shares its immutable runtime, credentials, limiter, hooks, and HTTP clients.
- Building another client creates an independent runtime and default governor state.
- Installing the same `Arc<dyn RateLimiter>` in several clients intentionally shares that limiter object.
- Pending requests retain the runtime snapshot of the client from which they were created.

### Build errors

`ClientBuildErrorKind` distinguishes missing input, invalid base URL, unavailable TLS, HTTP configuration, runtime configuration, unavailable required limiter, and internal safe failure.

### What cannot be changed per request

A request can override timeout and debug level. It cannot replace the built HTTP clients, hooks, limiter, finite limits, provider channel, or transport behavior.

## Scopes and endpoints

Scopes group endpoints under shared parameters and configuration. They are compile-time generated facades, not runtime registries.

```rust
scope Regions(region: String, locale: Option<String>) {
    host [scope.region, "api"];
    path ["regions", scope.region];
    query { "locale" = scope.locale; }

    GET Item(id: u64) -> Json<Item> {
        path ["items", ep.id];
    }
}
```

Application use:

```rust
let item = client
    .regions("eu-west".to_owned())
    .locale("fr".to_owned())
    .item(42)
    .await?;
```

### Scope parameters

Scope parameters are required or optional Rust values. Generated scope facade setters are available for optional values. Scope values are captured into endpoint snapshots; later operations do not mutate the client.

Scopes may nest to a maximum depth of 64. Configuration is inherited lexically.

### Endpoint parameters

Endpoint parameters become constructor arguments and builder methods. An optional endpoint parameter can usually be omitted and later set on the returned request/endpoint builder, depending on the generated shape.

### Explicit endpoint values

Every endpoint also has a public endpoint struct under a generated module:

```rust
let endpoint = catalog_api::endpoints::regions::Item::new(
    "eu-west".to_owned(),
    42,
);
let request = client.request(endpoint.locale("fr".to_owned()));
```

Explicit endpoints are useful for storing request descriptions, generic application code, or selecting endpoints without immediately constructing a request. They remain bound to the generated client capability; an endpoint from another client is rejected by Rust typing.

### Scope and endpoint names

Generated public method names use deterministic snake-case conversion. Acronyms are normalized predictably. Reserved names such as `builder`, `build`, `request`, `response`, `paginate`, and `debug` cannot be used for generated endpoint methods.

### What scopes do not provide

- They are not mutable server-side sessions.
- Scope parameter values do not create separate generated rate-limit buckets; lexical declarations own buckets.
- A scope cannot declare retry policy or a rate-limit observer; those are client-only.
- A scope does not grant access to secrets, credentials, native requests, or shared client mutation.

## Request shaping

Concord builds a logical URL and public headers from client, scope, endpoint, and pagination state. Authentication is materialized later at the private native boundary and is not inserted into the logical URL or public header map.

### Host

```rust
host [vars.platform, "api"];
```

A host declaration replaces inherited generated host labels while retaining the validated base domain structure. `host off;` returns to the fixed base host. Static labels are validated by the macro; dynamic labels are validated before protected execution.

### Path

```rust
path ["v1", "items", ep.id];
path replace ["health"];
path off;
```

Normal `path [...]` appends owned encoded segments. `/`, `?`, `#`, `%`, and `..` inside a dynamic segment remain data and cannot inject route structure. `path replace` replaces inherited generated segments; `path off` returns to the base path.

### Query

```rust
query {
    "search" = ep.search;
    "tag" = ep.tags;
    "locale" = scope.locale;
}
```

- Optional values append nothing when absent.
- Repeated values preserve iterator order.
- `query replace { ... }` replaces inherited public query entries.
- `query { remove "name"; }` removes a named inherited entry.
- `query off;` removes generated public query entries.

Authentication query parameters are separate and exist only in the native URL.

### Headers

```rust
headers {
    "X-Tenant" = vars.tenant;
    "Accept-Language" = scope.locale;
}
```

Header names are case-insensitive. Assigning a name replaces an inherited value for that name. `headers replace`, `remove`, and `headers off` mirror query operations. Reserved transport and authentication-sensitive header names are rejected.

### Expressions

Supported public expressions are:

- string literals;
- unsuffixed base-10 integer literals;
- `vars.NAME`, `scope.NAME`, and `ep.NAME`;
- nested `fmt[...]` concatenation.

Arbitrary calls, methods, macros, collections, blocks, secrets, and credentials are intentionally unavailable.

### Canonical identity

Pagination cycle protection derives a canonical structural identity after bound pagination fields have shaped host, path, query, and public headers. Authentication, request bodies, and native URLs are excluded.

### Security boundary

Hooks and debug events receive a safe logical URL and sanitized public headers. The selected custom limiter can intentionally receive semantic plan information, but generated lexical rate-limit plans contain no request values.
