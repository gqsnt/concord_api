Concord is a Rust library with one macro, concord::api!. You write a nested description of an HTTP API—its hosts, paths, credentials, and what its responses mean—and the macro generates a typed client over reqwest. This page is a working handbook: come here to build or look up something and leave having done it. Where a rule reflects a deliberate design trade-off, links point back to the design monograph.

Every piece of Rust on this page was compiled, and every claim about what goes out on the wire was checked by a test. Concord is at release candidate 5.0.0-rc.1, on GitHub and not yet published to crates.io.

Part I · Foundations

CHAPTER 01 · First clientStart

Add it to a project

The package is concord-api; the crate name you import in Rust is concord. Concord requires Rust 1.96 and a Tokio runtime to send a call. json, form, rustls, http2, and system-proxy are enabled by default; see Cargo features for the rest.

A first client

Here is a four-endpoint client followed immediately by the code that calls it:

↓ Calling the generated client

Read the description from the outside in:

  • pub client Shop(region: String, key: Secret) generates the client type Shop with Shop::new(region, key), plus a sibling module shop holding handles, call types, errors, and retry aliases.
  • Statements at the top of the client apply to every endpoint below: URL base, shared headers, and the response reader. There is no default format, so read Json; states it once.
  • scope books groups endpoints under a path segment and becomes a zero-I/O handle method shop.books().
  • Each endpoint declares an HTTP method, name, inputs, and return type; its block maps inputs onto the wire. The guiding rule (why): the signature is what callers see; the block is what goes on the wire.

On the calling side:

  • Required inputs are positional arguments in declaration order. They accept the type, a reference to it, text for String or Secret, and slices/arrays for Vec.
  • Optional inputs (year?: u16) become named setters on the call; unset inputs send nothing.
  • .await sends the call. Every endpoint on a client shares one error type (shop::Error, an alias for concord::Error<Problem>) and shop::Result<T> so ? composes across calls; non-2xx domain branches (like 404 => None) move into the return type instead of per-endpoint error enums (trade-off).
  • Clients, handles, and calls are all Send + Sync + Clone. Creating a child handle or call clones ancestor inputs and the middleware list while sharing the transport and middleware instances via Arc, so build one client, clone it into tasks, and keep large payloads out of client/scope inputs (or wrap them in Arc/Bytes).

Inspect what would be sent, and write a first test

Every call builds its outgoing reqwest::Request with .request() before middleware, without sending anything and without needing a Tokio runtime (requiring a replayable body; use .into_request() for one-shot streams)—the fastest way to verify a description against provider docs. CHAPTER 02 · The languageDescribe an API

The entire description language is three node kinds (client, scope, endpoint), one cross-cutting declaration (part), and twelve statements. Here they are together on a slice of GitHub's API:

↓ Calling the generated handles

The tree and inheritance

Two inheritance rules govern every statement (design rationale):

  • Single-value statements (base, read, idle_timeout): nearest wins. Writing read Binary; on diff replaces the client's read Json; for that endpoint alone.
  • Keyed statements (query, headers, status): entries accumulate down the tree. Replacing an inherited key requires override; dropping one requires remove. Setting the same key twice without override is a compile error.

path appends segments down the tree joined by single slashes: issues.get sends to base + repos/{owner}/{name} + issues + {number}. An endpoint without its own path (like repo.get) inherits its parent's path as-is. On the wire, query pairs and headers go out in tree order (client → scopes → endpoint), with spread parts ordered before a node's own entries.

Inputs

WrittenGenerated caller interface & wire behavior

year: Option<u16>Required argument that may be None.

Every input type must be owned and Clone—write String, never &str (callers can still pass references). Types appearing in a pub client must be pub. Every declared input must be used somewhere in the description or compilation fails. Concord has no syntax for default values: defaults belong to the server, and unset optional inputs are simply omitted.

Scopes may take inputs too (repo(owner, name)). To reference an ancestor's input inside a child node, qualify it by owner: repo.owner or client.token.

Paths and bases

  • {x} fills one path segment (or part of one), percent-encoded: / becomes %2F. Empty, ., and .. values fail with a Build error before anything is sent.
  • {*x} spans multiple segments and preserves /—use it for file paths and S3 object keys.
  • base supports templates too ("https://{region}.shop.example/v2"); a host placeholder fills a label or part of one.
  • An optional input (x?: T) cannot fill a placeholder in base or path.

Query and header entries

Entry syntaxMeaning
state;Shorthand: key state with the value of this node's input state.
"ref" = reference;Explicit wire key bound to an input.
"accept" = "text/plain";Constant string.
"authorization" = "Bearer {token}";Template. Omitted entirely while any referenced optional input is unset.
"labels" = labels.as_ref().map(|all| all.join(","));Arbitrary Rust expression. Returning None omits the entry.
override "accept" = …;Replaces a key inherited from an ancestor.
remove "authorization";Drops a key inherited from an ancestor.

Values serialize through serde, so enums emit their serde names. Query spaces always encode as %20, never +. In headers, the shorthand form is rejected when the identifier contains _: write "user-agent" = user_agent;. The host header cannot be set manually because it derives from base. Note that renaming a required input alone preserves positional callers, except when that input is used in a shorthand entry (state;), where renaming also changes the wire key.

Inside right-hand expressions, inputs are borrowed references: &T for title: T, &Option<T> for year?: T—hence labels.as_ref(). Because inputs act as local bindings inside a block, an input shadows any function or item of the same name in your module; qualify shadowed items with a path.

Parts: sharing rules across branches

A part bundles inputs with the statements that use them—pagination parameters, shared filters, host families, or a second credential (why parts exist beside scopes). Declare parts inside the client after the client's statements, and spread them into scopes or endpoints with ..name. A part accepts any statement except path, problem, and middleware, and cannot declare child endpoints or spread another part (remember that changing a scope's spread, such as ..platform to ..region, also changes its callers' public parameter type).

A part's statements belong directly to the node that spreads it: a node cannot re-declare a key already set by one of its parts, and two parts spread together cannot declare the same input name. One case merges automatically: when both a part and an endpoint declare entry-block bodies with the same writer (for example body json { … } in both, or body bracket_form { … } in both), Concord merges their entries into one request body.

Multiple hosts and caller-supplied bases

Any scope or endpoint may switch base (as release.upload switches to https://uploads.github.com). One safety rule applies at compile time (why): an inherited entry holding a Secret cannot silently cross a second base. Under the new base, either explicitly re-declare it with override or drop it with remove. (Root secrets still bind to the first base on each branch, so the description's author still chooses the initial host(s).)

For self-hosted APIs where the caller supplies the server address, take a concord::Base input (a validated scheme, host, optional port, and optional path prefix—rejecting userinfo, queries, and fragments). Separately, callers can redirect any entire client with with_base(…) (for staging or local test servers)—note that with_base redirects the whole client and sends every header, secrets included, to the caller's chosen base:

↓ Redirecting an entire client with with_base

Reserved names, HTTP methods, and attributes

Node and input names are lower snake_case. Because children and optional inputs become Rust methods, they cannot collide with methods their receiver already defines: clone, anything starting with with_, new, and call on the client, or any of the call methods on an endpoint. Inputs cannot be named client, match an enclosing scope's name, or be Rust keywords (write "type" = kind; or "ref" = reference;). Concord's own statement keywords (query, path, body, status) are free to use as input names.

Built-in HTTP methods are GET, HEAD, POST, PUT, PATCH, DELETE, and OPTIONS; write METHOD "PURGE" for any custom verb. Doc comments (///) work on nodes and inputs; #[cfg(…)] works on any node; #[deprecated] and #[doc(hidden)] work on scopes and endpoints.

CHAPTER 03 · Request bodiesRequest bodies

body accepts two forms:

  • Expression form: any Rust expression returning a concord::Body, &Body, Option<Body> (where None sends no body or content-type), or a Result of those (Body is a struct and IntoBody is sealed; built-in writers like json(x) return Result<Body, WriteError>). An Err aborts with a Build error before anything is sent.
  • Entry-block form: body json { title; done; }, body form { … }, or body bracket_form { … }. Entries follow the same syntax as query, omit unset optional inputs, and merge across a part and an endpoint using the same writer.

Every Body carries its own content-type; an explicit content-type in headers overrides it. Remember that inputs inside a block are references (&Bytes), so cloning cheap handles like Bytes or Body is normal. A Secret cannot be placed inside a serde struct passed to json(…)—secrets enter bodies strictly through entry blocks such as body form { user; password; }.

NDJSON (json_lines) and gzip-compressed bodies

json_lines(records, max_bytes) writes one compact JSON value followed by \n for each item in an iterator, bounding total encoded bytes (including newlines) and guarding nesting depth before sending. Wrap its result in gzip(…) (with the gzip-body feature) and set "content-encoding" = "gzip" when sending compressed batches. With the multipart feature, multipart_related and multipart_mixed frame ordered (HeaderMap, Body) parts with deterministic boundaries (concord-0000…) chosen to avoid colliding with buffered part bytes and headers. CHAPTER 04 · Responses & streamsResponses and streams

One rule covers every response (design rationale): a 2xx is decoded by the nearest reader into the return type after ->, and every other status becomes a Refused error. A status block declares every exception:

Status armBehavior
404 => NoneExact status. Body is not read; returns the expression directly.
2xx => trueStatus class (1xx–5xx). An exact code always beats a class.
409 { body } => Err(body)body is decoded by the nearest reader; Rust infers its type from the arm.
2xx { body, headers } => …Also binds headers (&Headers) and/or status (StatusCode).
override 404 => …, remove 404Replaces or removes an arm inherited from an ancestor.

After ->, Concord recognizes literal Option<T> and Result<T, E> (and their std/core paths): an unmatched 2xx decodes as T and wraps it in Some or Ok, while your arms supply None or Err. Inside an arm, ? short-circuits the call: headers.require("location")? turns a missing header into a Mismatch, and returning an Err(problem) of the client's problem type turns it into a Refused error carrying that problem. Arms are synchronous; move non-trivial logic into a helper returning Result<T, concord::Fail<P>>.

Spell Option and Result literally after ->

Do not hide Option<T> or Result<T, E> behind a type alias after ->. Because the macro checks token spelling rather than resolved types, an alias like type MaybeNumber = Option<u32> or type DomainNumber = Result<u32, String> compiles as an opaque Deserialize type and silently changes runtime decoding: 200 null fails with Mismatch under Option<u32> yet decodes as Ok(None) behind an alias, and 200 7 succeeds as Ok(Ok(7)) under Result<u32, String> yet fails with Mismatch behind an alias (design note).

Match 2xx (not just 201) when building a custom wrapper type like Created below—otherwise another 2xx status would fall through to the default rule and fail trying to decode Created directly. An endpoint with no -> returns () and skips reading the body (so 204 needs no arm); under an arrow with read Json, add 204 => None for empty responses. A HEAD endpoint with a return type has no body and must include a 2xx arm.

Byte streams, SSE, and mapped JsonLines

With read Stream;, read Sse::new(n);, or read JsonLines::new(n);, the call returns as soon as the response head arrives. Both the idle timeout (between chunks) and any call timeout (across the entire transfer) keep running while you pull records, so give long downloads or watch streams a generous call timeout or none. Escape hatch: send_raw() and read_response()

When you need raw access to the reqwest::Response before decoding—for example to inspect a redirect location, record custom headers before reading, or reuse a response you obtained outside Concord—combine send_raw() with read_response():

Know the exact contract of both methods: send_raw() runs middleware and passes statuses >= 400 through the retry policy, but skips status arms and leaves the body unread (note also that reqwest::Response's {:?} prints its URL). read_response(response) runs the endpoint's exact reader and status arms on any reqwest::Response without starting retries, timeouts, or pagination—so any error it returns reports tries() == 0.

CHAPTER 05 · Errors & envelopesErrors and envelopes

Declare problem Type; on the client to decode refusal bodies automatically (or problem S3Problem read Xml; when the error body uses another reader). Generated shop::Error is a type alias for concord::Error<Problem> (so two clients sharing the same problem type share the same Rust error type). Even when problem() is None (absent, undecodable, or over the 64 KiB cap), every Refused error still retains its status, headers, and up to 64 KiB of raw body:

Safe logging vs. error.details()

Secret boundaries to keep in mind

{e} and {e:?} never print URLs, headers, bodies, or secrets, making them safe for default logs. However, e.details() intentionally prints detailed retained evidence—headers plus the decoded problem (or, when no problem was decoded, the retained raw body bytes), plus reader diagnostics and error sources—e.source() preserves whatever a custom transport, middleware, or body writer put there, and a raw reqwest::Response from send_raw() prints its URL in {:?} (full security boundary notes).

Every pager returns a Paging value you can refine inline:

  • .has_more(|page| page.has_more) — asserts server-declared continuation; if has_more is true yet no next request can be built, ends with a Mismatch instead of stopping silently.
  • .stop_on_short_page(count, default) and .only_when_set(input) — custom stopping conditions (use stop_on_short_page when the server has a documented default size like Riot's 20 and guarantees full pages until the last).
  • .or_when_set(input, other_pager) — switches pagination direction when an alternate cursor is set (for example Stripe's ending_before alongside starting_after).
  • .map_next(|call, page| …) — edits the next call before sending (for example Kubernetes clearing resource_version once a continue token is active).

Across every pager, keep four engine behaviors in mind: a repeatable next request identical to the immediately previous request stops with a Mismatch (catching immediate self-repeats, not multi-step A → B → A cursor cycles); a next URL on another origin stops with a Build error without sending; a received page is always yielded before any error decided about continuing; and every page runs through retries, middleware, signing, and with_timeout as its own call—meaning with_timeout bounds each page individually, not the whole walk (wrap the pagination loop in tokio::time::timeout for a whole-walk deadline).

Expiring tokens: auth::Renewed

With the auth feature, Renewed caches an expiring access token, injects Authorization: Bearer …, coalesces concurrent renewals, and refreshes early. Describe the identity server as a separate client without the middleware so fetching a token never recurses. Renewed never resends requests itself: on a 401 it drops the rejected token, and pairing .with_retry(Retry::standard().when(after_401)) lets the engine issue one retry with a freshly fetched token (normal repeatability rules still protect unmarked POSTs):

Single-use rotating refresh tokens: auth::Rotating

When a provider invalidates each refresh token upon exchange, losing a newly returned refresh token locks the account out. With the rotating feature (which includes auth), Rotating::new(&base, store, exchange_fn) pairs a middleware handle with a driver future that your application spawns and drains (Concord starts no background tasks). Before calling your exchange closure, the driver writes Stored::Refreshing through your CredentialStore; after the exchange returns a new TokenPair, it persists Stored::Ready(pair). If persistence fails, the driver returns Err(RotationError::Unsaved { pair, .. }) so your application can recover the new token pair instead of losing it:

Keep three operational rules in mind for production CredentialStore implementations: configure the exchange client with Retry::none() (and default concord::Http) so a single-use refresh token is never sent twice; ensure save flushes durably (e.g. atomic temp-file write + sync_all + rename, or a database transaction) before returning; and note that Rotating uses error.request_not_sent() to decide whether a failed refresh exchange can reuse the same refresh token—under default Http, that evidence depends on internal error wrapping in reqwest, hyper-util, hyper, and h2 (with an untested pooled-connection hand-off race noted in its docs), so keep your refresh exchange tested across dependency upgrades. Drop every client clone during shutdown and await the driver handle so in-flight exchanges finish cleanly.

With the sign feature, SigV4 signs requests with AWS Signature Version 4. For a provider's custom HMAC or signature scheme, write a custom middleware—concord::sign::body_bytes and concord::sign::check_origin are public helpers built for it.

CHAPTER 08 · Retries & clocksRetries and timeouts

Facts about the API (idempotent, idle_timeout) live in the description; caller choices (whether to retry, total deadline) live on the client or on individual calls (why). Ship API-specific retry knowledge as a plain function beside the description:

↓ Applying policies on the client and overriding for a single call

When a request is retried

Nothing is retried until with_retry sets a policy. Once set, an attempt repeats only when all three checks pass:

  1. Repeatable body: buffered bytes or Body::repeatable, never a one-shot Body::stream.
  2. Repeatable operation: method is GET, HEAD, OPTIONS, PUT, or DELETE; or the endpoint declares idempotent; (any bool expression over inputs—idempotent false; revokes permission on a non-idempotent PUT); or the response status is listed in not_applied_on.
  3. Retryable failure: under Retry::standard(), a connect error, timeout, interrupted body, or status 408, 429, 502, 503, or 504.
Method on RetryEffect

Retry::none()1 attempt, empty table. Pair with .tries(n).when(…) for strictly custom rules.
.tries(n)Maximum attempts including the initial try.

Closures receive tried with .status(), .headers(), .problem(), .class(), and .number(). Always start from the client's alias (orders::Retry::standard(), not bare Retry::standard()) when writing closures that inspect tried.problem() so Rust knows the problem type. Each wait uses the maximum of your when delay, Retry-After, and full-jitter exponential backoff (1s, 2s, 4s, … up to 60s). If a wait exceeds max_retry_after or would run past the call's remaining with_timeout, the engine returns the failure immediately (preserving error.retry_after()) rather than sleeping to fail. Setting with_retry on a call replaces the client's policy whole; extend the helper with with_retry(retry().when(mine)) to layer rules.

CHAPTER 09 · Rate limitsRate limits

With the limit feature, concord::limit::Limit is a middleware that paces outgoing requests without retrying or altering responses:

  • Limit::new() alone coordinates Retry-After pauses after a 429 across concurrent callers.
  • .max_in_flight(n) bounds concurrent requests; each permit stays held until the response body finishes reading (or the stream is dropped).
  • Each Bucket maps a call to an optional key and enforces either known windows (Window::rolling, Window::fixed) or server-reported headers (counts, remaining, remaining_rfc3339, or a custom parser).
  • Requests wait up to 60 seconds for budget room by default before failing; adjust with .max_hold(d). Any call with_timeout applies independently.

Limit and Retry complement each other: the limit holds requests back before sending, while retries decide whether a refused attempt goes again (re-acquiring permits on each try). Clones of a Limit—and clones of a client using it—share the same in-process budget state.

CHAPTER 10 · Transport & callsTransport, Tower, and call methods

concord::Http and custom reqwest::Client

By default every client sends through concord::Http, which configures reqwest for API clients: redirects off (3xx surfaces as a response), internal protocol retries off, response decompression off until enabled, and a 30-second connect timeout. Customize TLS roots, proxies, or connect timeouts with Http::with, or supply your own reqwest::Client directly:

When supplying a raw reqwest::Client, remember its defaults follow up to 10 redirects and resend on HTTP/2 protocol resets below Concord's attempt counter—disable both unless you want them. To enable gzip/deflate response decompression, turn on Concord's gzip or deflate Cargo feature and call builder.gzip(true) inside Http::with; reader byte limits then measure the decoded bytes. Note also that Http's request_not_sent() classification inspects internal error wrapping in reqwest, hyper-util, hyper, and h2 (and its docs note an untested pooled-connection hand-off race), which matters if you rely on request_not_sent() or auth::Rotating.

Using a tower service as a transport

With the tower feature, concord::tower::Tower::new(service) wraps any tower_service::Service<reqwest::Request, Response = reqwest::Response> (including reqwest::Client wrapped in Tower layers) as a Concord Transport. The adapter locks the service only across poll_ready and call, then awaits the response future outside the lock—so stateful, non-Clone, non-Sync layers work directly:

Two practical notes: Tower classifies returned TransportErrors as-is and reqwest::Errors through From<reqwest::Error>, while any other layer error becomes Class::Other (so behind a Tower timeout layer, map its error to TransportError::timeout() so error.is_timeout() stays true). Note also that tower-http layers operate on http::Request, not reqwest::Request, so they do not sit directly inside Tower.

Part IV · Scale, extensions & reference

CHAPTER 12 · Real APIsDescribing a large real API

A sixty-endpoint description uses the exact same twelve statements as a four-endpoint one. What changes is the order of work. Here is the order proven across the ten real APIs in the repository's tests/real-apis:

  1. Start with client-wide truths: default credential, default read, problem type, and any shared middleware. Read the provider's errors page before writing a single endpoint.
  2. Extract cross-cutting parts next: multiple host families (part region / part platform), secondary auth (part player), pagination blocks, shared query filters, or idempotency keys on every write.
  3. Mirror the provider's reference in scopes: one scope per section, in the same order, so reviewing against the docs stays a straight line-by-line scan.
  4. Use newtypes for distinct IDs: because required inputs are positional and Arg never coerces &str into your types, Puuid and MatchId cannot be swapped at compile time.
  5. Decide non-2xx meanings endpoint by endpoint: a lookup's 404 is usually Option::None; a list's 404 usually signals a broken route and stays an error.
  6. State repeatability honestly: idempotent; on a keyed POST, idempotent false; on an appending PUT or stateful poll.
  7. Keep everything else in ordinary Rust beside the macro: serde types, pub fn retry(), pub fn quota(), and response helpers.

Practical habits at scale

  • Verify every endpoint with .request() against the provider's curl example as you add it.
  • Record uncertainties directly in /// doc comments so callers see them in rustdoc.
  • Put #[deprecated(note = "…")] on retiring endpoints to warn callers at compile time.
  • Remember the scope tree is public API: moving an endpoint to a different scope is a breaking change unless you wrap the client behind your own facade. Because Concord is at 5.0.0-rc.1 with breaking changes already queued in Unreleased, pin a git revision in Cargo.toml if stability matters.
  • Author-measured synthetic first-check compile times scale with endpoint count (full benchmark notes): < 1 s for 62 endpoints (Riot), ~8 s and < 1 GiB at 1,000 synthetic endpoints, ~30 s and 2.5 GiB at 3,000 (with dependencies built; incremental leaf vs. part edits are not separately measured).
  • Multiple concord::api! clients coexist cleanly in one crate (e.g. an identity token client beside the main API client, or an unauthenticated upload-host client).

CHAPTER 13 · Custom extensionsExtend Concord

The macro knows no wire format, authentication protocol, or pagination scheme (architecture diagram). Every built-in reader, writer, pager, and middleware uses the same five public extension points—three traits (Reader, Middleware, Transport), the Pager/Paging family, and plain body-writer functions (IntoBody is sealed)—shown here on one Ledger client:

A custom Reader

  • Always bound whole-body reads with body.bytes(limit).await? (or hand over chunks with body.stream()).
  • Propagate body failures with ?, and report malformed payloads with ReadError::not_the_type(bytes).
  • Put decoder error text in .with_details(…)—never in the summary message—so potentially echoed response fragments appear only in error.details().
  • Implement Reader<T> for specific types or generically (for example impl<T: DeserializeOwned> Reader<T> for Xml).

A custom body writer

A body writer is simply a Rust function returning Body or Result<Body, E> (Body is a struct; IntoBody is sealed). Take borrowed arguments (&[…]) because inputs inside a description block are references. Returning Err aborts with a Build error whose source() is your error.

A custom pager

For a one-off endpoint, pass a closure directly: paginate |call, answer| …;. To build a reusable pager across endpoints, accept a Call and one or more Slot parameters:

  • input.get(&call) reads a slot; input.set(call, value) returns the updated call.
  • Return Err(concord::mismatch("…")) when a response cannot be trusted; the caller receives the page first, then the error on the following try_next().
  • Paging::from_fn gives your pager all standard modifiers (.has_more, .map_next, .or_when_set).
  • Avoid naming the pager function identically to an endpoint input—inside the block, the input shadows it.

A custom Middleware

  • Attach permanently in the description (middleware Traced::default();, built in new from required client inputs only) or per client via with_middleware(…). Caller middleware runs first, then description middleware in declaration order.
  • handle runs on every attempt and every page; info.endpoint() gives the dotted endpoint name and info.number() the 1-based attempt number.
  • To block a request before sending (0 forwards), return Err(TransportError::blocked()).
  • Avoid resending from inside middleware: although next can technically be called more than once within one attempt, resending there bypasses the engine's attempt counter and repeatability checks. Use a Retry::when rule instead.
  • Keep URLs and secrets out of any error attached via with_source.

A custom Transport

Mark a failure with .not_sent() only when you are certain zero bytes left the process—callers and auth::Rotating rely on it to know whether a single-use credential was consumed.

CHAPTER 14 · TroubleshootingWhen it does not compile

Errors come from two stages. First, the macro validates the description and reports all structural issues in one pass with concrete help: lines. Once the macro succeeds, rustc type-checks the generated Rust and your expressions.

Tip on unused-import warnings

When the macro reports an error it emits no client code, so rustc often adds a secondary warning that Json or another import is unused. Fix the macro error first and that warning disappears.

Misspelled placeholder or unused input

Fix Match the placeholder spelling ({puuid}) to the declared input.
Fix Write "user-agent" = user_agent;, and either place limit in query { author; limit; } or remove it.

Referencing a client or scope input from a child

Fix Qualify ancestor inputs with their owner and an explicit key: query { "id" = shelf.id; }.
Fix Shorthand works only for the current node's own inputs; write "client_id" = client.client_id;.
Fix Ignore rustc's import suggestion; write "of" = shelf.id;.

Borrowed or optional input in the wrong place

Fix Declare owned isbn: String; callers can still pass &str.
Fix Path and base placeholders must be required: declare isbn: String without ?.

Missing reader, or return type not Deserialize

Fix Add read Json; (or another reader) on the client, scope, or endpoint.
Fix Add #[derive(serde::Deserialize)] to Book, or declare a reader that produces Book.

Accidental override or secret crossing a new base

Fix Write headers { override "accept" = "application/vnd.github.diff"; }.
Fix Under the new base, write headers { override "authorization" = "Bearer {client.token}"; } to send it there intentionally, or headers { remove "authorization"; } to omit it.

HEAD with a return type, awaiting a paged call, or passing text for a newtype

Fix Add a 2xx arm that does not bind body: status { 2xx => true, 404 => false }.
Fix Ignore rustc's suggestion to drop .await; use .pages().items(), .pages(), or .send().await for one page.
Fix Construct your newtype explicitly: riot.account(Puuid("…".into())).await.

Shadowed function name, or retry closure type inference

Fix Rename the pager function or call it by path: paginate crate::before(before);.
Fix Start from the client's alias: orders::Retry::standard().unless(…).
