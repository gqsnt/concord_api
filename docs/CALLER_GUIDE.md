# Using a generated client

This guide is for code that calls a client generated by `concord::api!`. Every Rust block is an
excerpt of [`examples/quickstart/tests/caller_guide.rs`](../examples/quickstart/tests/caller_guide.rs),
where each section is one test, run against a local stand-in server by
`cargo test -p concord-example-quickstart --test caller_guide`.

## The declaration used here

Excerpt of [`examples/quickstart/tests/caller_guide.rs`](../examples/quickstart/tests/caller_guide.rs):

```rust
concord::api! {
    /// A product catalog.
    pub client Catalog(
        /// The API key.
        #[sensitive] header("x-api-key") key: String,
        /// The preferred language of product names.
        header("accept-language") lang?: String = "en",
    ) {
        base "https://catalog.example.com/v1";
        request Json;
        response Json;

        /// One shop.
        scope shop(shop: String) {
            path "shops/{shop}";

            /// Lists products.
            GET products(
                query category?: String,
                query limit: u32 = 20,
                language?: Option<String>,
            ) -> Vec<Product> {
                path "products";
                headers { override "accept-language" = each language else inherit; }
            }

            /// One product.
            GET product(id: u64) -> Product { path "products/{id}"; }

            /// Renames a product.
            PUT rename(id: u64, body change: Rename) -> Product {
                path "products/{id}";
            }

            /// Deletes a product.
            DELETE delete(id: u64) { path "products/{id}"; }
        }
    }
}
```

It generates `Catalog`, `CatalogConfig`, the scope `CatalogShop` and one request type per
endpoint (`CatalogShopProducts`, `CatalogShopProduct`, `CatalogShopRename`, `CatalogShopDelete`).
The signatures, as rustdoc shows them (the test `the_documented_signatures` checks them):

```text
Catalog::new(http: reqwest::Client, config: CatalogConfig) -> Catalog
Catalog::with_base_url(self, url: impl AsRef<str>) -> Result<Catalog, concord::Error>
Catalog::set_key(self, value: impl IntoValue<String>) -> Catalog
Catalog::set_lang(self, value: impl IntoValue<String>) -> Catalog
Catalog::maybe_lang(self, value: Option<String>) -> Catalog
Catalog::shop(&self, shop: impl IntoValue<String>) -> CatalogShop

CatalogShop::set_shop(self, value: impl IntoValue<String>) -> CatalogShop
CatalogShop::products(&self) -> CatalogShopProducts
CatalogShop::product(&self, id: impl IntoValue<u64>) -> CatalogShopProduct
CatalogShop::rename(&self, id: impl IntoValue<u64>, change: impl IntoValue<Rename>) -> CatalogShopRename
CatalogShop::delete(&self, id: impl IntoValue<u64>) -> CatalogShopDelete

CatalogShopProducts::set_category(self, value: impl IntoValue<String>) -> Self
CatalogShopProducts::maybe_category(self, value: Option<String>) -> Self
CatalogShopProducts::set_limit(self, value: impl IntoValue<u32>) -> Self
CatalogShopProducts::set_language(self, value: impl IntoValue<Option<String>>) -> Self
CatalogShopProducts::maybe_language(self, value: Option<Option<String>>) -> Self
CatalogShopProducts::prepare(self) -> Result<concord::Prepared<Vec<Product>>, concord::Error>
async CatalogShopProducts::send(self) -> Result<Vec<Product>, concord::Error>
CatalogShopRename::set_change(self, value: impl IntoValue<Rename>) -> Self
async CatalogShopDelete::send(self) -> Result<(), concord::Error>
```

`impl IntoValue<T>` accepts exactly `T`, or `&str`/`&String` when `T` is `String`. Nothing else
converts: no `Into`, no numeric widening, no wrapping into `Option`; construct newtypes and
`Option`s yourself.

## 1. Creating a client

`Client::new` takes your `reqwest::Client` and, when the client has required values, the
generated `{Client}Config` struct. Config fields take exactly the declared type (`.into()` for a
string literal). `with_base_url` replaces the declared base and returns an error for anything
that is not an `http`/`https` URL with a host (no user information, query or fragment).

Excerpt of [`examples/quickstart/tests/caller_guide.rs`](../examples/quickstart/tests/caller_guide.rs):

```rust
// Transport settings live on your reqwest::Client.
let http = reqwest::Client::builder()
    .timeout(Duration::from_secs(30))
    .build()?;
let api = Catalog::new(http, CatalogConfig { key: "k1".into() });

// The same declaration against another deployment (staging, a local test server):
let staging = api
    .clone()
    .with_base_url("https://staging.catalog.example.com/v1")?;
let request = staging.shop("acme").product(7).prepare()?;
assert_eq!(
    request.request().url().as_str(),
    "https://staging.catalog.example.com/v1/shops/acme/products/7"
);

// Concord's Debug output withholds sensitive values.
assert_eq!(
    format!("{api:?}"),
    r#"Catalog { base: "https://catalog.example.com/v1", key: <redacted>, lang: Some("en") }"#
);
```

If the declaration uses `subdomain`, the base must stay a domain name: to reach a local server,
map the domain with `reqwest::ClientBuilder::resolve` (see the
[quick start](QUICKSTART.md#6-when-the-api-uses-subdomains)).

## 2. Navigating

- A scope method (`api.shop("acme")`) borrows its parent and returns a new handle that holds a
  snapshot of it (a clone of the parent handle plus the scope's own values, in one `Arc`).
- An endpoint method (`shop.products()`) returns a plain request struct holding a clone of its
  parent handle (a reference-count increment) and its own values. Nothing is sent. It is
  `#[must_use]`: call `send()` or `prepare()`.
- Required scope and endpoint values are positional arguments in declaration order; a required
  body takes its place among them (`rename(id, change)`).

## 3. Handles are snapshots

Client and scope handles are immutable snapshots: a setter consumes the handle and returns a new
one, and everything created from the old handle keeps what it captured. Cloning a handle is a
reference-count increment, so build the client once and clone it into tasks.

Excerpt of [`examples/quickstart/tests/caller_guide.rs`](../examples/quickstart/tests/caller_guide.rs):

```rust
/// The `accept-language` header a request would send.
fn language_of(request: CatalogShopProducts) -> Result<Option<String>, concord::Error> {
    let prepared = request.prepare()?;
    let header = prepared.request().headers().get("accept-language");
    Ok(header.map(|value| value.to_str().unwrap().to_owned()))
}
```

Excerpt of [`examples/quickstart/tests/caller_guide.rs`](../examples/quickstart/tests/caller_guide.rs):

```rust
let api = Catalog::new(reqwest::Client::new(), CatalogConfig { key: "k1".into() });
let acme = api.shop("acme"); // borrows `api`, keeps a snapshot of it
let request = acme.products(); // a request value; nothing is sent yet

let german = api.clone().set_lang("de"); // a new handle; `api` is unchanged
assert_eq!(
    language_of(german.shop("acme").products())?.as_deref(),
    Some("de")
);

// Handles and requests created earlier keep the values they captured.
assert_eq!(language_of(request)?.as_deref(), Some("en"));
assert_eq!(language_of(acme.products())?.as_deref(), Some("en"));
```

The snapshot is **structural**: it fixes which value each handle holds, not what is inside it. A
value with interior mutability (an `Arc<Mutex<_>>`, an atomic, a custom `Display` reading shared
state) is shared between handles, and every value is formatted when the request is prepared.

Handles and requests hold your `reqwest::Client` and the values, so they are `Send + Sync` when
the value types are; the test checks it for this declaration. Excerpt of [`examples/quickstart/tests/caller_guide.rs`](../examples/quickstart/tests/caller_guide.rs):

```rust
fn shareable<T: Send + Sync + Clone>() {}
shareable::<Catalog>();
shareable::<CatalogShop>();
shareable::<CatalogShopRename>();
```

## 4. Setting and omitting values

| Call | Effect |
|---|---|
| `set_x(v)` | the value is `v` (present) |
| `maybe_x(Some(v))` | same as `set_x(v)` |
| `maybe_x(None)` | absent — even for `x?: T = expr`: the initializer is not brought back |
| (no call) | the declared starting state: required values as supplied, `= expr` as evaluated, `?` absent |

`maybe_x` exists only for optional values; it takes exactly `Option<T>`, which is what you have
when passing an existing option along (a pagination cursor, an optional filter). There is no
`reset`: keep the original handle or call the endpoint again.

A value declared `x?: Option<U>` has three states — absent (`maybe_x(None)`), present `None`
(`set_x(None)`) and present `Some(u)` — which the declaration can map to "inherit", "omit" and
"replace" (the [author guide](AUTHOR_GUIDE.md#46-letting-the-caller-choose-inherit-omit-or-replace)
explains the declaration side).

Excerpt of [`examples/quickstart/tests/caller_guide.rs`](../examples/quickstart/tests/caller_guide.rs):

```rust
let api = Catalog::new(reqwest::Client::new(), CatalogConfig { key: "k1".into() });
let acme = api.shop("acme");

let lamps = acme.products().set_category("lamps").set_limit(50);
assert_eq!(
    query_of(lamps.clone())?.as_deref(),
    Some("category=lamps&limit=50")
);

// `maybe_x` sets exactly the given presence: pass an `Option` you already have.
let category: Option<String> = None;
let all = lamps.maybe_category(category);
assert_eq!(query_of(all)?.as_deref(), Some("limit=50"));

// `language?: Option<String>`: inherit, omit or replace, chosen per call.
let inherit = acme.products();
let omit = acme.products().set_language(None);
let replace = acme.products().set_language(Some("fr".to_owned()));
assert_eq!(language_of(inherit)?.as_deref(), Some("en"));
assert_eq!(language_of(omit)?, None);
assert_eq!(language_of(replace)?.as_deref(), Some("fr"));

// On an initialized optional value, `maybe_x(None)` means absent, not "the initial value".
let silent = api.clone().maybe_lang(None);
assert_eq!(language_of(silent.shop("acme").products())?, None);
```

(`query_of` returns the query string of the prepared request, like `language_of` above. In the
next sections, `local(&server)` creates the same client with `with_base_url` pointing at the
local stand-in server.)

## 5. Preparing and sending

- `prepare()` builds the native `reqwest::Request` with no I/O and returns
  `Result<Prepared<T>, Error>`, `T` being the declared output (`()` without `->`). A value that
  cannot form a valid request (an empty path segment, an invalid header value or host label) is an
  error of kind `Build`. `Prepared`'s `Debug` is redacted; `request()` gives read-only access to
  the native request, whose own `Debug` prints the full URL (sensitive query values and path
  segments included; flagged header values show as `Sensitive`).
- `send()` is `prepare()?.send()`: one `reqwest::Client::execute`, a 2xx check, the format's
  check of the response head, then reading and decoding the body with the endpoint's format (the
  navigation method's documentation names it, with the body's `Content-Type`). An endpoint without
  typed output accepts any 2xx and drains the body. No retry, no extra request.
- The request carries the format's `Accept` suggestion when the endpoint has a typed output and
  you declared no `accept` (`Json` suggests `application/json`); `prepared.request().headers()`
  shows what will be sent. A client default `Accept` of your `reqwest::Client` only goes out when
  Concord sends none ([author guide, 5.8](AUTHOR_GUIDE.md#58-what-goes-on-the-wire-accept-and-content-type)).
- `send_raw()` on a prepared request returns the native response, status unchecked, body unread.

Excerpt of [`examples/quickstart/tests/caller_guide.rs`](../examples/quickstart/tests/caller_guide.rs):

```rust
let server =
    LocalServer::start(|_| Response::json(200, json!([{ "id": 7, "name": "Lamp" }]))).await?;
let api = local(&server)?;
let request = api.shop("acme").products().set_category("lamps");

// prepare(): builds the native request; no I/O.
let prepared = request.clone().prepare()?;
assert_eq!(prepared.request().method(), reqwest::Method::GET);
let shown = format!("{prepared:?}"); // redacted: `x-api-key: <redacted>`
assert!(shown.contains("x-api-key: <redacted>") && !shown.contains("k1"));

// send(): prepare, execute once, require a 2xx status, decode as declared.
let products: Vec<Product> = request.send().await?;
assert_eq!(products[0].name, "Lamp");

// An endpoint without `->` returns `()`; any 2xx body is read and dropped.
api.shop("acme").delete(7).send().await?;

// send_raw(): the native response, status unchecked and body unread.
let response = api.shop("acme").product(7).prepare()?.send_raw().await?;
assert_eq!(response.status(), reqwest::StatusCode::OK);
```

A request is `Clone` when its values and body are, so it can be sent again. Whether re-sending is
safe is your decision, not something `Clone` promises; see the
[retry recipe](RECIPES.md#application-policies) for the assumptions to state.

## 6. Errors

Every call returns `Result<_, concord::Error>`.

| `error.kind()` | Meaning | Useful accessors |
|---|---|---|
| `ErrorKind::Build` | the request could not be built from the values, or its body could not be encoded; nothing was sent | `codec_error()` (an encoding failure) |
| `ErrorKind::Transport` | reqwest failed to send or to read the response (connect, timeout, ...) | `transport()` |
| `ErrorKind::Status` | the server answered with a non-2xx status | `status()`, `response()`, `into_response()` |
| `ErrorKind::Metadata` | the status was 2xx, but the endpoint's format refused the response head (for `Json`, its `Content-Type`) before the body was read | `response()`, `into_response()`, `codec_error()` |
| `ErrorKind::Decode` | a 2xx body could not be decoded with the endpoint's format | `codec_error()` |

`ErrorKind` is `#[non_exhaustive]`: keep a `_` arm when matching it. `error.endpoint()` names the
endpoint (`Catalog.shop.product`). `Display` is `METHOD Client.scope.endpoint: <message>` and only
contains static text — the endpoint, the failing placement's template, a header name, the status
code — never a request value, URL, header value or body.

A status that means "not found" for your application is an ordinary `match`. Excerpt of
[`examples/quickstart/tests/caller_guide.rs`](../examples/quickstart/tests/caller_guide.rs):

```rust
/// `Ok(None)` when the product does not exist; every other failure is an error.
async fn find_product(shop: &CatalogShop, id: u64) -> Result<Option<Product>, concord::Error> {
    match shop.product(id).send().await {
        Ok(product) => Ok(Some(product)),
        Err(error) if error.status() == Some(reqwest::StatusCode::NOT_FOUND) => Ok(None),
        Err(error) => Err(error),
    }
}
```

A status error keeps the **unread** response. `response()` borrows it, so its headers
(`Retry-After`, a request id) can be read while the error is kept, for example in a predicate
`Fn(&concord::Error) -> bool`. `into_response()` returns it, and returns any other error unchanged
as `Err`, so `?` propagates those. It consumes the error: read `status()` and `endpoint()` first if
you need them. Reading the body is reqwest's (`response.bytes()` fails with a
`reqwest::Error`, which does not convert into `concord::Error`). Decode the API's error document
with a format's `decode_body`, which decodes bytes and checks no response head: the endpoint's
format was never consulted for a non-2xx response. Excerpt of
[`examples/quickstart/tests/caller_guide.rs`](../examples/quickstart/tests/caller_guide.rs):

```rust
let server = LocalServer::start(|_| Response::problem(404, "no such product")).await?;
let api = local(&server)?;
assert!(find_product(&api.shop("acme"), 99).await?.is_none());

let error = api.shop("acme").product(99).send().await.unwrap_err();
assert_eq!(error.kind(), ErrorKind::Status);
assert_eq!(error.status(), Some(reqwest::StatusCode::NOT_FOUND));
assert_eq!(error.endpoint(), Some("Catalog.shop.product"));
assert_eq!(
    error.to_string(),
    "GET Catalog.shop.product: HTTP status 404 Not Found"
);

// Borrowed: headers can be read while the error is kept.
let response = error.response().expect("a status error");
assert_eq!(
    response.headers()["content-type"],
    "application/problem+json"
);

// The API's error document: the response of a status error is unread.
let response = error.into_response()?; // any other kind of error is returned as Err
let problem = <Json as Decode<Problem>>::decode_body((), response.bytes().await?)?;
assert_eq!(problem.title, "no such product");

// A value that cannot form a request is a build error; nothing is sent.
let error = api.shop("..").product(1).prepare().unwrap_err();
assert_eq!(error.kind(), ErrorKind::Build);
assert_eq!(
    error.to_string(),
    "GET Catalog.shop.product: request not built: path segment `{shop}` is empty, `.` or `..`"
);
```

The error body is read into memory; against an untrusted server, read it with `chunk()` up to
your own limit (see the [error-document recipe](RECIPES.md#error-documents)).

### A 2xx response the format refuses

A 2xx status is not always enough: before it reads the body, Concord lets the endpoint's format
check the response head. `Json` requires exactly one `Content-Type`, `application/json` or
`application/*+json`; a response labelled `text/html`, or not labelled, is not parsed. That is an
`ErrorKind::Metadata` error. Like a status error it keeps the response **unread**, so you can see
what the server sent. `status()` is `Status`-only and is `None` here; `response()` and
`into_response()` cover both kinds. `Display` shows the endpoint, a static label and never a
header value or the body. Excerpt of
[`crates/concord/tests/bodies.rs`](../crates/concord/tests/bodies.rs), a `Json` endpoint answered
with `text/html`:

```rust
let (_server, api) = shop(html()).await;
let error = api.item(2).send().await.unwrap_err();
assert_eq!(error.kind(), ErrorKind::Metadata);
assert_eq!(error.status(), None);
assert_eq!(
    error.to_string(),
    "GET Shop.item: response metadata not accepted: the response Content-Type is not application/json or an application/*+json type"
);
assert_eq!(
    error.response().unwrap().headers()["content-type"],
    "text/html"
);
let body = error.into_response().unwrap().bytes().await.unwrap();
assert_eq!(body.as_ref(), br#"{"id":2,"name":"y"}"#);
```

To find out why, read `error.codec_error().map(CodecError::label)` (a static text) and the
headers in `error.response()`. To react, in this order of preference:

1. Fix the server, or the test fixture, so that it labels what it sends. A response with a body
   and no `Content-Type` is refused.
2. Where the server cannot be fixed, select `IgnoreContentType<Json>` on that one endpoint
   (`response IgnoreContentType<Json>;`). It skips the `Content-Type` check and nothing else.
   Do not put it on the client to silence a few endpoints.
3. Read the refused body yourself with `into_response()`.

`into_response()` returns the response of a `Metadata` error too, and that response is a 2xx. A
handler that treats every `Ok` from `into_response()` as an error document should look at
`error.kind()` (or `status()`) first. The standard formats' rules are in the
[format guide](CUSTOM_FORMATS.md#7-strict-json-and-the-explicit-adapter).

Errors in documents a successful status carries (`{"ok": false}`) are the API's own: decode them
as the typed output, or write a format that turns them into a `Decode` error (the
[compatibility example](../examples/compat/README.md), case 2). Concord never inspects a body for
error markers.

### Reading the underlying error

`Error` has no `source()` chain on purpose. The underlying errors are reachable through
`transport()` (the reqwest error, top-level URL removed) and `codec_error()` (the format's
`CodecError`: a static label, numeric positions such as `line` and `column`, and
`source_unredacted()` for the parser's own error, if the format attached one); both are **not**
redacted below the top level: reqwest's nested errors can contain URLs (a refused redirect keeps
its target), TLS errors name hosts, and a parser's error quotes the body. `Display` and `Debug` of
a `CodecError` show the label and the positions only. To read the unredacted source, ask for it;
here the `Decode` error of a format that attached one. Excerpt of
[`crates/concord/tests/error_inspection.rs`](../crates/concord/tests/error_inspection.rs):

```rust
let source = error
    .codec_error()
    .and_then(concord::CodecError::source_unredacted)
    .unwrap();
assert_eq!(source.to_string(), "refused: CONTENT");
```

To log a source, pass it explicitly (`error.transport().map(|e| e as &dyn std::error::Error)`)
where that output may contain them.

## 7. Native requests

When one call needs something the declaration does not carry — a per-request timeout, an extra
header, a different body — take the prepared request apart, change it with reqwest's API, execute
it with the same client and finish with the endpoint's decoder. `Decoder::finish` applies the
status check, the declared decoding and Concord's transport-error conversion.

Excerpt of [`examples/quickstart/tests/caller_guide.rs`](../examples/quickstart/tests/caller_guide.rs):

```rust
let prepared = api.shop("acme").product(7).prepare()?;
let (client, mut request, decoder) = prepared.into_parts();
*request.timeout_mut() = Some(Duration::from_secs(2));
let request_id = reqwest::header::HeaderValue::from_static("req-1");
request.headers_mut().insert("x-request-id", request_id);
let product: Product = decoder.finish(client.execute(request).await).await?;

assert_eq!(product.id, 7);
assert_eq!(server.requests()[0].header("x-request-id"), Some("req-1"));
```

- `Decoder::decode(response)` applies the same handling to a response you already have: a
  non-2xx status is a `Status` error, the format checks the head (`Metadata`), then the body is
  read and decoded. `Decoder::<T>::new::<F>()` builds that handling for a format `F` and an
  output `T` without any declaration, for a response you obtained yourself.
- `reqwest::RequestBuilder::from_parts(client, request)` turns the pair back into a builder. Its
  `.header(..)` **appends** to the declared headers; `request.headers_mut().insert(..)` replaces
  one.
- `into_parts` is a one-way door for redaction: the native request's `Debug` prints the full URL,
  sensitive query values and path segments included; only header values flagged sensitive are
  masked (reqwest prints them as `Sensitive`). Mark extra secret headers with
  `HeaderValue::set_sensitive(true)` yourself.

More: the [recipes](RECIPES.md) (streaming, multipart, interleaved query parameters).

## 8. What Concord redacts, and what it does not

Covered — output produced by Concord:

- the generated `Debug` of clients, config structs, scopes and requests (they show values through
  `Display`, so numbers appear quoted: `limit: "20"`; a value placed only as a header shows its
  header value, `<redacted>` if it is a natively sensitive `HeaderValue`). Each shows only its own
  values — a request does not repeat its scope's or client's; for the whole request use
  `Prepared`'s `Debug`;
- `Prepared`'s `Debug`: sensitive query values, path segments and host labels appear as
  `<redacted>`, sensitive headers as `name: <redacted>`;
- `Error`'s `Display` and `Debug`.

Sensitive values are those marked `#[sensitive]`, those feeding a key with a well-known secret
name (`authorization`, `cookie`, `x-api-key`, `token`, `password`, ... — full list in the
[author guide](AUTHOR_GUIDE.md#7-sensitive-values)), and every key, segment or label they feed.
They are always sent. A `HeaderValue` you pass with `set_sensitive(true)` stays flagged on the
request (Concord never clears the flag) and is shown as `<redacted>`.

Not covered:

- the native `reqwest::Request`, `Url` and `Response` `Debug` — including `prepared.request()` and
  anything after `into_parts()`. It prints the full URL, sensitive query values and path segments
  included; header values Concord flagged sensitive print as `Sensitive` (reqwest's own masking);
- `Error::transport()` and the source of `Error::codec_error()`
  (`CodecError::source_unredacted()`), and reqwest errors from requests you execute yourself;
- redirects: reqwest forwards custom headers and sends a `Referer` with the query;
- tracing, middleware, proxies and server logs;
- the base URL, which is never treated as sensitive.
