Writing an HTTP API client is not as complicated as it is often made to sound. There is no exotic algorithm in it. What makes it tricky is that there are a few dozen small, concrete things to know, and that the right design for four endpoints is not the right design for forty.

What follows is an honest record of where I ended up writing API clients in Rust, and why. Every hand-written step compiles against the same running example: the Riot Games API. Riot is a useful teacher because its quirks are ordinary—two host families (platform hosts such as euw1 for game data, regional hosts such as europe for accounts and match histories), a second credential for signed-in players, 404 used to mean "not found", two pagination schemes, a POST served from one fixed host, and structured rate limits. GitHub has its second host, Stripe its idempotency keys, Slack its errors inside a 200, S3 its signatures; Riot simply puts enough of those shapes together to show where each client design bends.

Where this ends up

Part I · By hand

CHAPTER 01 · The problemSomebody else's domain, in your language

An HTTP API is not a flat list of URLs. It is somebody else's domain, with rules decided by another team:

  • where credentials go, and which subset of endpoints replaces the default credential with another;
  • which host family serves which group of operations;
  • which 404 means "no such player" and which means a broken request;
  • how a list continues from page to page, and how you tell it has ended;
  • which writes may safely be sent twice, and which status codes the provider guarantees were rejected before any side effect;
  • what the server's own error payload looks like.

Every client represents those rules in Rust somewhere. The architectural question is whether each rule is stated once where the compiler and a reviewer can inspect it, or survives only as a habit ("remember to encode that segment", "call the RSO helper here") that every new endpoint has to re-enact without a mistake. Complicating matters further, three different people read the same code and ask opposing questions of it:

Reader 01

The caller

Wants to type riot., discover operations, pass clear arguments, and get back useful types—without caring that start_time is spelled startTime on the wire or how many items fit on a page.

Reader 02

The maintainer

Sits with the provider's documentation open in a second window, checking paths, headers, query keys, and status codes endpoint by endpoint—the exact wire details the caller wants out of sight.

Reader 03

The person on call

Needs to know, when a request fails in production, which endpoint ran, what status came back, whether it retried, and that pasting the error into a ticket will not leak a key or user input.

Serving any one of those three is straightforward. Serving all three with the same code is where the real design tension lives.

CHAPTER 02 · Level 1A simple flat client

Declaration
Flat async methods
Usage
riot.match_ids("europe", p)
Pipeline
Raw reqwest::Client
Best for
Personal scripts (≤ 5 endpoints)

Suppose you need four operations from Riot: look up an account by Riot ID, list a player's recent match IDs, fetch one match, and fetch a summoner profile. The obvious starting point is sixty lines: a struct holding a reqwest::Client and four async methods.

For a small personal tool, stopping right here is the sensible choice. There is no abstraction to learn, each endpoint sits in one short function, and deleting an endpoint means deleting four lines. Anything heavier would be overhead.

The trouble appears when this code leaves a personal tool and runs in a service. Reading those sixty lines against the source of reqwest 0.13.5 turns up seven concrete defaults worth knowing:

  • The path is built with format!. name and tag come from outside the program. A space happens to survive because the URL parser percent-encodes it; a / or ? silently changes the route or starts a query string.
  • error_for_status() discards the server's explanation. It consumes the Response and returns an error holding only the status and URL. Riot's JSON body explaining why the request failed is thrown away.
  • reqwest::Error prints the URL in Display. It appends for url (…) whenever a URL is attached. With a header key that exposes user input from the path; with an API that puts its key in the query string, every logged error prints the secret.
  • Redirects are followed, up to ten hops, by default. When a redirect changes host, port, or scheme, reqwest strips Authorization, Cookie, Cookie2, Proxy-Authorization, and WWW-Authenticate. It does not strip X-Riot-Token, because a general HTTP client cannot know which custom headers hold credentials.
  • There are no timeouts. A default Client sets no connect timeout, no read timeout, and no total timeout. A peer that accepts TCP and stops answering holds the task indefinitely.
  • .json() buffers the entire body before parsing. A misbehaving proxy or unexpected response of arbitrary size is read completely into memory first.
  • Every 404 becomes an error, even though on three of these four endpoints it is Riot's ordinary way of saying "not found".

None of this is a flaw in reqwest. For a general HTTP client, following redirects, avoiding arbitrary timeout guesses, and reporting the failing URL are reasonable defaults. An API client simply knows things a general HTTP client cannot: which hosts it should talk to, which header holds a secret, and that a player profile is never two gigabytes long. Level 2 is telling reqwest what we know.

CHAPTER 03 · Level 2A careful simple flat client

Declaration
Flat methods + typed host enums
Usage
riot.match_ids(Region::Europe, p)
Pipeline
Shared edge helpers (~150 lines)
Best for
Small production APIs (4–10 endpoints)

Like most developers, this is where I started when writing a real client, and for a small API it is still where I stop. The endpoints stay flat methods on Riot, while each edge case from level 1 is handled once in a small helper. None of these pieces is complicated, and none of them disappears at later levels—only where they live changes.

A secret that cannot be printed

Seven lines close off a whole category of accidental leaks. A derived Debug on anything holding Secret prints Secret(…) instead of the key, and marking the outgoing HeaderValue with set_sensitive(true) hides it from HTTP-layer debug output as well.

A value fills one path segment

Passing every interpolated path value through seg encodes slashes as %2F and question marks as %3F, keeping untrusted input inside the single segment where it belongs.

Even this standard helper misses one subtle edge case until a test catches it: a value that is exactly .. (or ., or empty). Dots are unreserved characters, so seg("..") leaves .. untouched; the URL parser then normalizes the path and pops the preceding segment. Percent-encoding the dots as %2E%2E does not prevent it either, because URL parsing treats %2E%2E as a dot segment as well. A request for /matches/{id} with an id of .. resolves to the parent path while still carrying your credentials. Encoding is not enough here; the right fix is to refuse empty, ., and .. values before building the URL.

Query strings carry matching small traps: spaces can be encoded as %20 or + (and some servers accept only %20); lists are encoded as repeated keys, comma-joined values, or key[] depending on the provider; and an unset optional parameter must be omitted rather than sent empty. None of it is hard, and all of it is provider-specific knowledge that has to live somewhere.

Errors for callers and for the person on call

Three variants match the three actions a caller can take. On Network, no complete response arrived, so retrying may make sense. On Refused, the server answered negatively, and the caller needs the status, any Retry-After delay, and the decoded provider error. On Unexpected, a 2xx broke the expected shape or size limit, which usually points to a bug in the client or a breaking API change.

Three details protect the person on call: error.without_url() keeps user input and query credentials out of Network errors; both Display and a hand-written Debug on Error hide raw body bytes and decoded provider messages (since APIs regularly echo inputs back inside error payloads), leaving the RefusalBody field for explicit inspection; and RefusalBody distinguishes a complete body from one that exceeded 64 KiB or broke off mid-read, instead of silently collapsing failures into an empty vector.

Bounded reads, and two ways a response ends

Reading chunk by chunk and checking the running total before extending the buffer rejects oversized payloads as soon as they cross the cap rather than after allocating them. Ten mebibytes for a normal JSON payload and sixty-four kibibytes for an error body are conservative bounds; the point is having explicit bounds at all.

Notice send_opt sitting beside send_json. Whether a 404 means None or an error is a per-endpoint fact about Riot's API. In a flat client, that fact is encoded solely by which helper the method remembers to call.

Three clocks, not one

It is easy to treat "a timeout" as one number when there are three distinct clocks: connect (opening TCP and TLS), idle (read_timeout—how long the server may stay silent between bytes, catching stalled sockets without aborting slow active downloads), and total (how long the caller is willing to wait overall, which differs between a web handler and a batch job). Redirects are disabled with Policy::none(): an API client knows its hosts, and a 3xx is a response to inspect, not an automatic instruction to forward credentials elsewhere.

Replacing raw host strings with Region and Platform enums stops anyone from passing a platform where a region is expected. All told, there are under two hundred lines of reusable helpers, and each endpoint stays four lines long. If a client stays small, this is a good place to finish. Its weakness shows up only later: every safeguard above is a helper function, and a helper only protects the endpoints that remember to call it. Nothing stops the thirtieth endpoint, written quickly months later, from formatting a path without seg() or calling send_json where Riot uses 404 as absent.

CHAPTER 04 · Growth & changeWhen the API grows and moves

What pushed me past the flat client was not line count—twenty uniform GET endpoints on one host can live in level 2 comfortably enough. It was orthogonal rules multiplying as the API evolved:

A second credential. Riot Sign On adds endpoints that act for a signed-in player using Authorization: Bearer and must not send X-Riot-Token. Had the API key been placed in reqwest's default_headers, there would be no clean way out: reqwest merges default headers into every request lacking that key and offers no per-request removal. Because level 2 attaches the key in a helper, we add a second helper beside it—and the compiler will happily accept whichever one you type:

Optional query parameters. Match history gains filters. Past two or three optional positional arguments, call sites become unreadable, so we introduce a parameter struct:

Lists that span pages. Riot returns 20 match IDs by default and at most 100 per call. Fetching a season's games pushes pagination straight into application code:

Three facts about Riot—the default page size, the maximum, and that a short page ends the list—have leaked into caller code, where the next caller will rewrite them slightly differently. Worse, match_ids still returns a plain Vec<String> that looks complete while silently stopping at twenty items, a bug that passes every test with fewer than twenty-one fixtures.

A write on a fixed host, and retry safety. Tournament endpoints are POSTs served from americas. A GET that hits a 429 or 503 can safely wait out Retry-After and try again; a POST without an idempotency key cannot be replayed on a dropped socket, and should not be replayed on a 429 either unless the provider guarantees that every 429 rejects requests before side effects. (Riot's documentation tells callers to honor Retry-After and notes that underlying services can return 429 independently, without publishing a side-effect-free guarantee for writes—Retry-After says when to retry, not whether the first write took effect.) Making that distinction belongs in shared send logic that sees both the method and the failure, not copied into every method.

Structured rate limits. Riot tracks rate-limit buckets per application and per method on each host, announced in response headers. Respecting those buckets requires the sending layer to know which endpoint a request belongs to. In level 2, an endpoint is only a function name, never a piece of data the transport layer can inspect.

Where each fact lives

At this point, the cognitive load of the flat client is visible. Cognitive load here is not the length of the file; it is the number of unwritten rules a maintainer must hold in mind every time an endpoint is added or changed:

Fact about the API Where level 2 keeps it What checks it
Path parameters are encodedCalling seg() in each methodNothing
Which credential an endpoint usesCalling request() vs rso()Nothing
Which host family a group belongs toAn argument type repeated on every methodCompiler per method; the grouping, nothing
404 means absent hereCalling send_opt vs send_jsonNothing
How a list continues and endsA loop in caller codeNothing (not even inside the client)
Which operations may safely retryNowhere yetNothing
Which endpoint a request belongs toOnly a function name, not dataNothing
Facts, choices, and mechanism

Looking at that table exposes a three-way split that clarifies every design from here on. An API client mixes facts decided by the provider (credentials, hosts, status meanings, pagination, idempotency), choices decided by the caller (total deadline, retry budget, proxies, test mocks), and mechanism shared by every API (encoding, bounded reads, Retry-After math, retry loops, clocks).

Most maintenance pain in hand-written clients comes from these three bleeding into each other: a hard-coded total timeout puts a caller choice in the client, a pagination loop puts an API fact in application code, and repeating seg() forces every endpoint to invoke mechanism by hand.

CHAPTER 05 · Level 3The endpoint trait: a contract, still flat

Declaration
One struct + impl Endpoint each
Usage
riot.execute(&GetMatchesV5Ids { … })

Single executor (auth, bounds, retries)
Best for
Decoupled request values (15+ endpoints)

Once a client crossed fifteen or twenty endpoints with rules like those above, I stopped writing flat HTTP methods and moved to an endpoint trait.

That step changes how you think about a client. Instead of a bag of functions that each talk to reqwest, the client becomes a contract—close to a strategy pattern—with two clean sides. On one side sits the implementer of an endpoint: a struct that states facts about one request (output type, stable name, method, host, path, query, body, auth, idempotency) and knows nothing about networking. On the other side sits the caller and the single executor: client.execute(&endpoint) accepts any E: Endpoint, runs it through one pipeline, and returns Result<E::Output, Error>.

Every request of every endpoint now passes through one function, which is the single place that touches reqwest, attaches credentials, marks headers sensitive, enforces body limits, decodes errors, and handles retries:

This "endpoint as a value" architecture underpins several strong Rust libraries: gitlab pairs a five-method Endpoint trait (only method and endpoint required, organized in domain modules, with no associated Output type so callers can deserialize two different response projections from the same request value) with generic Query execution and composable wrappers (paged, ignore, raw); kube builds sans-I/O http::Request values in kube-core and executes them through a tower::Service; ruma splits Matrix operations into metadata! plus attributed #[request] structs. Separately, twilight-http gives every Discord endpoint a Route variant so its rate limiter can bucket headers per route, while its public request builders (such as CreateMessage<'a>) borrow &'a Client and implement IntoFuture rather than being detached values. Decoupling request descriptions from execution is a genuine strength.

Retrying, written once

again asks three questions in order: is this failure worth another attempt, may this request be repeated (a GET on 429 or 503, yes; an unmarked POST after a dropped socket, never; a POST on 429 only when not_applied_429 is true because a provider explicitly guarantees 429 rejects before side effects), and is the wait—the longer of Retry-After and jittered exponential backoff—within the cap?

Compare how two existing crates sit around that line: reqwest-retry's RetryableStrategy::handle receives only the response or error, never the HTTP method, so deciding which operations may safely repeat remains your job; AWS's Smithy-generated SDK makes 3 total attempts (at most 2 retries) in standard mode and can auto-fill @idempotencyToken fields because its model carries per-operation semantics. Notice also .retry(reqwest::retry::never()) in Riot::new above: reqwest 0.13.5 enables ProtocolNacks by default (up to two hidden resends on HTTP/2 remote REFUSED_STREAM or graceful GOAWAY), and disabling it ensures one pipeline owns every repeat.

Lists, written once

Putting Paged on the endpoint gets Riot's page-20 default and short-page rule out of caller code—though subtle loop edges remain open (what if a broken cursor repeats the same page forever, a next-page URL redirects to another origin, or page three fails after pages one and two succeeded?).

Where level 3 starts to pinch

Level 3 solved mechanism cleanly. Living with it across a real API exposed five frictions I could not shake:

  • Verbose even when simple. Look back at GetMatchesV5Match: it needs no query, no body, and no custom auth, yet still demands a struct, an impl Endpoint, an associated type, a name constant, host(), and path().
  • Repetition stays. Every regional endpoint repeats Host::Region(self.region); every match endpoint repeats /lol/match/v5/matches/; and 404 => None still does not fit execute -> E::Output cleanly without a second execute_opt method or per-endpoint decoding.
  • Inventing host types for relief. I ended up creating host wrapper traits like RegionalEndpoint and Regional<E> just to stop typing host() over and over—and immediately hit trait friction: either mirror every defaulted method of Endpoint onto parallel RegionalEndpoint and PlatformEndpoint traits, or fall back to raw Endpoint whenever an endpoint adds a query parameter or custom auth.
  • Flat, awkward call sites. Calling level 3 means filling in raw structs with explicit Nones (or deriving runtime-checked builders, as gitlab does, moving missing required fields to runtime errors from .build()).
  • The domain is gone. Look at GetMatchesV5Ids and GetMatchesV5Match. The API's real structure—scopes with their own hosts, prefixes, and credential rules—exists nowhere in the code except glued onto flat struct names.

CHAPTER 06 · Level 4What we ideally want — and trying to build it by hand

Ideal declaration

By hand (A)

By the end of level 3, what I ideally wanted was clear across all three axes of a client:

  1. In the declaration: each rule stated once at the level where it holds—the key on the client, the host and prefix on the scope, RSO credential replacement once—while still letting a maintainer read and check one endpoint without chasing five files.
  2. In the usage: callers navigate the domain itself—binding let matches = riot.matches(Region::Europe); once, awaiting a single lookup with matches.get(id).await, and streaming a paginated list with matches.ids(puuid).queue(420).count(100).pages().items()—with compile-time checks on required inputs, named setters on optional filters, and lists that cannot silently stop at page one.
  3. In what the client can do: every call still runs through one checked pipeline—encoding, sensitive headers, bounded reads, errors, retries, pagination guards, and network-free tests.

When many resources share the exact same CRUD verbs, hand-written Rust can get close to that ideal with one generic handle: kube's Api<K>::namespaced(client, ns) binds a resource type and namespace once and gives every resource get_opt (404 → None), list, and watch without repeating builders. Where an API instead has heterogeneous scopes—each with its own verbs, optional query filters, host families, and credential swaps—trying to reach that ideal in plain Rust pulls you into two different attempts, and each one fixes only half the problem.

Attempt A: domain scopes and a shared Call<E> by hand

Start from the usage we want. Compare calling level 3's flat struct with calling a domain handle built over the exact same pipeline:

The second call reads like the API. You bind matches once for a region, pass required inputs positionally, set only the filters you want by name, and await each call. That compiles, it is Send, and it shows both the strengths and the real limits of hand-written handles:

  • Borrow or own? Wrapping Arc<level3::Riot> keeps handles and calls lifetime-free and easy to store or move into tokio::spawn. Borrowing—as in octocrab's IssueHandler<'octo> (which cleanly shares many operations on one handler) and lifetime-bound ListIssuesBuilder—avoids an atomic refcount and is ergonomic at immediate call sites, with lifetimes pinching mainly in signatures, stored handles, or 'static tasks.
  • One calling convention or two? octocrab mixes plain async fn lookups (pulls(owner, repo).get(number).await) with builder lists finished by .send().await. Sharing one generic Call<E> with IntoFuture unifies calling cleanly (the example above boxes its future, just as Concord chooses to do, though IntoFuture itself does not require boxing).
  • Query serialization and Send futures. Pushing pairs by hand is repetitive; octocrab derives Serialize on the builder with #[serde(skip)] on the handler, coupling Rust fields to wire keys via serde attributes. Boxing Send futures also surfaces async traps where holding a non-Send temporary like format_args! across an .await compiles only until somebody spawns it.

With a shared Call<E>, adding a plain lookup like matches.get(id) in an existing scope is genuinely cheap—about fifteen lines. The friction shows up in two deeper places. First, any rich endpoint still splits its definition across four places: Riot::matches (how the host enters), Matches::PREFIX and Matches::ids (the prefix and defaults), impl Call<MatchIds> (optional setters), and impl Endpoint for MatchIds (path suffix, wire query keys like "startTime", and output type)—with no generated rustdoc assembling the effective URL and headers back together for a reviewer. Second, cross-cutting changes multiply across types: adding Riot Sign On to account.me, summoner.me, and rso_matches.ids—and sharing the four history filters between matches.ids and rso_matches.ids—means adding scope constructors, copying filter fields and setter impls onto each call struct, and still leaving seg(), 404 => None, pagination, and secret host boundaries unchecked by the compiler.

Attempt B: structural scopes chained in types

What if you attack repetition directly in Rust's type system instead—representing scopes as small composable types and chaining levels together, such as Chain<Regional, Chain<RsoAuth, Prefix>>?

↓ One adapter bridges any chained endpoint into level 3's single pipeline
↓ Two endpoints composed from reusable scope chains
↓ Now look at what the caller still has to write

Look honestly at what Attempt B buys and what it fails to solve:

  • It really does reduce repetition in definitions. Regional, PlatformHost, Prefix, and even cross-cutting RsoAuth are written once and composed into any endpoint's type Scope = Chain<…>.
  • It does not make usage follow the domain. Look at my_recent above: the caller is right back to constructing a flat GetRsoMatchIds struct and passing it to riot.execute(&Scoped(…)). There is no riot.rso_matches(Region::Europe, &token).ids().count(20). To give callers domain-shaped usage on top of structural scopes, you still have to write Attempt A's entire handle and builder layer by hand.
  • Understanding an endpoint still means chasing types, and bugs still compile. Knowing what GetRsoMatchIds sends requires reading Regional, RsoAuth, Prefix, and Scoped's resolution order. Worse, omitting a host from a chain (Chain<RsoAuth, Prefix>) still compiles and panics at runtime in parts.host.expect(…) unless you stack yet more marker traits onto the type system—and forgetting seg() or pagination still goes unchecked.

That is the wall you hit by hand. Combining one pipeline with a truthful domain representation is technically possible in plain Rust, yet paying for it in hand-written structs, builders, and chained scope traits splits every endpoint apart and becomes heavier than almost anyone wants to maintain.

Part II · The turn

CHAPTER 07 · Code generationGenerating it from a schema

When writing level 4 by hand gets that heavy, code generation is the next obvious question: describe the API once in a machine-readable schema and generate the structs, builders, and methods.

Where a trustworthy schema and a strong generator exist, zero marginal cost per endpoint is hard to beat:

  • The AWS SDK for Rust is generated from Smithy models: fluent builders (client.get_object().bucket(…).key(…).send()), per-operation error enums (GetObjectError::NoSuchKey) alongside a service-wide aws_sdk_s3::Error rollup, paginators, signing, and a retry runtime with automatic idempotency tokens.
  • Progenitor generates clients from OpenAPI 3.0 specifications—especially those emitted by Oxide's Dropshot servers—with positional or builder interfaces, optional tag-based grouping (tags = Separate), pre_hook/post_hook/inner_type customization, typed responses and errors, and paginated streams for Dropshot's pagination convention.
  • Riven, for Riot itself, generates grouped endpoint handles (such as .match_v5()) and models from riotapi-schema (automatically regenerated daily in CI from Riot's reference, with manual patches), maps nullable 404 endpoints to Option<T>, and layers a dynamic rate limiter on top that learns Riot's application and method buckets from headers.
  • The Google API crates (such as google-drive3) generate a hub, resource handles, and builders ending in .doit() from Google's discovery documents.

At three hundred endpoints with an accurate schema, the marginal cost of the three-hundredth endpoint is zero. Generation stops fitting for four practical reasons:

  • The generated API mirrors the generator's conventions, not bespoke Rust design. Riven groups operations under .match_v5(), yet its generated get_match_ids_by_puuid still takes eight positional arguments—route, PUUID, and six Options—as the generator's choice for optional query parameters. Switching to builder mode avoids long positional lists, and in both Progenitor's builder mode (Error::InvalidRequest) and the AWS SDK, omitting a required parameter turns into a runtime error on .send() rather than a compile error.
  • Wire schemas omit client semantics. OpenAPI can say an operation may return 404; it has no standard way to say that this 404 becomes Option::None, that a particular PUT is not idempotent, that a given status is guaranteed not to apply side effects, that a list ends on a short page, or that a long poll legitimately stays silent for a minute. Smithy models carry far more of this metadata—a major reason the AWS SDK works so well—yet few providers outside AWS publish Smithy models.
  • Often there is no schema, or it drifts from production. Riot publishes no official OpenAPI spec (riotapi-schema has to scrape Riot's docs and carry manual patches). Most internal services have no schema at all, and public schemas routinely disagree with production on optional fields, status codes, or query formats.
  • Multi-credential and multi-host policy still takes custom glue. Even though OpenAPI 3.0 can express per-operation security and servers, Progenitor does not wire credential selection automatically: its README shows reqwest::ClientBuilder::default_headers for the common case, and multi-credential or multi-host routing still means writing custom pre_hook/inner_type logic yourself alongside any client semantics like 404 => None.

CHAPTER 08 · The turnWhere Concord came from

Putting every hand-written and generated approach in one view makes the gap concrete:

Approach What it gets right What it gives up
Level 1 · Simple flatSixty lines; zero abstraction to learnSafety: encoding, timeouts, error bodies, redirects, bounds
Level 2 · Careful flatLocality: one endpoint is one short functionStructure; every safety rule relies on habit
Level 3 · Endpoint traitOne contract and pipeline; standalone named request valuesConciseness on simple calls; domain survives only in names
Level 4A · Hand handlesOne pipeline plus domain-shaped usage; ~15 lines per plain siblingSplits rich endpoints across 4 places; cross-cutting changes duplicate setters

Concord did not start with the goal of inventing a macro or a small language. It started more modestly: I liked level 3's contract and single pipeline, wanted level 3 to be lighter and less repetitive, and thought about a macro to clear away the boilerplate of structs, host traits, and impl Endpoint blocks.

The question that changed the design

If we are already jumping to a macro, what else can we gain?

Using a macro only to stamp out flat GetMatchesV5Ids structs keeps the flatness of level 3. The larger gain a macro makes possible is representing the domain truthfully—in declaration and in usage: achieving level 4's ideal without splitting one endpoint across four types or giving up navigable handles.

That meant asking one description to do seven specific things:

  1. keep an endpoint short and local enough to verify line by line against the provider's documentation;
  2. state each fact once, at the level where it holds—the key on the client, the host and prefix on the scope, 404 => None on the lookup;
  3. generate navigable domain handles and configurable calls on top of one checked pipeline;
  4. live inside the Rust crate, written by the person reading the docs, with no external schema required;
  5. express client semantics—status meanings, pagination, idempotency, idle timeouts—right beside the wire details;
  6. require exceptions to be explicit so the fortieth endpoint cannot silently diverge from its parent;
  7. leave escape hatches in ordinary Rust whenever an API does something unusual.

In ordinary Rust, hierarchy costs types, constructors, trait impls, and split definitions. Inside a macro that understands nesting directly, structure costs indentation.

CHAPTER 10 · Design tradesThe choices

Every piece of Concord's syntax and runtime reflects a deliberate trade against a sensible alternative. Here is where each trade lands, and what it gives up.

A tree, and one thing beside the tree

Modeling an API as a tree gets you far: the client declares what holds everywhere, scopes declare what holds for a group, and endpoints declare the rest. Single-value statements (base, read, idle_timeout) use nearest-wins; path appends segments; keyed statements (query, headers, status) inherit key by key.

Real APIs break pure trees immediately. In Riot, host routing (platform vs region) and authentication (API key vs RSO) cut right across subject scopes (account, matches, summoner). In Stripe, idempotency keys cut across every POST in every resource, and cursor parameters cut across every list. With scopes alone, you would either distort the caller's API with routing wrappers (riot.regional(Europe).matches()) or repeat the same lines across a dozen scopes.

So Concord puts one declaration beside the tree: a part. A part groups inputs with the statements that use them, and any scope or endpoint spreads them in with ..name without adding a handle level or a new type. Placement boundaries are strict: middleware and problem are client-wide only, and a part cannot hold path, problem, middleware, child nodes, type parameters, or nested spreads. When a subset of endpoints needs distinct middleware or a distinct error payload, you either branch on info.endpoint() or request origin inside client-wide middleware, or split out a second small client (such as an unauthenticated upload client). Leaving nested spreads and generic parts out costs some repetition—Kubernetes repeats list and watch for namespaced vs cluster pods, and Stripe's shared cursor part falls back to String instead of typed IDs—and keeps parts from turning into a second tree or a second type system inside the macro.

The signature and the block

Every input appears twice in a description: once in the signature (count?: u32) and once inside the braces where the wire uses it (count;). An obvious alternative puts wire placement directly in attributes on the parameter:

Annotation-driven styles (such as ruma's #[ruma_api(query)] fields) avoid repeating the identifier, and that is tempting. Two issues pushed me away from it. First, it mixes the two readers: the caller's signature fills up with wire annotations. Second, parameter attributes cannot express fixed headers, expressions combining two inputs (labels.join(",")), or overrides of inherited entries—so you still need a block anyway, splitting wire description across two places. The other shortcut—defaulting any unplaced input into the query string under its Rust name—is riskier still: renaming a parameter from start_time to since for callers would silently rename the wire key.

Drawing a clean boundary—outside the braces is the caller's interface, inside the braces is the wire—keeps both views readable, and the compiler enforces consistency between them. An unused input fails to compile, as does a header shorthand containing an underscore:

Refusing user_agent; in headers rather than silently rewriting _ to - keeps the shorthand rule uniform (the wire key is the identifier as written) while preventing underscore header names that proxies such as nginx ignore by default.

? is not Option

The ? marker in count?: u32 is the one piece of signature syntax that is not standard Rust. The alternative is inspecting type spelling for Option<T>, the way clap's derive macro checks whether a field's type is spelled Option.

Two problems make spelling-based detection fragile on inputs. First, a macro sees tokens rather than resolved types, so type PageSize = Option<u32> would silently turn an optional setter into a required positional argument. Second, "omitted by the caller" and "explicitly set to null" are distinct wire meanings. On GitHub's issue update endpoint, omitting milestone leaves it unchanged, sending null clears it, and sending a number sets it. Separating call optionality (?) from value nullability (Option<T>) expresses all three states directly:

↓ Three calls, three distinct JSON bodies on the wire

There is one awkward asymmetry here—and it is a real weakness to know about. After the return arrow, Concord does inspect token spelling for Option<T> and Result<T, E> (and their std and core paths) so an ordinary 2xx reads T and wraps it in Some or Ok. Because a macro sees tokens rather than resolved types, hiding either behind a type alias (type MaybeNumber = Option<u32> or type DomainNumber = Result<u32, String>) leaves the alias opaque—and since Option and Result implement serde::Deserialize, the code compiles and silently changes runtime decoding: on 200 null, literal Option<u32> fails with Kind::Mismatch (decoding u32), whereas MaybeNumber decodes Ok(None); on 200 7, literal Result<u32, String> returns Ok(Ok(7)), whereas DomainNumber compiles and fails at runtime with Kind::Mismatch. Always spell Option<T> and Result<T, E> literally after ->.

Exceptions are written

Single-value statements like read or idle_timeout use nearest-wins inheritance: an endpoint writing read Text; under a JSON client clearly means to replace the reader. For keyed statements—headers, query, and status—silent nearest-wins is hazardous. If a Slack client declares a client-level 200 arm to unwrap Slack's "ok": false envelope, a child endpoint adding its own 200 arm would quietly drop that check. Concord therefore requires override or remove whenever a child changes an inherited key:

The cost is one extra keyword at every exception. The benefit is that every divergence from parent rules is explicit and easy to find with grep.

A secret belongs to a host

GitHub serves its main API on api.github.com and release uploads on uploads.github.com. If an authentication header is declared on a client with base "https://api.github.com" and a child endpoint switches base, letting the secret follow automatically would send your token to a third-party pre-signed upload URL in another API. Concord rejects an inherited secret crossing a change of base:

Notably, the macro does not hard-code the name Secret to enforce this. When an entry is inherited across a second base (after binding to an earlier base, or to the first base below it on a branch), generated code passes the value through a helper bounded by a trait that serializable values implement and Secret does not. Rust's type system catches it even inside a template like "Bearer {token}" or behind a type alias. Sending the token to GitHub's upload host requires stating that choice explicitly:

Keep the boundary of this check clear: it guards the description across a second base—root secrets bind to the first base on each branch, so the description's author still chooses the initial host(s). And when a caller moves the entire client with with_base(…)—to hit a staging server or a local mock—every header, secrets included, goes to the new base, because the caller chose to redirect the whole client.

What a status means

By default, any 2xx is decoded by the active reader and any other status becomes a Refused error carrying the API's parsed problem body. A status block handles endpoint-specific or client-wide exceptions:

Compare this against the AWS SDK model. AWS generates per-operation #[non_exhaustive] error enums (GetObjectError) alongside a service-wide rollup (aws_sdk_s3::Error implementing From<SdkError<OpError>>), giving callers both granular operation errors and smooth ? composition across calls. Concord commits to one error type per client—generated riot::Error is a type alias for concord::Error<RiotProblem> (so two clients sharing the same problem type share the same Rust error type)—with four kinds: Build (the request could not be built), Transport (no complete response), Refused (the API rejected the call), and Mismatch (the response broke what the description promised). Whenever a specific non-2xx outcome is a normal domain branch callers ought to confront—a 404 lookup, a 409 version conflict, a 402 declined card—it moves into the return type as Option or Result. What you give up is per-operation error enums; callers inspect error.problem() and status codes as data instead.

A list is not a page

A call whose endpoint declares paginate does not implement IntoFuture:

Letting .await fetch page one would be more uniform and would avoid breaking callers if an endpoint later became paginated. I chose the compile error instead. Silently treating page one as the entire list is one of the easiest bugs to ship because small tests never cross a page boundary. Requiring .pages(), .pages().items(), or an explicit .send().await for one page costs one method call and turns silent truncation into a type error.

Three operational details of pagination belong in the open:

  • Short-page stopping when count is omitted. by_offset_limit(start, count) stops on a short page only when the caller sets count; when count is omitted, it waits for an empty page (making an extra request after a 1-item result). For APIs with a documented default page size like Riot's 20, write by_offset(start).stop_on_short_page(count, 20)—and use short-page stopping only when the provider guarantees full pages until the last one.
  • Per-page vs. whole-walk deadlines. Each page runs through the engine as its own call, so with_timeout on a paginated call bounds each page individually, not the whole walk. To cap total wall-clock time across all pages, wrap the pagination loop in tokio::time::timeout.
  • Loop, origin, and mid-walk failure guards. For repeatable requests, if a pager reproduces the immediately previous request (ignoring fragments and secret placements in the URL or headers), pagination halts with a Mismatch—catching immediate self-repeats (not multi-step A → B → A cursor cycles). If a next URL changes origin, pagination halts with a Build error without sending anything. And if page three fails, the caller has already received pages one and two and gets the error from the third try_next(), after which the stream ends.

Facts in the description, choices at the call

There is no retry statement and no total timeout statement in concord::api!. That follows directly from separating facts from choices: idempotent; and idle_timeout are facts about the endpoint (a write carries an idempotency key; a long poll stays quiet for a minute), whereas "try three times" and "abort after five seconds" belong to the calling program. Retries stay off until a caller passes with_retry(…), and there is no total timeout until a caller passes with_timeout(…) on the client or on a single call.

API-specific retry knowledge—like Telegram placing its retry delay in the JSON body, or a hypothetical provider whose edge gateway explicitly guarantees 429 rejects requests before touching state—ships as an ordinary Rust function beside the description (pub fn retry() -> orders::Retry) that callers opt into with with_retry(retry()). Be careful with not_applied_on(status): a Retry-After header tells you when to retry, not whether the first write had side effects, and listing a status in not_applied_on permits retries on that status across every endpoint sharing that policy (even endpoints marked idempotent false) whenever the body is replayable. Inside the engine, repeatability is always checked before custom when rules run, so a custom rule cannot accidentally retry an unmarked POST after a lost connection. The cost is that a new user's first client does not retry automatically and must opt in; keeping the three homes separate is worth that small surprise:

The macro knows no format

A fair worry with any macro language is lock-in: it looks clean on plain JSON REST endpoints, and then you meet XML, SigV4 signing, NDJSON watches, or a custom envelope and end up fighting the macro.

Concord avoids that with a strict boundary. The macro knows the tree, the twelve statements, and input placement. It knows no data format, no authentication protocol, and no pagination scheme. What follows read, paginate, middleware, idempotent, and idle_timeout—and the expression form of body (alongside its entry-block form body json { … })—is ordinary Rust. The five public extension points are three traits (Reader, Middleware, Transport), one pager trait/closure family (Pager / Paging), and plain body-writer functions returning Body or Result<Body, E> (Body is a struct, IntoBody is sealed, and json(…) returns Result<Body, WriteError>).

Middleware added by the caller via with_middleware runs first, followed by the description's middleware declarations in the order written—so the author places a request signer last among description middleware so it signs the final bytes. Within one attempt, middleware receives a Next handle and may short-circuit (0 forwards) or forward more than once (though resending from middleware is discouraged because it bypasses attempt accounting and repeatability checks). Concord's test suite exercises that boundary against ten real APIs: S3 uses a fifteen-line quick-xml Reader written beside the description plus SigV4 signing middleware; Slack and Telegram unwrap 200-with-"ok": false envelopes in ordinary functions; Kubernetes reads watches through JsonLines and turns ERROR lines into client problems; Elasticsearch drives point-in-time pagination with a custom pager that refuses incomplete shard responses. None required special cases in the macro.

The calling side

Four connected choices shape the generated Rust surface:

  • Every scope generates a handle. Callers write riot.matches(region).ids(puuid) instead of riot.match_ids(region, puuid). Handles can be stored and passed around, and call sites mirror the API's structure. The trade-off is that your tree layout becomes public API: moving an endpoint to another scope breaks callers unless you wrap the client behind your own facade.
  • Required inputs are positional; optional inputs are named setters. Positional arguments verify required inputs at compile time, paired with a closed Arg conversion trait: a value accepts itself, a reference (cloned inside), text for String or Secret, and slices or arrays for Vec (lifted through up to two Option layers), and nothing outside Concord can add conversions into your own types. Newtypes such as Puuid and MatchId stay genuinely distinct—&str never coerces into them—though two bare String parameters side by side can still be swapped.
  • Calls own their inputs and clone parent state. Input types must be owned and Clone (id: &str in a description is rejected). Creating a child scope or call clones its parent—cloning ancestor inputs, options, and the middleware Vec<Arc<…>> while sharing transport and middleware instances via Arc—so keep large payloads out of client/scope inputs (or wrap them in Arc/Bytes). In return no handle or call carries a lifetime, every one is Send + Sync + Clone, calls move cleanly into spawned tasks, and the engine can rebuild requests on retries and subsequent pages. Note that Clone on a call is distinct from body replayability: a call holding a one-shot Body::stream still cannot retry. Compared with level 3 values like gitlab::Endpoint or kube_core::Request, a Concord Call<E> is bound to a live client rather than being a standalone sans-I/O value.
  • Every call shares one generic type, Call<Endpoint>, parameterized by a public marker type per endpoint (the generated Endpoint trait itself is sealed). Inside the SDK's own crate, you can write an inherent impl riot::Call<riot::matches::Get> directly; from a separate consuming crate, Rust's orphan rule rejects inherent impls (E0116), so consumers attach custom methods via an extension trait instead.

Why a language at all

The largest design commitment is choosing a function-like macro with its own small syntax instead of attributes on Rust items, a build script, or an external spec file.

Both alternatives are technically possible in Rust: proc-macro attributes can inspect inline mod blocks to recover nesting, and build scripts can emit include!d Rust expressions that still type-check against your crate's types. What drove Concord to a small function-like DSL is editorial rather than a claim of impossibility. With inline modules and attributes, every scope and endpoint still carries Rust module, struct, and field ceremony that pushes inherited context, cross-cutting parts, and leaf wire rules apart across the screen; with a build script, the description leaves the module where its types and helpers live. Keeping the tree, its twelve statements, and its parts compact enough to read on one page—with right-hand sides checked as ordinary Rust in your module, one-pass macro diagnostics, and generated effective-request rustdoc—is what the small syntax buys.

Part IV · Reality check

CHAPTER 11 · CorrectnessHow you know it is right

A client is correct when the bytes it sends match what the provider accepts, and the bytes it receives are interpreted as the provider intended. Four checks divide that work:

  • By construction. Once rules are declared, structural mistakes fail to compile: unused inputs, underscore header shorthands, accidental overrides of inherited keys, secrets crossing a second base, and awaiting a declared paginated list directly are rejected before any test runs.
  • By reading. Keeping each endpoint short and written in the API's own vocabulary—backed by generated rustdoc showing each endpoint's effective URL, headers, and status arms—makes side-by-side review against the provider's documentation practical in a way that chasing hand-written handles, setters, and trait impls across four places is not.
  • By testing the wire. Every call has .request(), which builds the outgoing reqwest::Request before middleware without sending it (requiring a replayable body; use .into_request() for one-shot streams). To inspect requests after middleware (such as signers or auth), plug in concord::fake; to verify exact wire bytes and framing over TCP, use concord_testkit::Server. The wire assertions behind the Riot, GitHub, and Payments examples on this page run without opening a socket.
  • By testing time. Retries, Retry-After waits, and timeouts often go untested because real sleeps slow down test suites. Pairing concord-testkit's Script transport with Tokio's paused clock lets a test verify a 429 with Retry-After: 2 in milliseconds of real time:

None of those four checks guarantees that a description matches a live server. An author can still omit a paginate rule or a 404 arm, a provider's live behavior can drift from its docs, and custom middleware, transports, or decoders can still carry runtime bugs. What these checks do is catch structural drift early and make wire bytes and time-dependent paths straightforward to review and test.

CHAPTER 12 · The billWhat it costs

None of those gains is free. Generating structs, setters, and rustdoc for every endpoint shifts work onto rustc. In the library author's measurements on synthetic clients with dependencies built, first cargo check cost scales as (incremental edits to a leaf endpoint vs. a shared part have not been measured separately here):

< 1 s 62-endpoint Riot client · first cargo check
~8 s · < 1 GiB 1,000 synthetic endpoints (deps built)
~30 s · 2.5 GiB 3,000 synthetic endpoints (deps built)

For an API on the scale of AWS, this is the wrong tool. Beyond compile time, here is the rest of the bill in full:

Non-Rust syntax & output-alias caveat

rustfmt skips concord::api! bodies, and editors assist less inside macro tokens than in plain Rust. Inner expressions are type-checked with source spans, though bad expressions can surface generated helper names. Also, because the macro recognizes Option<T> and Result<T, E> after -> by token spelling, hiding either behind a type alias compiles and silently changes runtime decoding.

Twelve statements to learn

Plus inheritance rules, parts, and ? on inputs. Small enough to pick up quickly, yet still a small language every contributor to your crate must learn before editing an endpoint.

You write the data models

Concord reads no OpenAPI document and generates no serde structs. For an API with large payloads like Riot's Match, writing or importing the response types remains most of the work.

Coupled to reqwest, Tokio, and upstream error shapes

Transport and Middleware expose reqwest::Request and reqwest::Response; sending requires Tokio, there is no blocking client, and each call's future (Sending) is boxed. Additionally, Http's request_not_sent() signal (relied on by auth::Rotating) depends on internal error wrapping in reqwest, hyper-util, hyper, and h2, and its docs note an untested pooled-connection hand-off race.

One error type; public tree

You trade per-operation error enums for one client error alias (concord::Error<P>) and runtime inspection of error.problem(). Moving scopes breaks callers unless wrapped in a facade; renaming a required input preserves positional callers, except that renaming an input used in a shorthand entry (count;) also changes the wire key.

Explicit secret boundaries

Display and Debug on clients, calls, and errors print no values, and secret headers are marked sensitive. However, error.details() prints retained headers and problem/body evidence, source() keeps custom transport/writer errors, with_base sends secrets to the caller's chosen base, and send_raw() returns a reqwest::Response whose {:?} prints its URL.

Early maturity and MSRV

Concord is a release candidate (5.0.0-rc.1), not yet published to crates.io, sets rust-version = "1.96", and promises no compatibility before a stable release (its Unreleased changelog already contains breaking changes relative to rc.1). Early adopters should pin a git revision and wrap the client behind a facade if stability matters.

CHAPTER 13 · FitWhen to use something else

A small client (a handful of endpoints)

Write level 2. A hundred and fifty lines of careful helpers beat adopting a macro when there is not yet a domain hierarchy to manage.

A strong provider SDK (AWS)

Use the AWS SDK; a hand-maintained description will not rival a runtime generated from Smithy models with signing, paginators, and retries built in.

You own the server and emit OpenAPI

Generate the client—Progenitor with Dropshot is the model here. Writing a separate description would create a second source of truth when you already have one.

A long-lived cluster state machine

For Kubernetes, use kube: keeping watches, reflectors, and cluster config healthy over weeks is far more than describing HTTP routes.

Caller-chosen shapes or sans-I/O values

If callers pick partial response structs per call or queue standalone requests independent of any live client, the level 3 design of gitlab, kube-core, or ruma fits better.

Where Concord fits

The large middle where many real integrations live: fifteen to a few hundred endpoints documented in prose without a schema you trust, whose rules cross-cut scopes and whose client you expect to maintain as the API moves.
