# The rules: what a user must know

*Concord V5 design · reference · [index](../README.md) · the other sheets: [grammar](grammar.md), [messages](messages.md), [the crate](crate.md), [engineering](engineering.md) · the tradeoffs: [chapter 8](8-scope.md)*

Everything on this page is something a Rust developer could **not** guess from one example and from Rust habits. There are 26 rows. What can be guessed is not here. What only the code and the tests must hold is in the [contracts](contracts.md). How the engine runs a call (the tries, the two clocks, pages, `concord::Http`) is in [the engine](engine.md); how the macro checks a description is in [the macro](macro.md).

Each rule has a mark. It says what happens when a reader guesses wrong.

| Mark | A wrong guess… |
|---|---|
| **C** | …does not compile. The message says what to write. |
| **B** | …is refused when the request is built. Nothing is sent. |
| **S** | …is silent. These are the ones to learn. There are 7. |
| **C·S** | The form is checked, and one consequence is silent. There are 7. |

What holds each rule is the contracts that it cites, in [the contracts](contracts.md), each with its state; the tests of each contract are listed in `build/MATRIX.md`.

## The tree

| # | | Rule |
|---|---|---|
| 1 | C | **Three kinds of node.** `client Name(inputs) { }` gives a type with `Name::new(…)`. `scope name(inputs) { }` gives a method that returns a handle. An endpoint starts with its method: `GET name(inputs) -> T { }` gives a method that returns a call. With nothing in its block it ends with `;`. The required inputs are the arguments, in the order written. |
| 2 | C | **An input marked `?` is optional:** `count?: u32`. It is not an argument: it gets a method with its own name, on the call, or for an input of a client or a scope on the client or the handle (`github.repo("rust-lang", "rust").reference("stable")`). It is not sent when it was not set. The method takes a `T`, a `&T`, what an argument of type `T` takes, or an `Option<T>` (`None` un-sets it). In the block, the name is a `&Option<T>`. Without `?`, `x: Option<T>` is a required argument that may be `None`. **`milestone?: Option<u64>` has three states** (not set; set to nothing; set to a number). `milestone;` in a JSON body of entries sends them as left out, `null` and a number; in a query, a header or a form, "not set" and "nothing" both send nothing (rule 8). The author's own code can tell them apart. `.milestone(5)` and `.milestone(Some(5))` give the number, `.milestone(None::<u64>)` gives "nothing", and a bare `None` does not compile there. The method converts through these two levels, `name?: T` and `name?: Option<T>`, and no more: `n?: Option<Option<u64>>` takes its exact value. There is no written default: a default belongs to the provider. |
| 3 | C | **An argument** is the declared type, a reference to it (it is cloned inside), text (`"Faker"`) for a `String` or a `Secret`, or an array or a slice for a `Vec`. For an optional list of `String`, text in an array or a slice too: `.labels(["bug", "ui"])` for `labels?: Vec<String>`. Nothing else: `ids("p-1")` does not compile for `puuid: Puuid`; write `Puuid::from("p-1")`. An input owns its data: its type cannot borrow, and it is at least as visible as the client. |
| 4 | C | **A bare name is an input of the node that wrote the statement.** An input of a node above is named with its owner: `client.key`, `matches.route`; an owner's name is in reach in its own node and below. So no input may have the name of an owner in reach: `client`, or a scope above it. A bare name that is not an input is whatever Rust finds in your module, with no word. And an input hides an item of its name in the lines of its node: the item is then written with its path (`body concord::form(form);`). A `const` or a `static` in reach is not hidden: an input with its name does not compile (E0530). One name is not hidden: the path before a body of entries. In `body form { form; }`, `form` before the block is the function, seen from where `api!` stands. |

## The request

| # | | Rule |
|---|---|---|
| 5 | S | **The URL is glued, root first:** the nearest `base`, then every `path` on the way down, the endpoint's own last. Pieces are joined with one `/`. The URL ends with `/` when the last piece does: the last `path`, or the `base` when no `path` follows. |
| 6 | B | **A value stays in its slot.** In a path, `{x}` fills one segment or a piece of one, and is encoded. `{*x}` is a whole segment that may hold several: each piece between two `/` is encoded, and empty pieces are kept (`folder/` and `a//b` are sent as they are). In the host, `{x}` is one label or a piece of one (`"https://api-{label}.example"`), and the finished label is checked: 63 characters at most, letters, digits and `-`. After `:` it is the port. Refused: a `{x}` or `{*x}` value that is empty; a finished segment that is `.` or `..` (`v{x}` with `..` gives `v..`, which is sent); a host value that is not one label; and a host that a URL parser would read as another one. |
| 7 | C | **An entry** of `query { }` or `headers { }` is `name;` (the key `name`, the input `name` of this node) or `"key" = value;`. A value is an input, fixed text, a template (`"v{version}"`), or any Rust expression (`labels.join(",")`). `client.x;` is not a short entry: write `"x" = client.x;`. In `headers`, a short entry whose name has `_` is refused (`"user-agent" = user_agent;`), and `host` is not a key: the host is the `base`. |
| 8 | S | **A value is written by `serde`**, in a path, a query and a header as in a body: a type has one wire form. There it must be one text; in a query and in headers also nothing (not sent) or a list (the key is sent once for each item). **In every block of entries (`query`, `headers`, a body), a `None` writes nothing:** one level of `Option` is presence, and what is inside is written as the place writes it (the table below). A `None` in a path is refused, and an empty list in a hole of a template is nothing: the entry is not sent. Anything else is refused when the request is built. Text is percent-encoded for its place, `%` too; a space is `%20`. A header value is never percent-encoded. |
| 9 | C·S | **One body for an endpoint: `body <expression>;`, or a body of entries, `body json { chat_id; text; }`.** The expression is Rust, with the inputs as variables, and gives a `concord::Body` that carries its `Content-Type`. `json(x)` and `form(x)` are functions of the crate; a function of yours is the same thing. **A body of entries is written as `query` is:** a `None` writes nothing (rule 8); a template is as in `query` (a hole that reads nothing leaves the entry out; one that reads several is a Build error); a `Secret` is an entry like any other, written as its text (`body form { grant_type; client_id; client_secret; }`). Inside one level of `Option`, a value is written by the format: in JSON, `"k" = Some(x);` writes `null` for a `None` in `x`. A form has no `null`: an inner `None` writes no pair either, and a list or a struct as a value is a Build error. A struct that holds a `Secret` is still not written: `body json(task)` with a secret field does not compile. *Silent:* a body made by an expression follows its type: `json!({ "cursor": cursor })` writes `null` for a `cursor?` that was not set, where `body json { cursor; }` leaves it out; a struct leaves it out with `#[serde(skip_serializing_if = "Option::is_none")]`. And in a form, `milestone?: Option<u64>` set to nothing sends what "not set" sends: nothing. |
| 10 | C·S | **What a node sets holds for everything below it.** A statement that holds one value (`base`, `read`, `idle_timeout`) is the nearest one. A key (an entry of `query` or `headers`, an arm: for an arm, what it takes, rule 13) that is set above is set again lower only with `override`, and taken away with `remove`. Inside one node, a key is written once. Only `path` adds. *Silent:* an `override` whose value is `None` sends nothing for that key. After a `remove`, a level below sets the key again plainly, and the entry goes on the wire at the place where the key was first written above. **For each send (each page is one), `idle_timeout` runs first, then `idempotent`, then the expressions of the request,** by kind (the base, the paths, the query, the headers, the body), and inside a kind in the order of the tree: the client first, a node's parts before its own lines. An `override` runs at the turn of the node that wrote it, and its entry goes on the wire where its key was first written ([the engine](engine.md), section 2.1). `read` runs for each answer; a pager once, at `.pages()`; a `middleware` expression once, in `new`. |

**An `Option` in an entry** (rules 8 and 9), in `query`, `headers` or a body:

| Written | What goes out |
|---|---|
| `x?: T`, or `x: Option<T>`, with `x;` | nothing, or the value |
| `milestone?: Option<u64>` with `milestone;` | nothing, `null`, or a number (JSON) |
| `"k" = value;` where the value is an `Option` (`"x" = client.x;`, `"ids" = ids.as_ref().map(join);`) | nothing when it is `None` |
| `"k" = Some(x);` with `x: Option<T>` | `null`, or the value: the way to write a `None` as `null` |

`null` is JSON's. A query, a header and a form have no `null`: there an inner `None` writes nothing too.

## The response

| # | | Rule |
|---|---|---|
| 11 | C·S | **A 2xx is the success.** Its body is read into the type after the arrow by the nearest reader. **After the arrow, `Option<T>` and `Result<T, E>` are read as `T`,** and given as `Some` or `Ok`; the arms give the rest (`404 => None`, `409 { body } => Err(body)`). So a `200` whose body is `null` is not a `None`. A body of no bytes is the reader's affair: `Text` gives an empty text, `Binary` no bytes, and `Json` a Mismatch, so a `204` under `-> T` with `read Json;` needs an arm (`204 => None`). **There is no format by default:** a client says `read Json;` once, and an endpoint that differs says its own (`Text`, `Binary`, `Stream`, or a reader of yours). An endpoint that reads a body (by this rule, or by an arm that binds `body`) and has no reader in reach does not compile. **A `HEAD` with an arrow has nothing to read:** it needs an arm for a 2xx, an exact status or the class (`2xx => true`), and a 2xx that no arm takes is a Mismatch. `Json`, `Text` and `Binary` stop at 10 MiB. Any other status is an error. *Silent:* `Option` and `Result` after the arrow are found by a closed list of spellings ([contracts](contracts.md) C1.7); behind an alias, the body is read into the alias as into any type. |
| 12 | C·S | **With no arrow, success gives `()`.** The body is ignored, and nothing about it can make the call fail. So an endpoint with no arrow, under an arm in reach that would read a body (`2xx { body } => Reply::into_result(body)?`), does not compile: give it an arrow (`-> Ignored`, a type of yours that reads anything), or remove the arm. *Silent:* with no arrow, a body that is not what the API promised goes unseen. |
| 13 | C | **`status { }` holds arms, and they add to rule 11:** `404 => None` gives a meaning to the `404`, and a 2xx with no arm is still the body (under a `HEAD`, a Mismatch: rule 11). An arm that needs a part of the answer binds it: `200 { body } => Some(body)`, `201 { body, headers } => …`, `4xx { status } => …`. Naming `body` is what reads it; a part that is not named is not there. In an arm, `?` on the API's own problem ends the call with it, and `headers.require("location")?` ends it as "not what was promised" when the header is missing. **An arm is written, overridden and removed by its key; what it takes decides only when `override` is needed.** In one node, a class and an exact status of that class may both be written: the exact one wins. A class arm from above (`2xx`, `4xx`) takes every status of its class: an exact status under it is written with `override` (`override 404 => None` under a client's `4xx { body } => …`), and `override 2xx => …` over inherited exact arms of that class is refused until each of them is overridden or removed. A class arm under an inherited exact arm of its class (`2xx => …` under a `200` from above) is written plainly: the exact arm keeps its status. `remove 4xx` takes away the arm written `4xx`, and nothing else; `remove 404` with only a `4xx` above is refused: to take `404` from the class arm, write `override 404 => …`. For a `HEAD`, the edits are resolved first; then an inherited arm that binds `body` is left out. **A 2xx arm from above that binds `body` does not reach an endpoint whose arrow is an `Option` or a `Result`:** under it a `null` in the body would be a `None`, with no word. The endpoint writes that arm itself (`override 2xx { body } => Some(unpack(body))`) or removes it (message 46). |
| 14 | C | **`problem E;` on the client** names how the API says no. When it refuses and the body is an `E`, `e.problem()` gives it. It is read by the reader written on the client; another one is named on the line (`problem E read Xml;`). |
| 15 | S | **An error is small and silent.** It keeps the status, the headers, at most 64 KiB of the body, and at most 1 KiB of a reader's own message. Printed, it shows its kind, the status, the name of the endpoint, and where it can a name for the cause (the place in the body that did not decode, made of names of the program and indexes, so a key of a map prints as `[key]`; for a failed connection, one of `connection refused`, `connection reset`, `name not found`, `no connection`). Never a value: not a URL, not the body, not a text that your code gave; and `source()` holds no value of the answer either. That text is in `e.reason()`, and `e.details()` prints everything, the reader's own message too, when you ask. |

## Behaviour

| # | | Rule |
|---|---|---|
| 16 | C·S | **Who you are is a value.** A credential is an input of type `Secret`, placed like any value: `headers { "authorization" = "Bearer {token}"; }`, `query { "api_key" = key; }`, `body form { client_id; client_secret; }`. A value that holds a `Secret` is secret wherever it goes. **It is bound to a `base`:** an entry, or a piece of a `path`, whose value holds a `Secret` belongs to the `base` in reach where it is written: the one of its own node, or the nearest above. Only where none is in reach (a secret on the client, above every `base`) is it bound to the first `base` below, on each branch: so a key on the client, with a `base` on each scope, goes to all of them. Under any other `base` further down, the description does not compile until the entry is written again there (`override "authorization" = "Bearer {client.token}";`) or removed. A `path` cannot be written again or removed: write that `path` under each `base` that needs it, not above them. Any `base` written below is another `base`, also with the same text. A caller's `with_base` moves everything: it is the caller's own word. A signature, a token that is renewed, a quota: a `middleware` ([rule 26](#parts-and-middleware)). Concord has no rule of its own for a `401`. *Silent:* a secret is read once, when the request is built. |
| 17 | C | **`paginate p;`** on an endpoint adds `.pages()`. **A call to it is not awaited directly:** `.send().await` gives one page, `.pages()` gives them all, and `.pages().items()` gives the items when the type after the arrow has `concord::page::IntoItems` (`Vec<T>` has it; you write it for a list type of yours; `Option` and `Result` do not have it). `p` is a function from the call and its answer to the next call: a closure, a function of yours, or one that a shipped function gives (`by_offset(start)`, `by_offset_limit(start, count)`, `by_cursor(after, f)`, `by_page(page, first)`, `by_link()`, `by_next_url(f)`). The counting ones (`by_offset`, `by_offset_limit`, `by_page`) need `IntoItems` too. In `p`, an input of the endpoint names its place on the call, not its value; a pager written in place is a `move` closure. The request of a page is built when that page is asked for. **`at_url` gives a path and a query, never an origin:** a URL at another origin than the one that the call builds is a Build error, in pages and outside them. A relative URL is resolved against the URL of the answer that gave it, or, with no answer (your own `call.at_url("../next")`), against the URL that the call builds; a fragment is dropped. **Every page goes to the origin of the first request:** another origin is a Build error. A next page that is the request just sent is a Mismatch: the same method, the same URL, the same bytes of the body and the same headers, once what a secret wrote in the URL or in a header is left out (a piece of a path, a pair of the query, a value of a header). A body is compared as its bytes. A header value is left out by its `sensitive` mark, so one that your `edit_request` marks is left out too. These checks look at the request as it was built, before any middleware. A pager that fails gives a Mismatch, or with the API's problem a Refused error. A paged call whose body is one `Body` that is a one-shot stream (an input) fails at its second page, with a Build error; an expression that makes a new stream each time it runs gives each page its own. After an error the pages are over. |
| 18 | S | **Retry is off until you set it** (`with_retry`, on the client or on a call). Then a request goes out again when three things hold: its body is not a stream; it may be repeated, in one of three ways (its method: a `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE` that does not say `idempotent false;`; its mark: an endpoint that says `idempotent;`; or the status of the answer is one that the policy lists with `not_applied_on`, as an author's `slack::retry()` does for a `429`); and the failure is one worth another try (the standard table: a connection that failed, a timeout, a body that broke, `408`, `429`, `502`, `503`, `504`; or a rule of yours). The method is the one of the request as it was built, before any middleware. So a `POST` that is not marked is not sent again after a connection that failed: you get the error, and `e.class()` says `Connect`. The waits are fixed: a random time up to 1 second, then 2, then 4, never more than 60, and never less than a `Retry-After`. A `Retry-After` is read in seconds or as a date: one that cannot be read counts as none, and a date in the past is a wait of zero. A `Retry-After`, or a wait that a rule asks for, over 60 seconds: no other try; the error is the result, and `e.retry_after()` gives the longer of the two waits. Rules add up inside one policy: every `unless` is asked, and the `when` rules in the order they were added; the first that gives a wait wins. **A `with_retry` on a call replaces the whole policy of the client** for that call: keep the author's by passing it on, `with_retry(github::retry().when(mine))`. Each try goes through the middlewares and the transport again. After `blocked`, the result is the blocked error. |
| 19 | S | **Two clocks.** `idle_timeout` bounds one silence: 30 seconds, unless it is set. It watches two things, and nothing else: **the transport**, from the moment it gets the request until the head of the answer (each piece of a stream body going out starts it again); and **a body while it is read** (each piece starts it again). A middleware's time, before or after the transport, and a reader's own waits are never silence: only `timeout` bounds them, and with no `timeout` they may wait for ever. A `ByteStream` counts silence only while a `try_next()` waits; after `send_raw()`, neither clock follows the answer. `timeout`: the whole call; no limit until you give one; no request is handed to the transport after it has ended. Both are set with `with_…`, on the client or on a call, and neither changes the other. The description may set the clock for silence of the calls below a node, for a long poll (`idle_timeout <expression>;`, [sentence 19](grammar.md)). The order: `with_idle_timeout` on the call, then the description's `idle_timeout`, then `with_idle_timeout` on the client, then 30 seconds. *Silent:* a body held in memory goes out in one piece. A large one on a slow line, or a slow answer, needs a longer `idle_timeout`. |

## The call and the client

| # | | Rule |
|---|---|---|
| 20 | C·S | **A call is a value.** `.await` sends it (`send()` does the same; for a paged call, rule 17). `send_full()` gives an `Answer<T>`: the value with the status and the headers. `send_raw()` gives the `reqwest::Response`, with nothing read and no arm asked (with retry on, the policy still looks at a head of `400` or above: rule 18). `send_if_none_match(etag)`, on a `GET` or a `HEAD`, takes a `&str`, writes `If-None-Match` when the request is built (in place of any that the description wrote, and before the edits of `edit_request`), and gives an `Answer<Option<T>>`: a `304` that no arm takes gives `None`, with its headers. `request()` builds the `reqwest::Request` to look at; `into_request()` takes it. An option of the API keeps its own name; Concord's settings start with `with_` (`with_retry`, `with_timeout`, `with_idle_timeout`), and `edit_request(…)` changes the built request. `read_response(response)` reads an answer that you got yourself, with the arms and the reader of the endpoint. *Silent:* `request()` is the request as the description builds it, with the values that it places, a `Secret` among them; what a middleware or a transport adds on the way out is not in it. |
| 21 | C | **On a client,** the same `with_…` settings as on a call, and three more: `with_base(…)`; `with_transport(…)`, what really sends (`concord::Http` with settings of yours, a `reqwest::Client` of yours, a fake, a transport of your own), under the middlewares; and `with_middleware(…)`, a middleware of yours, which a request goes through before the ones of the description. Each returns the client, changed. |
| 22 | S | **Concord's own HTTP client, `concord::Http`,** waits at most 30 seconds for a connection, follows no redirect (a `3xx` is an answer), and keeps no cookies by default. `Http::with(\|builder\| …)` adds a setting of yours (a certificate, a proxy); nothing in it can make this client follow a redirect. A `reqwest::Client` that you bring keeps its own settings. |
| 23 | S | **Concord prints names, never values:** the endpoint, the status, the try. It logs one event, `retry` (the endpoint, the try, the status or the class, the wait), at the level debug. A `Secret` hides itself from `Debug`, and its header is marked sensitive for the HTTP library. A `Secret` in a path or a host is part of the URL: Concord prints no URL, and what a proxy logs is outside. A `Secret` can be replaced while the program runs (`key.replace(…)`): every holder of a clone sends the new one in each request built from then on. |
| 24 | C | **Generated names follow the tree.** The client `Riot` gives the module `riot`; its scope `matches` gives `riot::Matches`; the endpoint `ids` in it gives `riot::matches::Ids`. The error is `riot::Error`, with `riot::Result<T>`, and the retry policy of the client is `riot::Retry`. The module is the name of the client in snake case: `GitHub` gives `git_hub`, and `Github` gives `github` ([contracts](contracts.md) C1.5). A scope may have the name of one of your types: `riot::Account` is the handle, `Account` stays yours. **Some names are Concord's.** A name that becomes a method (a child, or an optional input) may not be a method that its receiver already has (`send`, `request`, `read_response`, `pages`, `at_url`, `clone`, `call`, `new`, …), nor start with `with_`. These are exact names, by receiver: the table is [contracts](contracts.md) C1.6. A required input is an argument and makes no method: it may have any name. Concord adds no name to a call, a handle or a client in a minor version, unless it starts with `with_`. |

## Parts and middleware

| # | | Rule |
|---|---|---|
| 25 | C | **A node that names a part (`..page`) has its inputs and its statements, as if it had written them:** the inputs after its own, in the order written; the statements before its own. Entries and arms are put together, and inside one node a key is written once: a key (an entry, an arm) or a statement that holds one value (`base`, `read`, `body`, `paginate`, `idempotent`, `idle_timeout`), written by the part and again by the node, or by two parts of one node, does not compile. One exception: bodies of entries with the same function, in the parts and in the node, are put together: the parts' entries first, in the order in which the node names them, then its own; a key that two of them write does not compile. `override` is for a key from a level above, not for a part; an entry or an arm of a part that says `override` or `remove` is checked where the part is named. An input of a part may not have the name of an input of the node, and a node names a part once. Inside a part, a bare name is an input of the part, and `client.x` is an input of the client; an input of a scope is not there. |
| 26 | C·S | **`middleware m;` on the client** is what every request goes through on its way out. A request goes first through the middlewares that a caller added (`with_middleware`), then through the ones of the description, in the order written, then to the transport; the answer comes back the same way. **The author writes the one that signs last:** nothing changes a request after it was signed. `m` gives a value with `concord::Middleware`. It is made once, in `new`: its expression sees the required inputs of the client (`key` or `client.key`), as references, and nothing else; the macro refuses an optional input there, and `?` does not compile. What a middleware changes is its author's affair: the checks of pages and of retry look at the request as it was built, before any middleware. It runs for every try and every page: a request that is sent again is signed again. Nothing takes it away, not a node below and not a caller. `with_transport(…)` replaces what really sends, under it. *Silent:* every handle and every call of the client shares that one value, and what it holds (a quota, a token). |

## The silent ones, again

These are the ones a reader can get wrong without a message. A new user should read these first.

| # | In short |
|---|---|
| 5 | The URL is the nearest `base`, then every `path`. It ends with `/` when the last piece does. |
| 8 | A value is written as `serde` writes it. A list repeats its key. A `None` in an entry writes nothing. |
| 15 | An error keeps 64 KiB and prints no value. `details()` when you want them. |
| 18 | Retry is off. Then only what may be repeated goes out again: `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE` unless marked `idempotent false;`, an endpoint marked `idempotent;`, or a status that the policy lists with `not_applied_on`. An unmarked `POST` is not sent again after a failed connection. A `with_retry` on a call replaces the client's policy. |
| 19 | 30 seconds of silence at most (`idle_timeout`): the transport, and a body while it is read; a middleware's time is not silence. A body in memory goes out in one piece. No limit in all until you set `timeout`. |
| 22 | `concord::Http`: 30 seconds for a connection; no redirect followed; no cookies by default. A `reqwest::Client` of yours keeps its own settings. |
| 23 | Names in the logs, never values. |

And the silent half of seven rules that are otherwise checked:

| # | In short |
|---|---|
| 9 | In a body made by an expression, a `None` is what the type writes (`null` in `json!`), not "not sent". A body of entries leaves out every `None`; `"k" = Some(x);` writes `null`. A form has no `null`. |
| 10 | An `override` with `None` sends nothing for that key. A `remove` leaves nothing. For each send: `idle_timeout`, then `idempotent`, then the request by kind, from the client down; an entry keeps the place where its key was first written. |
| 11 | There is no format by default: an endpoint reads with the nearest `read`, and `Json`, `Text` and `Binary` stop at 10 MiB. An alias of `Option` after the arrow is not seen. |
| 12 | No arrow: success gives `()`, and the body goes unseen. |
