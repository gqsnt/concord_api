# The cases: every case and its outcome

*[Concord](../../README.md) · [docs](../README.md) · reference · previous: [the contracts](contracts.md)*

This page is for you when you want the outcome of one exact case: where a statement may appear, what a node inherits, what a name means, how a value is serialized, what a response produces, when a request is retried, what the timeouts do, what pages do, and where a secret goes. Each of the nine tables lists every case of one question, with its one outcome and the page where that outcome is stated: [the grammar](grammar.md), [the rules](rules.md), [the messages](messages.md), [the contracts](contracts.md), [the engine](../internals/engine.md) or [the macro](../internals/macro.md). A cell adds nothing to those pages.

Every case has one outcome. "Does not arise" and "cannot be" mean that another cell already rules the case out.

How a reference is written: `rule 13` is a rule of [the rules](rules.md); `sentence 5` is one of the nineteen sentences of [the grammar](grammar.md); `C5.2` is a [contract](contracts.md); `message 32` is a message at compile time, and `messages 2` the texts at run time, in [the messages](messages.md); engine, [Pages](../internals/engine.md#pages) and macro, [The steps](../internals/macro.md#the-steps) link to a part of [the engine](../internals/engine.md) or of [the macro](../internals/macro.md), and grammar, [What follows each statement](grammar.md#what-follows-each-statement) to a part of the grammar; `grammar, table` is the table of [where each statement may appear](grammar.md#where-each-statement-may-appear), `grammar, ref` names a line of [the grammar itself](grammar.md#the-grammar), and `messages, opening` is the text above the first message of [the messages](messages.md).

A statement that holds one value (`base`, `read`, `idle_timeout`) is the nearest one (sentence 1; rule 10). A secret under another `base` is table 9. ## 3. A name on the right-hand side

Before an expression written in a node, the generated code binds one local for each enclosing owner and one for each input of that node; every one is a reference (macro, [The author's names in the author's Rust](../internals/macro.md#the-authors-names-in-the-authors-rust)). An owner's name is visible in its own node and below: `client.key` in a line of the client is right (rule 4; C1.10). The macro reads a name itself only in a template placeholder, a `name;` entry and a `base`. In an expression, a bare name that is not an input of the node is whatever Rust finds in the module, with no message (rule 4; C1.16); if Rust finds nothing, the message is `rustc`'s (C1.10). An input shadows an item with the same name in the lines of its node (rule 4). One name is not shadowed: the `f` of `body f { … }` is a path, not an expression (rule 4; C1.16). An entry of a body of entries is as an entry of `query` (sentence 18; C1.21).

## 4. A value and where it is placed

A value is serialized by `serde` in one of three shapes: nothing, one string, several (C2.4). A type with no `Serialize` does not compile (macro, [The messages that are `rustc`'s](../internals/macro.md#the-messages-that-are-rustcs)); a shape that is not accepted where the value is placed is a Build error (C2.4; rule 8). The macro does not look at the type of an input (macro, [What the macro may know](../internals/macro.md#what-the-macro-may-know)): only the mark `?` is seen at compile time.

The last two columns are an entry of a body of entries. There the value is a template, anything that `serde` can serialize, or a `Secret` (grammar, [What follows each statement](grammar.md#what-follows-each-statement)), and the function before the block receives all the entries as one map (sentence 18; C2.14): `json` writes it with `serde_json`, `form` with `serde_urlencoded` (C2.9). A `None` writes nothing there, as in `query` and in `headers`: one level of `Option` is presence, and what is inside is written as the format writes it (rule 8; rule 9; C2.14). The macro knows no type for this: `Entries` asks `serde` whether the value is a `None` (C2.14; engine, [How a value is written](../internals/engine.md#how-a-value-is-written)). A form has no `null`: there an inner `None` writes no pair either, and a list or a struct as a value is a Build error (rule 9; C2.14). The unit (`()`) is not a `None`: in a body it is written as the format writes it, `null` in JSON, and a form cannot write it, which is a Build error; in a query and a header it writes nothing (C2.4; C2.14).

## 6. Retries

Three conditions must hold for another attempt: the request can be copied; it may be repeated, by its method, by its mark, or by a status that the policy lists with `not_applied_on`; and the failure is worth another attempt (C4.1; rule 18). The method is the one of the request as it was built, before any middleware (C4.1). The expression of the mark runs once for a send, after `idle_timeout` and before the request is built (rule 10; C4.1; C10.3). The order of the checks is in the engine, [The decision to retry](../internals/engine.md#the-decision-to-retry). "Another attempt" below always means: if an attempt is left (3 in all for `Retry::standard()`, C4.2) and the wait is allowed (C4.3). When the attempts run out, the last outcome is the result (C4.4). A `with_retry` on a call replaces the whole policy of the client (C4.6).

## 7. The timeouts

A timeout ends a wait, and nothing else: work that can finish without waiting finishes, and code that does not yield is not interrupted (C7.6). When a timeout expires, the caller gets a Transport error of class timeout whose note names the timeout, what it waited for, and where its length is set (C7.6; messages 2). An outcome that is already known, an error response or the Mismatch of `no_arm`, is returned in its place, with `kept()` saying interrupted (C7.6; engine, [The two timeouts](../internals/engine.md#the-two-timeouts)). Two timeouts that expire at the same instant: the one that covers more is reported, `timeout` over the connect timeout, over a wait between two attempts, over the idle timeout (engine, [The two timeouts](../internals/engine.md#the-two-timeouts)).

## 8. Pages

Nothing is sent before the first `try_next()`. The request of each page is built when that page is requested (C8.4). After a page arrives, the pager runs before the page is returned; the page is always returned first, and what was found about the next one comes with the following `try_next()` (C8.4). After an error, there are no more pages: every later `try_next()` returns `Ok(None)` (C8.4; rule 17).

"The same request" is: the same method, the same URL without its fragment, the same values of each header, in their order, and the same bytes of the body, with what a secret wrote in the URL or in a header left out: its text in the path, a pair of the query, a value of a header (rule 17; C8.4; engine, [Pages](../internals/engine.md#pages)). A value of a header is left out by its `sensitive` flag, so one that `edit_request` marks is left out too (C3.1; C8.4). A body is compared as its bytes (rule 17; C8.4; engine, [Pages](../internals/engine.md#pages)); a body that is a stream has no bytes to compare, and a request with one is never "the same request" (C8.4; engine, [Pages](../internals/engine.md#pages)). This check and the check of the origin look at the request as it was built, after `.edit_request(…)` and before any middleware (C8.4). The request of a page is built once, by the first half of a send; the origin is checked on it first, then "the same request"; then that same request is sent (C10.10; engine, [Pages](../internals/engine.md#pages), `Ready`).

`at_url` provides a path and a query, never an origin: a URL at another origin than the one that the call builds is a Build error, in pages and outside them (rule 17; C8.6; engine, [Pages](../internals/engine.md#pages)). It is checked when the request is built, before the edits of `edit_request`; the pages are held to the origin of their first request, as it is after those edits. The two checks are separate (engine, [The path of one call](../internals/engine.md#the-path-of-one-call), step 3; engine, [Pages](../internals/engine.md#pages)).

| A call sent to a URL (`at_url`) at another origin than the one that the call builds | With the `try_next()` that builds that request: the URL is checked when the request is built, before the edits of `edit_request` (engine, [The path of one call](../internals/engine.md#the-path-of-one-call), step 3; engine, [Pages](../internals/engine.md#pages), `Ready` and the bullet of `at_url`). For a call that was given the URL before `.pages()`, that is the first one (C8.6: "in pages and outside them"). | A Build error: `the URL is at another origin than the call` (messages 2; rule 17; C8.6). Nothing is sent (C2.11). Then `Ok(None)`. |
| A failure with the API's problem | With the `try_next()` after the page (C8.4; engine, [Pages](../internals/engine.md#pages), `Failed`). | A Refused error with that problem and the status of the page that came: `refused: status 200, in tasks.list` (C8.4; messages 2). Then `Ok(None)`. |
| A `mismatch` | With the `try_next()` after the page (C8.4; engine, [Pages](../internals/engine.md#pages), `Failed`). | A Mismatch whose `reason()` is the text (C5.8); printed as `the next page cannot be asked` (messages 2). Then `Ok(None)`. |
| A relative URL, from a response | Not at all, when it is sound: it is resolved against the URL of the response that contained it, and its fragment is dropped (rule 17; C8.6; engine, [Pages](../internals/engine.md#pages)). | The next page, as for a next call: its path and its query replace the ones of the description (C8.6). The resolved URL is still held to the origin that the call builds (C8.6) and to the first origin (C8.4). |
| Not from a pager: a caller's own `call.at_url(url)`, with no response | When the call is sent, or its first page requested (C8.6; engine, [The path of one call](../internals/engine.md#the-path-of-one-call), step 3). | A relative URL (`"../next"`) is resolved against the URL that the call builds; a fragment is dropped (rule 17; C8.6; engine, [Pages](../internals/engine.md#pages)). A URL at another origin: the Build error of the row above, also outside pages. A URL that does not parse: a Build error (C8.6). |
| A next call whose request does not build (a URL that does not parse, a value that cannot be placed) | With the following `try_next()` (C8.6: "when the call is sent"; engine, [Pages](../internals/engine.md#pages), `Ready`). | The Build error. Then `Ok(None)`. |
| A next call, when the body of the call is one `Body` that is a stream which can be read once (an input: the clones of the call share it) | With the `try_next()` after the first page. The first page took the stream and is returned; the building of the second page fails (rule 17; C2.15; C8.4; engine, [Pages](../internals/engine.md#pages)). | A Build error: `the body is a stream that was already sent` (messages 2). Nothing is sent (C2.15; engine, [Pages](../internals/engine.md#pages)). Then `Ok(None)`. |
| A next call, when the expression of the body makes a new stream each time it runs (`body fresh();`) | With the following `try_next()`: the request of the page is built then, and the expression runs again (C8.4; C2.15; rule 10). | The next page: one-shot is a property of a `Body`, a value, and each send has its own; each page is one send (C2.15; rule 10). When the pager requests the same method, URL and headers again: the next page still, and it is sent. A stream has no bytes to compare, so a request whose body is a stream is never "the same request" (C8.4; engine, [Pages](../internals/engine.md#pages)). |

`.pages().items()` yields the items of each page in order, requests the next page when one is used up, and yields an error once (C8.7). A paginated call is not awaited directly: `.send()` returns one page (C8.8).

## 9. A secret and a change of `base`

A value "holds a `Secret`" when it is a `Secret`, an `Option<Secret>`, a reference to one, or a template with one in a placeholder (C2.4). An entry, or a placeholder in a `path`, with such a value stays with the `base` that applies where it was written: the rule, and which `base` that is, are in [rule 16](rules.md#behaviour) (C8.9). A `base` that a part holds is the `base` of the node that names the part (rule 25): in this table it is written on that node.

The message is `rustc`'s, in Concord's words (messages, opening; macro, [The messages that are `rustc`'s](../internals/macro.md#the-messages-that-are-rustcs)). At an entry: `a secret does not follow a change of base`, with the note `write this entry again with override, or remove it, under the new base`. At a placeholder in a `path`: `a secret in a path does not follow a change of base`, with the note `write this path under each base that needs it, rather than above those bases`.

| What was written, and where | The `base` that it is bound to | The endpoint is under that `base` | Another `base` is written further down that branch: on a node between, or on the endpoint | The caller moved the base: `with_base(…)` |
|---|---|---|---|---|
| An entry with a `Secret`, on the client; the `base` is on the client too | The client's: the `base` of its own node (rule 16; C8.9). | Sent (rule 16). In a header it is marked sensitive (C2.7). | It does not compile, until the entry is written again there (`override "authorization" = "Bearer {client.token}";`) or removed (rule 16; C8.9). | Sent to the new base: a caller's `with_base` moves everything, it is the caller's own decision (rule 16; C8.9). |
| An entry with a `Secret`, on the client; no `base` on the client, one on each scope | None applies: on each branch, the first `base` below the client, the one of each scope (sentence 10; rule 16; C8.9). | Sent, to all of them: "a key on the client, with a `base` on each scope, goes to all of them" (rule 16). | It does not compile under a `base` below the scope's (on an endpoint of that scope), until the entry is written again there or removed (rule 16; C8.9). | As the first row. |
| The same, and each scope gets its `base` from a part (`scope matches(..regional)`) | On each branch, the `base` of the scope: the part's `base` is the scope's own (rule 25; sentence 11; rule 16). | Sent, to all of them (rule 16). | As the row above. | As the first row. |
| An entry with a `Secret`, on a scope that has its own `base` | The scope's: the `base` of its own node (rule 16; C8.9). | Sent (rule 16). | It does not compile, until the node below writes it again or removes it (rule 16; C8.9). | As the first row. |
| An entry with a `Secret`, on a scope with no `base` of its own; the `base` is above, on the client | The client's: the `base` that applies where it is written, the nearest above (sentence 10; rule 16; C8.9; macro, [The steps](../internals/macro.md#the-steps), step 3, the row of an entry). | Sent, when no `base` is written below the scope: the endpoint is under the client's `base` (rule 16). | It does not compile, until the entry is written again there or removed: the new `base` is another one than the client's. A `base` applied where the entry is written, and one more is written below it on the way (rule 16; C8.9; macro, [The steps](../internals/macro.md#the-steps), step 3, the row of an entry). | As the first row. |
| An entry of a part, with a `Secret`; the part holds no `base` | It is the entry of the node that names the part (rule 25): as the row of that node. | As the row of that node. | As the row of that node. | As the first row. |
| An entry with a `Secret` and a `base`, both in one part | The `base` of the part: both are the node's own, and it is the `base` of its own node (rule 25; rule 16). | Sent (rule 16). | It does not compile, until the node below writes it again or removes it (rule 16; C8.9). | As the first row. |
| A placeholder in a `path` that holds a `Secret` | As an entry written on the same node (rule 16; C8.9). | Sent, as part of the URL (rule 23; C8.2). | As an entry written on the same node. Where it does not compile, a `path` cannot be written again or removed: write that `path` under each `base` that needs it, not above them (rule 16; C8.9; messages, opening). | Sent: `with_base` replaces the whole base, and the `path` lines stay (C2.10; rule 16). |
| An entry of a body of entries, with a `Secret` (`body form { client_id; client_secret; }`) | The `base` that applies to the endpoint: a body appears on an endpoint, or in a part that an endpoint names (rule 16; C8.9; table 1). | Sent, written as its text (rule 9; C2.14; C8.2). | Does not arise: no node is below an endpoint, and a body inherits nothing from a level above (grammar, `endpoint`; C1.21). | As the first row. |
| An entry whose value holds no `Secret` (also a string that the author's code made from one) | None: the check is on the secret side of the adapter only (C8.9; C2.4). | Sent. | Inherited, like any entry (sentence 1). | Sent: `with_base` replaces the base, and nothing else (C2.10). |
| A `middleware` that adds a credential | None: it is not a value that the description places (sentence 16). | It runs for every request (sentence 16). | It runs too: nothing takes it away, not a node below. One that must leave some requests alone looks at the request, or at `info.endpoint()` (C9.6). | It runs too (sentence 16; C9.6). |

Beside the cells:

- A `base` written below with the same text as the one above is another `base` (rule 16; C8.9).
- A next URL of a page: a query pair whose value holds a `Secret` is written on it, every pair of that key already there is taken out first, and no other pair is added (C8.2; engine, [Pages](../internals/engine.md#pages)). Every page goes to the origin of the first request (C8.4), and `at_url` never provides an origin (rule 17; C8.6).
- A redirect: `concord::Http` follows none (rule 22). A caller's own `reqwest::Client` that follows one: what goes with it is up to `reqwest`, and no middleware sees it (C7.5).
