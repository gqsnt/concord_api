# The contracts: what Concord does, exactly

*[Concord](../../README.md) · [docs](../README.md) · reference · previous: [the crates](crates.md) · next: [the cases](cases.md)*

For you when you must know exactly what Concord does in one case, or when you change Concord and must not break a promise. This is the specification of the macro, the engine and the shipped pieces. It says **what** each part does. **How** the engine does it is in [the engine](../internals/engine.md), and how the macro does it is in [the macro](../internals/macro.md); where a line links there, that part is its design.

There are 104 numbers in ten groups, `C1` to `C10`. A number is never used twice; five are not used. Other pages cite a contract by its number.

**The tests of a contract carry its number.** A test that holds contract C5.4 has `c5_4_` at the start of its name. `just matrix` lists every contract with its tests, in `target/contracts-matrix.md`.

**The code:** the engine is in [`concord-core`](../../concord-core/src), what is shipped in [`concord-extras`](../../concord-extras/src), the macro in [`concord-macros`](../../concord-macros/src).

## C1. The description

| # | Contract |
|---|---|
| C1.1 | In a block, statements come first, then children. In the block of the client, the parts (C1.17) stand between the two. Anything out of this order is a compile error. |
| C1.2 | An endpoint is `METHOD name(inputs) [-> T] { … }`, or the same with `;` in place of an empty block. The method words are `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`; `METHOD "X" name(…)` sends the token `X`. The string is checked when the description compiles: it must be an HTTP token (`METHOD "VERSION-CONTROL"`). |
| C1.3 | There are twelve statements. In one node, each of these is written at most once: `base`, `path`, `body`, `read`, `paginate`, `problem`, `idempotent`, `idle_timeout`, and one block each of `query`, `headers` and `status`. The twelfth, `middleware`, stands on the client and may be written several times (C1.19). |
| C1.4 | A name of a scope, an endpoint or an input is lower snake case: the letters `a` to `z`, digits and single `_`, starting with a letter, not ending with `_`. A Rust keyword is refused, in every edition, and so is a raw identifier. The list is closed: `abstract`, `as`, `async`, `await`, `become`, `box`, `break`, `const`, `continue`, `crate`, `do`, `dyn`, `else`, `enum`, `extern`, `false`, `final`, `fn`, `for`, `gen`, `if`, `impl`, `in`, `let`, `loop`, `macro`, `match`, `mod`, `move`, `mut`, `override`, `priv`, `pub`, `ref`, `return`, `self`, `static`, `struct`, `super`, `trait`, `true`, `try`, `type`, `typeof`, `unsafe`, `unsized`, `use`, `virtual`, `where`, `while`, `yield`. An input may have the name of any word of the language that is not a Rust keyword and not an owner in reach (C1.10). |
| C1.5 | A type name is made in one way: cut the name at each `_`, make the first character of each piece a capital, join. A digit never cuts: `get_sha256sum` gives `GetSha256sum`. Two names of one level that give one type are a compile error: `one2` and `one_2` both give `One2`. A client name is upper camel case; its module is that name in lower case, with a `_` before each capital that follows a small letter or a digit, and before the last capital of a run that is followed by a small letter (`XMLHttpClient` gives `xml_http_client`). `Self`, and a name whose module would be a keyword, are refused. |
| C1.6 | **Reserved names**, for a name that becomes a method: a child, or an optional input (its setter). It may not have the name of a method that its receiver already has. The exact names: on a call, `send`, `send_full`, `send_raw`, `send_if_none_match`, `request`, `into_request`, `edit_request`, `read_response`, `pages`, `at_url`, `into_future`, `clone`; on a client or a handle, `call` (kept for later) and `clone`; on a client, `new`. Anywhere: a name that starts with `with_`. **Concord adds no name to a call, a handle or a client in a minor version, unless it starts with `with_`.** A required input is an argument, and may have any name. In the module of a client: `Error`, `Result` and `Retry`. A name that clashes is a compile error, and the message says to rename it. **Every name that the macro makes for itself starts with `__`** (a method, a field, a type), so no name of an author can meet it. |
| C1.7 | **An optional input is marked: `count?: u32`.** With `?` the input is not an argument: it is a method with its own name, on the call, or on the client or the handle for an input of a client or a scope. It is not sent when it was not set. The type is the type of the value when it is given; in the block, the name is a `&Option<T>`. The setter takes a `T`, a `&T`, what an argument of type `T` takes, or an `Option<T>` (`None` un-sets it). `milestone?: Option<u64>` keeps "not set" apart from "set to nothing": a body made of entries in JSON leaves the first out and writes the second as `null` (C2.14), and the author's own code can tell them apart; a query, a header and a form send nothing for both. Its setter: `.milestone(5)` and `.milestone(Some(5))` give the number, `.milestone(None::<u64>)` gives "nothing", and a bare `None` does not compile. The setter of `name?: Option<String>` takes text. A setter converts through two levels, `name?: T` and `name?: Option<T>`, and no more: a deeper type (`n?: Option<Option<u64>>`) takes its exact value. `x: Option<T>` without `?` is a required argument that may be `None`. An alias changes nothing. An optional input cannot fill a hole of a path or of a `base`, nor be the input of `base x;`. **After the arrow**, the macro finds `Option` and `Result` by their spelling, from a closed list: `Option<…>`, `std::option::Option<…>`, `core::option::Option<…>`; `Result<…, …>`, `std::result::Result<…, …>`, `core::result::Result<…, …>`. `Result<…>` spelled with one argument (an alias of the author's, `type Result<T> = std::result::Result<T, MyError>;`) is the same wrapper, read as its `T`; `riot::Result<T>` is another spelling, and is not. A leading `::` and parentheses around the type are ignored. It is the spelling and nothing but the spelling: a type of the author's with one of these names is written with another path (`model::Option<T>`). What such an arrow reads is C5.2. |
| C1.8 | An input type cannot borrow. It is `Clone + Send + Sync + 'static`. A `concord::Body` is `Clone` too: bytes can be built again, a stream is taken once. |
| C1.9 | Every input is used at its node or below: in a hole, an entry, or as a variable in an expression. This is a check of the text: an identifier among the tokens of an expression counts, also inside a macro call, and so does a name inside a string of a macro call (`format!("{n}")`); letters inside another string do not. An input that is never used is a compile error. |
| C1.10 | An input of a node above is named `client.x` or `scopename.x`. An owner's name is in reach in its own node and below (`client.key` in a line of the client is right). A scope cannot be named `client`, a scope name cannot repeat on one chain, and an input cannot have the name of an owner in reach (`client`, or a scope above it). `client.x;` is not a short entry: write `"x" = client.x;`. The macro checks such a reference only where it reads it itself: in a template hole, a `name;` entry, a `base`. Inside an expression, a name that does not exist is `rustc`'s error (the macro, [A name of the author, in the author's Rust](../internals/macro.md#a-name-of-the-author-in-the-authors-rust)). |
| C1.11 | **A generated type is defined at its place in the tree, and has no other name** (`riot::matches::Ids`): in a module of the client, made by the macro. Its `impl` blocks stand at the place of the macro call, so every type and every expression of the author resolves there. No code of the author is ever pasted inside a generated module, and a generated module has no `use super::*;`. A type of the author reaches the fields through **one hidden trait for each client**, with one associated type for each input and for the problem type, implemented once at the place of the macro call. The trait has the visibility of the client, so an input type must be at least as visible as the client. Before an expression, each owner in reach is one hidden view whose fields are references to the inputs of its level: `client.region` is a `&Region`, as `region` is (the macro, [Where the generated items live, and how they reach the author's types](../internals/macro.md#where-the-generated-items-live-and-how-they-reach-the-authors-types) and [A name of the author, in the author's Rust](../internals/macro.md#a-name-of-the-author-in-the-authors-rust)). A call has one field for each of its inputs, and **its fields are not public**: a pager reads an input through its place (C8.6), never as `call.page`. **`api!` writes items:** like every item of Rust, they cannot name a generic parameter of an enclosing function (`rustc` says it: E0401). `Self` in a type of a description is refused by the macro: write the path of the type. |
| C1.12 | The visibility written on the client holds for every generated item. A visibility that is relative (`pub(super)`) is written again for each depth of the generated modules, so that it means what the author wrote. `///` (or `#[doc = "…"]`) on a node goes to what is generated for it; on a required input, to the method that takes it; on an optional input, to its setter. `#[cfg]` stands on a node only (a client, a scope, an endpoint) and goes on everything that depends on it, the associated types of the hidden trait too; the description is still checked in full. `#[deprecated]` and `#[doc(hidden)]` stand on a scope or an endpoint, and go on every item generated for it; inside generated code, a use of a deprecated item of its own does not warn. An input and a part take doc comments, and no other attribute. |
| C1.13 | `override` and `remove` apply to what has a key: an entry of `query` or `headers`, and an arm. `override` or `remove` of a key that is not set above is a compile error (one exception: `override 2xx` with no `2xx` above is accepted when exact arms of that class are above, and takes their place; each of them is still overridden or removed in the same node, below), and so is either word before a statement that is not an entry or an arm (`path`, `base`, `read`, `idle_timeout`, `body`, `paginate`, `idempotent`, `problem`, `middleware`) or before a whole block (`override headers { … }`): the message names the statement. A key set above, written again without one of them, is a compile error. For `base`, `read` and `idle_timeout` the nearest statement is used, and no word is written; `base` may stand on a client, a part, a scope or an endpoint, and the `path` lines above it still apply. An endpoint with no `base` in reach does not compile. `path` only adds. Header names are compared without case, query keys exactly. **Arms are compared by what they take:** a class arm from above (`2xx`, `4xx`) takes every status of its class. So an exact status under an inherited class arm is written with `override` (`override 404 => None` under a client's `4xx { body } => …`): it takes that status away from the class arm. And `override 2xx => …` over inherited exact arms of that class is refused until each one is overridden or removed. A class arm written under an inherited exact arm of its class (`2xx => …` under a `200` from above) is written plainly: the exact arm keeps its status. In one node, a class and an exact status of that class may both be written; the exact one wins. An arm is still written, overridden and removed by its key: "what it takes" decides only when `override` is needed. So `remove 4xx` takes away the arm written `4xx`, and nothing else (an exact arm set on the way stays), and `remove 404` when only a `4xx` is set above is a compile error: to take `404` away from the class arm, write `override 404 => …`. A status key is one token: three digits from 100 to 599, or a digit from 1 to 5 and `xx`. |
| C1.14 | "Set above" means the state after every level above, removals included. After a `remove`, a level below sets the thing again plainly, and cannot `override` it. `read` cannot be removed, only named again. Inside one node, a key is written once, with the parts that the node names (C1.17). |
| C1.15 | Path text is not empty, has no leading `/` (it may end with one: C2.3), no empty piece, no piece that is `.` or `..`, no space, `?`, `#` or `%`, no `\` (the URL would read it as `/`), and no ASCII control character (a tab, a line end: the URL would lose it); the fixed text of a `base` has neither, and a `Base` made at run time refuses both (a Build error). A `{*x}` hole stands in a path only, and is a whole segment. `{{` and `}}` are braces. |
| C1.16 | **The macro knows no item of `concord-extras`, and no format, scheme or pager.** What stands after `body`, `read`, `paginate`, `idempotent`, `idle_timeout` and `middleware`, after `read` on the `problem` line, as the value of an entry and as the expression of an arm is a Rust expression that it copies as written, at the place of the macro call. In it, an input, bare or with its owner (`client.x`), is a reference to the input (in `paginate`, a bare name is its place: C8.6), so the core takes references where it takes values: `Value` for `&Secret`, `Reader<T>` for `&R`, and `idempotent` takes a `bool` or a `&bool`, and nothing else. An input hides an item of its name in the lines of its node, by Rust's own rule: the item is then written with its path (`concord::form(form)`). The `f` of `body f { … }` is not an expression and is not hidden: it is a path (C1.21). A bare name that is not an input of the node is whatever Rust finds there, with no word. No expression is awaited. `read` and `idempotent` run inside a closure that is not `async` and does not return a `Result`, so `.await` does not compile there, nor `?` in `idempotent`; `?` in `read` is not promised either way ([when an expression runs](grammar.md#when-an-expression-runs)). **`return` is allowed** in an expression that stands in a closure. In `read { … }`, `idempotent { … }` and a pager it gives the value of that expression, of the type the author would write there, and the macro adapts that value outside the closure. In a status arm and in `body`, where `?` works, it gives what `?` would give: `return Ok(17)`, `return Err(…)`. **The author's expression sees only the names that this page gives it** (the inputs, the owners, and in an arm `body`, `headers` and `status`): every local of the generated code has mixed-site hygiene, so the expression cannot read it, change it or collide with it. A `const` or a `static` of the author's module is read by Rust as a pattern in a `let` of the same name (E0530), and hygiene does not prevent it: so the author declares no item whose name begins with `__` in the module of `api!`, and none with the name of an input in reach of it. What `read` gives goes through a hidden helper that carries the type that is read, so that Rust finds the type of a problem, and `?` cannot be used on it. `?` in `paginate` or `idle_timeout` is refused by `rustc` too. `?` in an entry or a `body` ends the call with a Build error whose `source()` is the failure: the expression runs in a closure that gives `Result<_, Box<dyn Error + Send + Sync>>`. `?` in an arm ends it with the API's problem or a Mismatch (C5.8). When each one runs, and in which order for a send, is C10.3 ([when an expression runs](grammar.md#when-an-expression-runs)). A crate that holds a description needs `concord` and `serde` among its dependencies, and nothing else of Concord's. |
| C1.17 | **Parts.** `part name(inputs) { statements }` stands in the block of the client. Its signature names no other part. It may hold a `base` (the input that goes in the host, with the line that places it); it holds no `path`, no `problem`, no `middleware` and no child. A scope or an endpoint names parts at the end of its inputs: `..a, ..b`. It then has the inputs of each part after its own, in the order written, and the statements of each part before its own, as if it had written them. So inside one node a key (an entry, an arm) or a statement that holds one value (`base`, `read`, `body`, `paginate`, `idempotent`, `idle_timeout`) is written once: written by a part and again by the node, or by two parts of one node, it is a compile error. One exception: bodies made of entries (C1.21) in the parts that a node names and in the node itself are put together, the parts' entries first (in the order in which the node names the parts), when all call the same function, written the same way (a path, so the same spelling is the same function: C1.21); another function, the other form of `body`, or a key that two of them write is a compile error. An entry or an arm of a part may say `override` or `remove`: it is checked where the part is named, as if written there. `override` is for a key from a level above, not for a part (C1.13). A part that holds `body`, `paginate` or `idempotent` cannot be named by a scope. Inside a part, a bare name is an input of the part, and `client.x` an input of the client, and nothing else; in the node, an input of the part is an input of the node. A name after `..` that is no part, a part that no node names, an input of a part with the name of an input of the node, a part named twice by one node (`..page, ..page`), and two parts with one name are compile errors. The `///` of a part is for the author and goes nowhere; the `///` of its inputs go to every node that names it. A part generates nothing by itself (the macro, [The steps](../internals/macro.md#the-steps) and [What is written](../internals/macro.md#what-is-written)). |
| C1.18 | The macro refuses with the compile-time messages of [the messages](messages.md), each at the place that the page gives. All the mistakes of one build are shown together, and the macro still writes every item that is sound (the macro, [The steps](../internals/macro.md#the-steps) and [Where a message points](../internals/macro.md#where-a-message-points)). Below a node, a block or an arm that an earlier step marked as damaged or refused, no message is raised whose truth depends on what was dropped. A help line never leads to another message (the messages, [3. Three rules for every message](messages.md#3-three-rules-for-every-message)). |
| C1.19 | **`middleware m;`** stands on the client only: in a part, or anywhere else, it is a compile error. It may be written several times. `m` is a Rust expression, copied as written, that gives a value with `concord::Middleware` (C9.6). It is evaluated once, in `new`, in the order written. It sees the required inputs of the client, as references, bare or as `client.x`, and nothing else: an optional input of the client named in it is refused by the macro. `new` cannot fail, so `?` in it is refused by `rustc`; what can fail is done in `handle`. No node below and no caller takes a middleware away. A `///` above `middleware` goes to the page of the client; the text of the expression is never printed (it could hold a literal key). The order of the middlewares is C3.4. |
| C1.20 | **The grammar of [grammar.md](grammar.md) is exact**, with what the grammar alone cannot say: a template is read after Rust has decoded the string, and a raw string is a template too. A hole holds a reference (a name, or an owner, a `.` and a name) and nothing else: no space, no comment. As the value of an entry, a bare string literal is a template, and anything else is an expression. The client and a part take inputs and no `..name`; a scope and an endpoint take inputs, then parts. |
| C1.21 | **A body made of entries:** `body f { entries }`. **`f` is a path to a function, seen from where `api!` stands** (`json`, `form`, a function of the author's): an input of the same name does not hide it, so the same spelling in a part and in the node is the same function. An entry is as in `query`, `name;` or `"key" = value;`. A body inherits nothing from a level above, so `override` and `remove` there have no target: a compile error. The entries are one value of the core (C2.14), and `body f { … }` is `body f(entries)`: any function that takes something that `serde` can write fits, and the macro still knows no format. A part may hold `body f { … }`; the node that names it writes `body f { … }` with the same `f`, or no body. Another function, or the other form of `body`, is a body written twice: a compile error. A `Secret` may be an entry, short or as a value (`body form { grant_type; client_id; client_secret; }`): C2.14. |
| C1.22 | **`idle_timeout <expression>;`** stands on the client, a part, a scope or an endpoint; the nearest one is used. The expression is Rust with the inputs as variables, and gives a `std::time::Duration`: the clock for silence of the calls below (C7.6 for its order with the caller's settings). |

## C2. Building a request

| # | Contract |
|---|---|
| C2.1 | `base "…";` is `http://` or `https://`, a host, maybe a port, and maybe a path prefix whose segments are held to C1.15: no user, no query, no fragment. A hole in the host gives a label, or a piece of one (`"https://api-{label}.example"`); the finished label is checked: 1 to 63 characters, ASCII letters, digits and `-`, not at the ends. A name that is not ASCII is refused: an international name is given in its ASCII form. An empty value in a host hole is the Build error of a host hole (`input <name> is not one label of a host`); an empty value in a port hole is the Build error of the base. A hole after `:` gives the port: digits. After the URL is parsed, the host must be the host that was written, each label compared without case; a number that a parser reads as an address is refused. Anything else is a Build error. |
| C2.2 | `base x;` takes one input of the type `concord::Base`. A `Base` is parsed from text: a scheme, a host, maybe a port, and maybe a path prefix. No user, no query, no fragment. **A `Base` is taken only when the URL library gives back what was written, piece by piece:** the scheme, case aside; the host as the library reads a host on its own (upper case, a longer spelling of an IPv6 address, an international name are the same host); the port, or none when the default one was written; the path once both are decoded (an empty path is the root: a bare host, `https://api.example.com`, is a legal base). Any other difference is refused. So what the library would change with no word is never sent: a `\`, a control character, a user found in what looked like a path, a dot piece. A trailing `/` of a base is kept only when no `path` follows it (C2.3): the URL ends with `/` when the last piece on the way down does. Each segment of the prefix is held to C1.15 and is decoded once. The prefix comes first in the path. `with_base(…)` takes the same text; a text that is not a `Base` makes the next send a Build error, `the base is not a URL that can be used (with_base)`. |
| C2.3 | The path is the prefix of the base, then the pieces of every `path`, root first, joined with one `/`. **The URL ends with `/` when the last piece on the way down does:** the last `path`, or the `base` when no `path` follows. Fixed text is sent as written (a parser may encode a character of it). The value of a `{x}` hole is percent-encoded: every byte outside `A-Z a-z 0-9 - . _ ~` becomes `%XX` with upper-case hex digits (`%2F`), `%` too, so that it cannot add a `/`, a `?` or a `#`. It is a Build error when it is empty. A finished segment that is `.` or `..` is a Build error: `v{x}` with `x = ".."` gives `v..`, which is sent. A `{*x}` hole is cut at each `/`, and each piece is encoded and is a segment. **A piece of `{*x}` may be empty:** a final `/` and `//` are sent as they are. Its whole value may not be empty, and a piece that is `.` or `..` is a Build error. The built URL has as many segments as were written, or it is a Build error. |
| C2.4 | **The text of a value.** A value in a path, a host, a query, a header or a template is written by `serde`, with a serializer of Concord that knows three shapes. *Nothing:* `None`, the unit. *One text:* a string, a `char`, a `bool` (`true`, `false`), a number (a float that is not finite is a Build error; a float is written as `serde_json` writes a number: the shortest text that reads back the same, with `.0` for a whole number, `1.0`), a variant with no data (its `serde` name), a newtype or a `Some` around one of these. *Several:* a sequence or a tuple of texts. Any other shape (a map, a struct, a variant with data, bytes, a list inside a list) is a Build error. So is a value nested more than 128 levels deep, at every place and in a body of entries (`input <name> cannot be written in a <place>`): no input can overflow the stack while it is written. **`Secret` has no `Serialize`**, so `json(x)` of a type that holds one does not compile: `body json(task)` with a secret field is refused. The generated code passes every value that it places through one adapter of the hidden module, which knows `Secret` and `Option<Secret>`, and references to them, before it asks for `Serialize`; an optional input `key?: Option<Secret>` can be placed too. The entries of a body go through the same adapter, so a `Secret` there is written as its text, as in a query (C2.14). With a template that has a `Secret` in a hole, these are the only shapes of a value that holds a `Secret`: a list of secrets does not compile. |
| C2.5 | Where each shape may go. A value that is a whole entry of a query or of headers: nothing (the entry is not sent), one, several. A whole entry of a body is C2.14. A hole in a template of an entry, of a query, of headers or of a body: one; nothing makes the entry not sent (C2.8), and an empty list is nothing; several is a Build error. A hole in a path or in a host: one; nothing or several is a Build error. |
| C2.6 | Query pairs are in the order of the declaration, root first; the items of a list in their order. Keys and values are percent-encoded: every byte outside `A–Z a–z 0–9 - . _ ~` becomes `%XX`, with upper-case hex digits. A request with no query pair has no `?`. An empty text as a value writes `k=`. An `override` keeps the place of the pair or pairs it replaces. |
| C2.7 | A header name is checked at compile time and sent in lower case. `host` cannot be a key of `headers`: the host is the `base`. A short entry (`name;`) in `headers` whose name has `_` is refused: write `"user-agent" = user_agent;`. (In `query` the short entry is unchanged.) A header value is never percent-encoded. A value may hold the bytes 0x20 to 0x7E and a tab: a space is legal (`Bearer {token}`). Another control character (a line break) or a byte over 0x7E is a Build error, unless a level below replaces or removes that header. `Draft::header` is given the name as written, and compares and stores it without case. A list sends one field line for each item. A header whose value holds a `Secret` (what `basic` gives is one) is marked sensitive. **The label of a body is a header value:** the label of `Body::new(bytes, label)` or of `Body::stream(…).content_type(label)` is written as `content-type`, under the same rule; one that is not legal is the Build error of that header, `the value of header content-type is not a legal header value`. |
| C2.8 | A template that reads a `None` makes its entry not sent; every hole of the template is checked before the entry is left out. An `override` whose value is `None` makes the key not sent. A `content-type` entry whose value is `None` sends nothing, and the body's own label is then written. |
| C2.9 | `body <expression>;`. The expression is evaluated when the request is built, with the inputs in scope as references. It gives a `concord::Body`, a `&Body` (it is cloned), or a `Result` of one of these whose error is any error that `Box<dyn Error + Send + Sync>` takes: an `Err` is a Build error with that error as its `source()`. `request(&self)` never spends the call: on a call whose body holds a one-shot stream it is a Build error, and no part of the body is touched (C2.15). `into_request(self)` gives the request and takes the stream with it. A `Body` is bytes or a stream, or a body made of bodies (C2.15), with maybe a content type. The content type is written to the request unless a `content-type` entry in reach gives a value (C2.8). `json(x)` writes with `serde_json` and says `application/json`; `form(x)` writes with `serde_urlencoded` and says `application/x-www-form-urlencoded`. `multipart()` (feature `multipart`) builds a multipart body: `body multipart().text("chat_id", id).file("photo", "a.jpg", "image/jpeg", photo).finish();` (C2.16). The other form of `body` is C1.21. |
| C2.10 | `with_base(x)` replaces the whole base: the scheme, the host, the port and the path prefix of the `base` line. The `path` lines stay. |
| C2.11 | A Build error always means that nothing was sent. **A URL that cannot be sent is a Build error:** a URL longer than 65,534 bytes, the most the HTTP layer can hold, counted once the path and the query are encoded (C2.3, C2.6) and after `at_url` and the edits of `edit_request`, is `build error: the URL is too long to be sent`, before any middleware sees the request, with zero tries. |
| C2.12 | **A `content-length` that the description writes** (`"content-length" = size;`). For a body in memory it must be the length of the body, or the request is a Build error. For a stream, which has no length of its own, it is sent as written; if the stream is longer or shorter, what happens is the HTTP library's and the server's affair. |
| C2.13 | **A Build error names its value.** Each value that the generated code gives to the request comes with a name, `Piece::Val("region", &value)`: for a hole and for a `name;` entry, the input (`region`, `client.tenant`); for an entry written `"key" = value;`, the key, also when the value is a bare input. The words are always `input <name>` (the engine, [How a value is written](../internals/engine.md#how-a-value-is-written)). An entry of `query` or `headers` whose expression fails prints `input <name> could not be written`, with the author's error as `source()`; only a `body` prints `the body could not be written`. |
| C2.14 | **`concord::body::Entries`**, the value of a body made of entries (C1.21), is written by `serde` as a map, in the order written: any `serde` writer sees a plain map, with no wrapper and no hidden name. **A `None` writes nothing**, as in a query and in headers: one level of `Option` is presence, and what is inside is written as the format writes it. So `x;` with `x?: T` or `x: Option<T>` writes no key, or the value. `milestone;` with `milestone?: Option<u64>` writes no key, `null` or a number (in JSON). `"k" = value;` whose value is an `Option` (`"x" = client.x;`, `"ids" = ids.as_ref().map(join);`) writes no key when it is `None`. `"k" = Some(x);` with `x: Option<T>` writes `null`, or the value: it is the way to write a `None` as `null`. **A form has no `null`:** there an inner `None` writes no pair either, and a list or a struct as a value is a Build error (`the body could not be written`). The macro knows no type for this: `Entries` asks `serde` whether a value is a `None`, when the body is written. So a value is asked twice, whether it is a `None` and then to be written, and its `Serialize` must give the same both times. A `Secret`, short or as a value, is written as its text, through the adapter that writes it in a query (C2.4). A template as a value (`"note" = "by {name}";`) is as in `query`: its text is written, a hole that reads nothing leaves the entry out, and a hole that reads several is a Build error (C2.5). The unit (`()`) is not a `None`: in a body it is written as the format writes it (`null` in JSON; a form cannot write it, which is a Build error, `the body could not be written`); in a query and a header it writes nothing (C2.4). |
| C2.15 | **A body made of bodies: `Body::concat(parts)`**, in the core, joins bodies in order. A one-shot stream inside is taken with the whole, when the request is built for a send (before the middlewares). So a stream that was already sent is a Build error before anything goes out, also inside a `multipart` body. One-shot is a property of a `Body`, a value: a clone of a call shares the stream of an input, and the first send takes it; a second send of that same `Body`, through a clone or by the next page of a paged call, is that Build error (`the body is a stream that was already sent`), and nothing is sent. An expression that makes a new stream each time it runs (`body fresh();`) gives each send its own. `request()` refuses a body that holds a one-shot stream without touching a part. `Body::as_bytes()` and `Body::into_stream()` are public: a writer of the author's needs them, as `multipart` does. |
| C2.16 | **`multipart`** (`concord-extras`, feature `multipart`): `multipart().text(name, value).file(name, file_name, content_type, body).finish()`. `text` and `file` give the builder back. `finish()` gives a `Result` of a `Body`: a content type that is not a legal header value is its error, and so is a field name or a file name that holds a control character (a NUL, a CR, a LF, a tab); nothing panics. A `"` in a name is written `%22`, and nothing else is changed: a `%` is written as it is, as browsers do (WHATWG, "multipart/form-data encoding algorithm"). So two names can be written the same: `"` and `%22`. Concord does not check that the names of one body differ. **The boundary is not random when every part is in memory:** it is the first of a fixed list that no part holds, so the same inputs give the same bytes (G6 of [what Concord promises](../guide/promises.md), and "the same request" of pages, C8.4). With a part that is a stream, the boundary is random (128 bits): such a body goes out once anyway. |

| # | Contract |
|---|---|
| C3.1 | The request is built once (C2). `.edit_request(f)` runs once on each request that is built: once for a call, once for each page (C8.4). `f` is `Fn(&mut reqwest::Request) + Send + Sync + 'static` and cannot fail. | C3.3 | **After `blocked`.** A middleware or a transport that will not send gives `TransportError::blocked()`: no other try is made, and the result is the blocked error (a Transport error of the class `blocked`). |
| C3.4 | **The way out.** The copy goes first through the middlewares that a caller added (`with_middleware`), then through those of the description, in the order written, then to the transport, with its `TryInfo` (C9.5, C9.6). | C3.6 | Retry looks at the outcome (C4). A value, a Mismatch and a Build error are final. For `send_raw()`, a head below `400` is final, like a value; a head of `400` or above is looked at by the policy, as a refusal is. |
| C3.7 | not used |
| C3.8 | One loop of the hidden module of the core runs the tries (C3.2 to C3.6, C4) around a function that the generated code gives it for the rest of a try (the engine, [The tries](../internals/engine.md#the-tries)). `__private::exchange` (a send) and `__private::exchange_raw` (`send_raw()`) both use it, and differ only in how a try reads its answer. |

## C4. Retry

| # | Contract |
|---|---|
| C4.1 | **Three conditions**, all needed for another try. *It can be sent again:* C3.2 gives a copy whose body is bytes. *It may be repeated*, in one of three ways: by its mark, when the endpoint says `idempotent <expression>;` and it gives `true` for this call (`idempotent;` alone is `true`; the expression runs once for a send); by its method, when the endpoint has no `idempotent` and the method of the request as it was built (after `.edit_request(…)`, before any middleware) is `GET`, `HEAD`, `OPTIONS`, `PUT` or `DELETE`; or by its status, when the outcome is a refusal (kind Refused) whose status the policy lists with `not_applied_on(status)` (a `429` on a `POST` that is not marked: `idempotent;` would also send it again after a lost connection). A body that broke, or a clock that ended, after a head with that status does not open this gate. `not_applied_on(n)` never panics: a number outside 100 to 999 is kept and matches no answer. A `POST` that is not marked is not sent again after a connection that failed: its caller gets the error (`e.class()` says Connect) and decides. *The failure is worth it:* no rule of `unless` says no, and C4.2 or a rule of `when` says yes (C4.7). The order of the checks is in the engine, [The decision to try again](../internals/engine.md#the-decision-to-try-again). |
| C4.2 | `Retry::standard()`: at most 3 tries; `tries(n)` is held to at least 1, which means no other try. Outcomes it names: a Transport error of class connect, timeout or body; `408`, `429`, `502`, `503`, `504`. |
| C4.3 | **The waits are fixed.** Before try `n+1`, a random time up to `2^(n−1)` seconds: up to 1 second, then 2, then 4; never more than 60 seconds. A wait is never less than a `Retry-After`, nor than what a rule of `when` asked (C4.7). A `Retry-After`, or an asked wait, over 60 seconds means no other try: the error is the result, and `e.retry_after()` says how long. **`e.retry_after()` gives the longer of two waits:** the `Retry-After` of the answer, and the wait that a rule of `when` asked for the try that did not happen. No rule is asked twice: the decision gives what was asked together with its verdict. A wait that would not end before the `timeout` of the call also means no other try. A wait has one deadline, taken once: past the end of `timeout`, the wait is not started; if the clock still cuts a wait that was started, the caller gets the last outcome, unchanged, and not a timeout. `Retry-After` is read as seconds or as a date, by Concord itself: the three forms of RFC 9110, section 5.6.7, and a year of two digits by its rule of fifty years. A value that is neither a number of seconds nor an HTTP date is taken as absent. A date in the past is a wait of zero. A date is compared with the clock of the machine; one more than 60 seconds ahead means no other try, in whatever year. |
| C4.4 | When the tries run out, the last outcome is the result, unchanged. `tries()` on the error says how many tries the engine handed to the middlewares: a try is counted when it is handed over, so a timeout before any head counts that try. What happens below that is not counted: what a middleware sends again with `next.send` inside one try, what a transport sends on its own, and what the HTTP library sends again (`reqwest`'s own resend of a stream that the server refused before processing it). |
| C4.5 | The answer of a try that is given up is dropped before the next one is sent. |
| C4.6 | `.with_retry(…)` on a call replaces the whole policy of the client for that call, `tries` and rules: that is the caller's own word. An author ships the policy of the API (`slack::retry()`, with its `not_applied_on`), and a caller keeps it by passing it on: `with_retry(slack::retry().when(mine))`. |
| C4.7 | `Retry<E>::when(f)`, with `f: Fn(&Tried<E>) -> Option<Duration>`, and `Retry<E>::unless(f)`, with `f: Fn(&Tried<E>) -> bool`. **Rules add up inside one policy:** every `unless` is asked, and the `when` rules are asked in the order they were added; the first that gives a wait wins, and the rules after it are not asked. A rule is asked only when another try is still possible: after C3.6, the number of tries, the copy of C3.2 and the gate of C4.1; the `unless` rules first. `Tried` gives the status, the headers, the class, the number of the try, and `problem()`. With a rule set, the body of a refusal (at most 64 KiB) is read and `problem()` is tried before the rule is asked. An `unless` that gives `true`: no other try. A `when` that gives `Some(wait)`: another try, after at least `wait` (C4.3). No `when` gives a wait: C4.2 decides. For `send_raw()` the try ends at the head, and only a head of `400` or above is looked at (C3.6): a rule gets the status and the headers, `problem()` is `None`, and nothing of the body is read. A failure of class blocked is never tried again (C3.3). |

## C5. The answer

| # | Contract |
|---|---|
| C5.1 | The status picks the arm before any byte of the body is read. An exact status wins over a class (for an inherited class arm, C1.13). |
| C5.2 | **Arms add.** The arms in reach are the ones written at the node and above, and in the parts that they name. A status that none of them takes: a 2xx is the body, read into the type after the arrow (with an arrow), or `()` (without); anything else is a Refused error. **An `Option<T>` or a `Result<T, E>` after the arrow** (C1.7): a 2xx that no arm takes is read as `T`, and given as `Some` or as `Ok`; the arms give the rest (`404 => None`, `409 { body } => Err(body)`). A body of no bytes is the reader's affair: `Text` gives an empty text, `Binary` no bytes, and `Json` a Mismatch, so a `204` under `-> T` with `read Json` needs an arm (`204 => None`). **A `HEAD` with an arrow** writes its arm for a 2xx (an exact status or the class): there is nothing to read. A 2xx that no arm takes is then a Mismatch: the hidden helper `no_arm(response, &info)` makes it, and keeps the evidence (the status, the headers, at most 64 KiB) as a refusal does. **An endpoint with no arrow that an arm in reach would read does not compile:** it gets an arrow (`-> Ignored`, a type of the author's that reads anything), or it removes the arm. |
| C5.3 | **An arm binds what it uses:** `key => EXPR` or `key { fields } => EXPR`. The fields are `body`, `headers` and `status`, each at most once, each with another name if wanted (`body: task`). A field that is not named is not there. `body` is the body, owned, read by the reader in reach before `EXPR` runs; its type is found by Rust from the arm. When Rust cannot find it, the arm says it: `4xx { body } => { let odd: UploadError = body; Err(odd.into())? }`. Naming `body` is what reads it: no word inside `EXPR` starts a read. `headers` is a `&concord::Headers`, `status` an `http::StatusCode`. `EXPR` runs as `Ok({ EXPR })` in a function that gives `Result<A, concord::Fail<E>>`. A field that is not one of the three is a compile error. **On a status that is not a 2xx, an arm's `body` that does not read gives a Refused error**, with the status, the headers and the bytes kept; `problem()` is `None`. (A Mismatch stays for a 2xx whose body does not read, and for `mismatch(…)` and `require(…)` in an arm.) For a `HEAD`, the edits (`override`, `remove`) are resolved first; then an inherited arm that binds `body` is left out, and an arm of its own that binds `body` (also one of a part that it names) is a compile error. Its arrow is C5.2. **An inherited arm that takes a 2xx and binds `body` does not reach an endpoint whose arrow is spelled `Option<T>` or `Result<T, E>`:** a compile error at the arrow, until the endpoint writes that arm itself (`override`) or removes it. The order is: the edits, then for a `HEAD` the leaving out, then this check on what is left; so a `HEAD` never meets it. (Under such an arm Rust would find `Option<T>` as the type of what is read, and a `null` would be a `None` with no word: the hole that C5.2 closes for the simple rule.) (the macro, [A name of the author, in the author's Rust](../internals/macro.md#a-name-of-the-author-in-the-authors-rust)) |
| C5.4 | Reading a body whole: an announced size over the limit is a Mismatch before anything is read. **The announced size** is the `Content-Length` header of the answer when it has one, else what the transport says of the size of the body; this holds for a `fake`, a `tower` service and a middleware that replays an answer. It is used only inside the reader's limit, and it never decides how much memory is reserved at once: the engine never reserves more than what has arrived, doubled, with a floor of 64 KiB, however large the limit. When the announced size is inside the limit, it is the ceiling of the buffer: an honest body of 100 MiB ends in a buffer of 100 MiB, not 128. An allocation that fails is a Transport error of class body, never an abort. Bytes are counted as the transport gives them (`concord::Http` does not decompress unless its closure turns that on: C7.1). A chunk that would pass the limit is not kept. A body that breaks, or ends before its announced size, is a Transport error that keeps the status and the headers; it is never a shorter value. |
| C5.5 | A body that no arm names is not wanted. It is dropped, and nothing that happens to it changes the result. |
| C5.6 | **Everything that an error keeps from an answer is bounded:** a Refused error and a Mismatch keep up to 64 KiB of the body, in a buffer of their own, and up to 1 KiB of a reader's own message (C6.3), its mark included: the kept text and ` … [cut]` are 1024 bytes or less, and a text that was already cut is not cut again. The cut at 1 KiB bounds the memory too, also for a short text in a large allocation. `kept()` says complete, cut or interrupted, and is `None` when no byte of a body was kept (an announced size over the limit). For a Refused error from a status, `problem()` is tried from a complete body, into `E`, by the reader of the `problem` line: the `read` of the client node, or the one named after `read` on that line (C5.11). When it does not decode, it is `None`. This never makes another error. It is not tried for a Mismatch: a body is never read to see what it is. With no `problem` line there is no problem type, and `problem()` is always `None`. |
| C5.7 | A failure that is known stays: a Refused error whose body then breaks, or never ends, is still that Refused error. |
| C5.8 | `?` in an arm, on the API's error type, gives a Refused error with that problem and the status of the answer (it can be 200). It keeps the typed problem and no bytes. `concord::mismatch(text)` gives a `concord::Fail<E>`, and so does `headers.require(name)` when the header is missing; returned as the `Err` of an arm or of a pager, it ends the call with a Mismatch whose `reason()` is the text. |
| C5.9 | `send_full()` takes the same path as `send()` and keeps the head. |
| C5.10 | `read Stream`: a success ends the try at the head. The status rule runs on the head, then the body is handed over unread. A refusal is read like any refusal (64 KiB, the problem type). What fails later is a `concord::read::StreamError` from `try_next()`: its kind is Transport, with the status, the headers, the endpoint and the tries; with `?` it becomes any `concord::Error<P>`, and a `ReadError`. A `ByteStream` may read ahead of what the caller asked for. |
| C5.11 | A reader is a value with the trait `concord::Reader<T>`; `read` takes a Rust expression, copied as written. **The core has none, and there is no default:** an endpoint in which a body is read (by the rule of C5.2, or by an arm that binds `body`) needs a `read` in reach, or it is a compile error at what reads. `HEAD exists() -> bool { status { 2xx => true, 404 => false } }` needs none. `problem E;` is read by the `read` of the client node, or by the expression after `read` on its line (`problem E read Xml;`); with neither, a compile error. The shipped readers are in `concord-extras`: `Json` (10 MiB; `.limit(n)`; it reads a 2xx whatever its label says, and `.strict()` refuses a label that is not `application/json` or `…+json`, before reading; it skips a UTF-8 byte order mark, gives the place where the body stopped fitting, with the crate `serde_path_to_error`, and says when the label was not JSON), `Text` (UTF-8; other bytes are a Mismatch; 10 MiB), `Binary` (10 MiB), `Stream` (no limit). `Incoming` gives the status and the headers. A reader that fails gives `ReadError::not_the_type(body)`, then, since the core has no format, what it knows: `.at(place)`, the place, a `concord::read::Place` made of pieces: `Place::root().field("items").index(3).field("kind")` (a `field` takes a `&'static str`, a name of the program and never text of the answer; `.key()` for a key of a map, printed `[key]`; `.variant()` for a tag of an enum that was read, printed `[variant]`; 32 pieces at most); `.with_details(text)`, its own message, which Concord cuts at 1 KiB; and `.label_was_not_expected()`. The place and the label are printed (C6.2); the details are behind `details()` (C6.3). **A reader hands Concord no cause of its own:** the `source()` of the Mismatch is made by Concord from the place and the kind, and a reader gives no free text that is printed (the place is pieces; the details are behind `details()`), so no reader, shipped or the author's, can put a value of the answer there. Its `reason()` is `None`. `Json` gives the place where `serde` gives one (not through a flattened or a tagged enum). |
| C5.12 | **`send_if_none_match(etag)`**, on a call whose method is `GET` or `HEAD`, takes a `&str` and is awaited like `send()`. It writes `If-None-Match` when the request is built, in place of any that the description wrote, and before the edits of `edit_request`. It gives an `Answer<Option<T>>`. On a `304` that no arm takes, the value is `None`, and the headers are there (a new `ETag`, `Cache-Control`). Any other answer is read as by `send_full()`, and its value is `Some`. |

## C7. Concord's own client, and the clocks

| # | Contract |
|---|---|
| C7.1 | **`concord::Http`** is Concord's own HTTP client and the default transport: a `reqwest::Client` in a type of its own. `Http::with(f)` sets 30 seconds to connect and no `Referer`, then runs `f` on `reqwest`'s builder, then sets one thing that `f` cannot change: no redirect is followed (a `3xx` is the answer). `Http::new()` is `Http::with(\|b\| b)`; both give a `Result` with `reqwest`'s error. By default it does not decompress (a body is given as it came) and keeps no cookies: a caller whose build of `reqwest` has them may turn either on in `f`. With decompression on, a reader gets, and its limit counts, the bytes that the transport gives. It reads the proxy settings of the environment, as `reqwest` does. `reqwest`'s own resend (a stream that the server refused before processing it) is left as `reqwest` has it, below what Concord counts (C4.4). (the crates, [Concord's own HTTP client](crates.md#concords-own-http-client)) |
| C7.2 | not used |
| C7.3 | The default transport, a `concord::Http`, is made at the first send of a client that was given none, once, in a cell that all its clones share. If it cannot be made, that send is a Build error. `Name::new(…)` never fails. |
| C7.4 | not used |
| C7.5 | `concord::Http` follows no redirect (C7.1). For a client of the user that does: the method and the body of a followed request are `reqwest`'s affair, and no middleware sees it. |
| C7.6 | **Two clocks.** `idle_timeout` (30 seconds) and `timeout` (none); neither changes the other. `timeout` comes from the call, or else from the client. *Timeout* starts when the call is sent, before the request is built (each page: C8.5), and bounds everything: building, the middlewares, each try, each wait between tries, the reading of the body, and a `ByteStream` that was handed over, until its end. No request is handed to the transport after it has ended. *Idle*, the clock for silence, watches two things and nothing else: **the transport, from the moment it gets the request until the head of the answer** (each piece of a stream body going out starts it again); and **a body while it is read** (each piece starts it again). A body held in memory goes out in one piece. A middleware's time, before or after the transport, and a reader's own waits are never silence: only `timeout` bounds them; a middleware that waits with no `timeout` set may wait for ever, and that is its author's affair. So there is no shared instant for a whole try: one timer around the `send` of the transport, and one around each wait for a piece. The idle clock of a `ByteStream` runs while a `try_next()` waits, not between two of them. Through `impl Stream for ByteStream` it runs from the first poll that found nothing until the next piece, also between two polls: a dropped `next()` cannot be seen. After `send_raw()`, neither clock follows the answer. **The length of the clock for silence** of a call: `with_idle_timeout` on the call, then the nearest `idle_timeout` of the description (C1.22), then `with_idle_timeout` on the client, then 30 seconds. **A clock ends a wait, and nothing else:** work that can finish without waiting finishes, and code that does not yield is not interrupted. The engine drops what it waits for when a clock ends. When one ends: a Transport error of class timeout, whose note names the clock, what it waited for (an answer, or a body after its status) and where its length is set (the messages, [2. When a request is built or answered](messages.md#2-when-a-request-is-built-or-answered)). **An outcome that is already known is never lost to a clock:** a refusal (C5.7), and the Mismatch of `no_arm` (C5.2). `refused` writes the status, the headers and each piece of the body into the `Run` as they come; when a clock ends the try, the outcome is that error, with `kept()` saying interrupted; if none was known, the Timeout error. (the engine, [The two clocks](../internals/engine.md#the-two-clocks)) |
| C7.7 | **A drop.** When a call on its way is dropped, Concord stops, and starts no other try. What the HTTP library does with the connection is its own. (the engine, [A drop](../internals/engine.md#a-drop)) |

## C8. Secrets and pages

| # | Contract |
|---|---|
| C8.1 | not used |
| C8.2 | **A credential that is a value.** There is no `auth` statement and no trait for it. An entry of `headers`, of `query` or of a body made of entries whose value holds a `Secret` (one of the shapes of C2.4) writes that text; in a header, the value is marked sensitive. `basic(user, pass)` of `concord-extras` gives a `Secret`: `Basic`, a space, and `user:pass` as UTF-8 in base 64 with padding, with the text as given. A value that is not a legal header value is a Build error. As an argument, a `Secret` input also takes text: a `&str` or a `String`. A `Secret` in a path or in a host is part of the URL: Concord prints no URL, and what a proxy logs is outside. When a call is sent to a next URL (C8.6), each pair of the query whose value holds a `Secret` is written on that URL: every pair of that key already there is taken out first. No other pair is added. |
| C8.3 | A `Secret` holds its text behind a shared cell. `expose()` gives the text as it is at that moment, as a value that reads as `&str` and keeps that text alive while it is held. `replace(text)` changes what every clone gives from then on; a text that was already exposed does not change, and is freed when its last holder is gone. A request reads a secret once, when it is built: a later try sends what the first one sent. A middleware reads what it wants at each try. |
| C8.4 | **Pages.** `.pages()` gives a `Pages`; nothing is sent before the first `try_next()`. **The request of each page is built when that page is asked for**, so a `Secret` replaced between two pages is used. After a page, the pager is called with a clone of the call and with the `Answer<T>`, and gives `Some(next)`, `None`, or an `Err(concord::Fail<E>)`, before the page is given to the caller. **Every page of one `.pages()` goes to the origin of its first request,** as that request was finished (after `.edit_request(…)`), whatever the pager did: another origin is a Build error. (An edit that moves every request to another host is its author's word: the first page goes there, and the pages stay there. With a pager that uses `at_url` it does not go together: C8.6.) **The same request twice is a Mismatch:** a request is the one that was just sent when it has the same method, the same URL without its fragment, the same values of each header, in their order, and the same bytes of the body, **with what a secret wrote in the URL or in a header left out**: a piece of a path, a pair of the query, a value of a header. A body is compared as its bytes, so a secret that is an entry of a body, replaced between two pages, looks like a move, once. (An API that pages by a header moves; a key that was replaced, also a token in the path, does not look like a move.) What marks a value of a header is the flag that Concord itself sets (`sensitive`, C2.7): a value that `edit_request` marks is left out too (C3.1). Both checks look at the request as it was built (after `.edit_request(…)`, before any middleware): what a middleware changes is its author's affair. A paged call whose body is one `Body` that is a one-shot stream (an input) fails at its second page, with a Build error; a body that the description makes new for each send (C2.15) gives each page its own, and a request whose body is a stream is never "the same request" (a stream has no bytes to compare). A secret in a host that was replaced between two pages is another origin: that check comes first, and the pages end with its Build error. After an `edit_request` that changed the URL, the pieces that a secret wrote are no longer known, and the URL is compared as it is. The request of a page is built once, and that same request is sent (C10.10). A page and its items are `Send`. The page that arrived is always given first. What was found about the next one comes with the following `try_next()`: the next page, `None`, or the error. `try_next()` gives `Ok(Some(page))`, `Ok(None)` at the end, or the error. **After an error the pages are over:** every later `try_next()` gives `Ok(None)`, and the stream has ended. A pager that fails with the API's problem type gives a Refused error with that problem and the status of the page that came (`refused: status 200, in tasks.list`); one that fails with `concord::mismatch(…)` gives a Mismatch. (the engine, [Pages](../internals/engine.md#pages)) |
| C8.5 | `Pages` holds the exchange that is in flight; `try_next()` and the `Stream` implementation poll the same state. A `try_next()` that is dropped does not cancel it and does not lose it: the next `try_next()` goes on with the same one. Nothing is sent twice, and no page is skipped. Each page is one call, with the call's retry policy and its two clocks. The `timeout` of every page starts when the page is asked for, and covers the building of its request. The time between two pages is not counted, and nothing bounds the whole loop. |
| C8.6 | **A pager is an expression, copied as written.** In it, each input of the endpoint is bound with `let` to a value that is `Copy` and has no size, with `concord::page::Slot<Call>`: the place of that input (`get` on a call, `set` giving the call changed). The macro writes one such type for each input of an endpoint that has `paginate`. A pager is `Send + 'static` and owns what it holds, so a pager written in place as a closure is a `move` closure. Every call has `concord::page::Call`: its `Value`, its `Problem`, and `at_url(url)`, the same call sent to that URL. **`at_url` gives a path and a query, never an origin:** they replace the ones of the description (C8.2 for a secret pair). A URL at another origin than the one that the call builds (its `base`, or `with_base`) is a Build error, in pages and outside them; it is checked when the request is built, before the edits of `edit_request`. A fragment (`#…`) is dropped from a next URL before it is compared. A relative URL is resolved against the URL of the answer that gave it (an `Answer` keeps that URL, hidden; an answer with no URL of its own, as a transport of the caller, a `fake` or a `tower` service makes it from an `http::Response`, is taken to come from the URL of its request); with no answer (a caller's own `call.at_url("../next")`), against the URL that the call builds. A URL that does not parse is a Build error when the call is sent: `the next URL is not a URL`. An `edit_request` that moves the host does not go together with a pager that uses `at_url`; use `with_base` to move the client. The shipped pagers are functions of `concord-extras`, each named for what it follows. `by_offset(a)`: `n` is the number of items of the page (`IntoItems::count`, C8.7); `n = 0` ends; else the next call has `a = a.unwrap_or_default() + n`; an `n` that the type of `a` cannot hold is a Mismatch. `by_offset_limit(a, c)`: also ends when `c` is `Some(k)` and `n < k`. `by_page(p, first)`: the next call has `p + 1`; with no `p` given, the page that was answered was number `first`; an empty page ends. `by_cursor(a, f)`: `f(&T)` gives an `Option<V>`; `Some(v)` gives the next call with `a = v`. `by_link()`: reads every `Link` field of the answer as RFC 8288 says (a `;` or a `,` inside a quoted string ends nothing, and quoted text is read as bytes), and takes a link whose relations hold `next`; a link with an `anchor` is not taken, and a field that cannot be read is a Mismatch, not the end of the list. What is checked is the shape of a field (the brackets, the parameters, the quotes); its target is read as `reqwest` reads a URL, so a target that a strict grammar would refuse (`</a|b>`) is taken as servers send it. `by_next_url(f)`: `f(&T)` gives the URL as text, or `None`. |
| C8.7 | **`.items()` is on `Pages`:** `call.pages().items()` gives the items of each page in order, asks the next page when one is used up, and gives an error once. It asks of the type after the arrow the trait **`concord::page::IntoItems`** (`trait IntoItems: Send { type Item: Send; fn into_items(self) -> Vec<Self::Item>; fn count(&self) -> usize; }`), which the counting pagers (`by_offset`, `by_offset_limit`, `by_page`) ask too. The core writes it for `Vec<T>`; an author writes it for a list type of their own (`List<T>`), in a few lines. `Option` and `Result` do not have it, through an alias or not: `.items()` on such a page does not compile, and no error of the API is lost in an iterator. When it is not met, `rustc` says it in Concord's words (`is not a list of items`): the bound stands on the method, `fn items<I>(self) -> Items<I, E> where T: IntoItems<Item = I>`. The page and its items are `Send` (C8.4). |
| C8.8 | **A paged call is not awaited directly.** A call to an endpoint with `paginate` has no `IntoFuture`: `.send().await` gives one page, on purpose, and `.pages()` gives them all. Awaited by mistake, it gets `rustc`'s own message (`is not a future`); its `#[must_use]` text says what to write: `.send()` for one page, `.pages()` for all. |
| C8.9 | **A secret and a `base`.** An entry, or a piece of a `path`, that holds a `Secret` is bound to **the `base` in reach where it is written:** the one of its node, or the nearest above. Only where none is in reach (a secret on the client, above every `base`) is it bound to the first `base` below, on each branch: a key on the client, with a `base` on each scope, goes to all of them. Under any other `base` further down, the description does not compile until the entry is written again (`override "authorization" = "Bearer {client.token}";`) or removed. A piece of a `path` cannot be written again or removed: the `path` is moved, written under each `base` that needs it, and the message says so. Any `base` written below is another `base`, also with the same text. A caller's `with_base` moves everything: it is the caller's own word. It is checked through two traits of the hidden module that the secret side of the adapter (C2.4) does not have, `InheritAcrossBase` for an entry and `InheritPathAcrossBase` for a piece of a `path`: the error is `rustc`'s, at the entry or the `path`, in Concord's words (the macro, [The messages that are `rustc`'s](../internals/macro.md#the-messages-that-are-rustcs)). |

## C9. The transport, and tests

| # | Contract |
|---|---|
| C9.1 | **The transport is what really sends.** `Transport` has one method, from a `reqwest::Request` to a `reqwest::Response` or a failure with a class. `concord::Http` and `reqwest::Client` have it. A function wrapped by `concord::fake` has it. A type of the caller can have it. |
| C9.2 | A fake built with `concord::fake` and `concord::reply` can give: a whole answer; a failure before any head; a body in pieces, where a piece can fail or never come. An answer after a delay needs a type of the caller with the trait (four lines). |
| C9.3 | A transport gets the request after `.edit_request(…)` and after the middlewares, once for each try and for each page, with the endpoint and the number of the try. It must not change what a middleware signed (C3.4). **The engine sees one try:** C4.1, C4.4 and the log are about what is handed over, and not about what a middleware or a transport sends again on its own inside one try. A middleware or a transport says `blocked()` only when no request left during its call. A transport that follows redirects itself is outside [G3](../guide/promises.md). |
| C9.4 | A client has one thing that really sends: `with_transport(x)`, where `x` is a `concord::Http`, a `reqwest::Client`, a fake or a transport of the user. The last call wins. It replaces the transport **under** the middlewares: a fake gets the request as the middlewares made it. |
| C9.5 | `Transport::send` and `Middleware::handle` get a `concord::transport::TryInfo`: the name of the endpoint and the number of the try (1 for the first). `info.endpoint()` is a promise: the names of the tree joined with `.`, the same text as in a printed error (C6.4). It also carries the clocks of its call (the `Run`, hidden), so it is `Clone` and not `Copy`. A `TransportError` says what failed (`connect()`, `timeout()`, `blocked()`, a class), and no more. `TransportError::blocked()` is a failure of class blocked: nothing was sent during this call, no more tries are made, and the result is the blocked error (C3.3). |
| C9.6 | **`Middleware` and `Next`.** `concord::Middleware` has one method: `handle(&self, request, info, next)`, which gives a `reqwest::Response` or a `TransportError`. `next.send(request, info)` sends on, to the next middleware and then to the transport. It may be called more than once (a token that is renewed sends a copy again after a `401`), or not at all (`TransportError::blocked()`: the tries end, C3.3). A middleware runs for every try and for every page: a request that is sent again goes through it again. `with_middleware(m)` on a client adds one; a caller's middlewares come before every middleware of the description (C3.4). Nothing removes one: a middleware that must leave some requests alone looks at the request, or at `info.endpoint()`. **What a middleware changes is its author's affair:** one that sends a request elsewhere is like `edit_request`, allowed; the checks of pages and of retry look at the request as it was built (C4.1, C8.4). Its time is bounded by `timeout` only (C7.6). `request()` and `into_request()` give the request before any middleware. |

## C10. The generated code, and the log

| # | Contract |
|---|---|
| C10.1 | It names Concord only by absolute path (`::concord::…`): public items, and the hidden module `__private` (the macro, [What the macro may know](../internals/macro.md#what-the-macro-may-know)). Every path that the macro or a helper macro of the core writes is a full path, so a client compiles in a module that shadows `Option`, `Result`, `Some`, `Ok`, `String`, `Vec`, `Box` and the names `concord`, `core` and `std`. A module under `#![no_implicit_prelude]` is not promised: a method call on the author's own value (`.clone()`, `.into()`) is written as the author wrote it. [`tests/tour`](../../tests/tour/src) holds the same clients written by hand, and [`tests/tour-gen`](../../tests/tour-gen/src) the clients that the macro writes from their descriptions: both pass the same tests. |
| C10.2 | A handle is `Clone + Send + Sync`. A call is `Clone + Send + Sync`, and the future of its send is `Send + 'static`. |
| C10.3 | One struct for each endpoint, with `IntoFuture` (not for an endpoint with `paginate`: C8.8). Each endpoint has its whole request in one hidden function: what it inherits is worked out at compile time. **The order of running, for each send** (each page is one): `idle_timeout`, then `idempotent`, then the request, by kind first (the base, the paths, the query, the headers, the body), and inside a kind in the order of the tree (the client first, and for a node the lines of its parts before its own). An expression that fails ends the building there. `read` runs for each answer; a `paginate` expression once, at `.pages()`; a `middleware` expression once, in `new`. **The order on the wire** is the order of first writing: an entry that overrides runs at the turn of the node that wrote it, and is written at the place of the key. The values of a kind are kept until all of that kind have run. Its answer (the arms, the reader, the problem) is one function too, used by a send and by `read_response` (the macro, [What is written](../internals/macro.md#what-is-written)). |
| C10.4 | The generated docs follow the rules of the macro, [The generated documentation](../internals/macro.md#the-generated-documentation). Among them, an endpoint shows its request line (`GET https://{route}.api…/ids ?count&queue`), and the page of the client gets the `///` written above each `middleware`. The text of a `middleware` expression is never printed (C1.19). |
| C10.5 | not used |
| C10.6 | **One log event, `retry`**, through `tracing` with the target `concord`, at the level debug, each time Concord decides to try again. Its fields: `endpoint`, the name of the endpoint (C6.4); `try`, the number of the try that failed; `status`, the status of the answer, when the failed try had one; `class`, the class of the failure, when it had no answer; `wait_ms`, the wait before the next try, in whole milliseconds. The event has `status` or `class`, never both. Its name and its fields are a contract. A field never holds a value of a request or of an answer, other than the status. A middleware sees every try and every answer: a log of the traffic is one of them ([what Concord logs](../guide/promises.md)). |
| C10.7 | **`Debug` prints names.** Every `Debug` of Concord's own types prints names and no value: `Headers` the names of its headers, `Answer` its status and those names, an error its line (C6.2). Every generated type (a client, a handle, a call) prints no input (the macro, [What is written](../internals/macro.md#what-is-written)). There is no exception: `TransportError`, `Body`, `Base` and `Tried` follow it too. |
| C10.8 | **`new` makes the middlewares** of the description (C1.19), once, in the order written. The client holds them, and a clone of the client, every handle and every call share them: a middleware can hold what must be shared, a quota or a token that is renewed. What it keeps and a caller wants to read (a quota) comes in as a required input of the client, and the caller keeps a clone. |
| C10.9 | **The crates are a pair.** `concord` depends on `concord-core` and on `concord-macros` at exact versions, so that the macro and the engine that it writes for are always the same release. |
| C10.10 | **A send is two halves, both hidden.** `prepare` starts the `Run` (the clocks), runs `idle_timeout` and then `idempotent`, builds the request and finishes it for a send; it gives a `Prepared`: the `Run`, the request, what a secret wrote in it, the mark, and what reads the answer. `Prepared::send` runs the tries. `send_full()` is one after the other, and the hidden trait of every call has both, so that the engine can look at a request between the two: pages check the origin and "the same request" there, and nothing is built twice. `idle_timeout` runs for each send, also when the call set its own length, which then wins. A call whose method is `GET` or `HEAD` has a second first half, `__prepare_if_none_match(etag)`, written by the core's helper macro `call_methods!`: it writes `If-None-Match` after the headers of the description and before the edits, and its `Prepared` reads a `304` that no arm takes as `None` (C5.12). `send_raw()` is `prepare` and then `Prepared::send_raw`, which ends at the head. The machine of pages calls `answered_from(url)` on the call that a pager gave, with the URL of the answer that the pager saw: a relative `at_url` is resolved against it when the request is finished, before the check of the origin and the edits (C8.6). The whole hidden interface, method by method, is one table of the engine, [The hidden interface, method by method](../internals/engine.md#the-hidden-interface-method-by-method). (the engine, [The path of one call](../internals/engine.md#the-path-of-one-call), [Pages](../internals/engine.md#pages) and [Reading an answer that you got yourself](../internals/engine.md#reading-an-answer-that-you-got-yourself)) |
