# The contracts: what Concord does, exactly

*[Concord](../../README.md) · [docs](../README.md) · reference · previous: [the crates](crates.md) · next: [the cases](cases.md)*

This page is for you when you must know exactly what Concord does in one case, or when you change Concord and must not break a promise. It is the specification of the macro, the engine and the shipped items, and it says **what** each of them does. **How** the engine does it is described in [the engine](../internals/engine.md), and how the macro does it in [the macro](../internals/macro.md); where a line links there, the linked section is its design.

There are 130 numbers in twelve groups, `C1` to `C12`. A number is never reused; five are not used. Other pages cite a contract by its number.

**The tests of a contract carry its number.** A test of contract C5.4 has `c5_4_` at the start of its name. `just matrix` lists every contract with its tests, in `target/contracts-matrix.md`.

**The code:** the engine is in [`concord-core`](../../concord-core/src), the shipped items in [`concord-extras`](../../concord-extras/src), the macro in [`concord-macros`](../../concord-macros/src).

## C1. The description

| # | Contract |
|---|---|
| C1.1 | In a block, statements come first, then children. In the block of the client, the parts (C1.17) appear between the two. Anything out of this order is a compile error. |
| C1.2 | An endpoint is `METHOD name(inputs) [-> T] { … }`, or the same with `;` in place of an empty block. The method keywords are `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`; `METHOD "X" name(…)` sends the token `X`. The string is checked when the description compiles: it must be an HTTP token (`METHOD "VERSION-CONTROL"`). |
| C1.3 | There are twelve statements. In one node, each of these is written at most once: `base`, `path`, `body`, `read`, `paginate`, `problem`, `idempotent`, `idle_timeout`, and one block each of `query`, `headers` and `status`. The twelfth, `middleware`, appears on the client and may be written several times (C1.19). |
| C1.4 | A name of a scope, an endpoint or an input is lower snake case: the letters `a` to `z`, digits and single `_`, starting with a letter, not ending with `_`. A Rust keyword is rejected, in every edition, and so is a raw identifier. The list is closed: `abstract`, `as`, `async`, `await`, `become`, `box`, `break`, `const`, `continue`, `crate`, `do`, `dyn`, `else`, `enum`, `extern`, `false`, `final`, `fn`, `for`, `gen`, `if`, `impl`, `in`, `let`, `loop`, `macro`, `match`, `mod`, `move`, `mut`, `override`, `priv`, `pub`, `ref`, `return`, `self`, `static`, `struct`, `super`, `trait`, `true`, `try`, `type`, `typeof`, `unsafe`, `unsized`, `use`, `virtual`, `where`, `while`, `yield`. An input may have the name of any word of the language that is not a Rust keyword and not the name of an enclosing owner (C1.10). |
| C1.5 | A type name is formed in one way: split the name at each `_`, capitalize the first character of each part, and join the parts. A digit never splits a name: `get_sha256sum` becomes `GetSha256sum`. Two names at one level that produce the same type are a compile error: `one2` and `one_2` both become `One2`. A client name is upper camel case; its module is that name in lower case, with a `_` before each capital that follows a lower-case letter or a digit, and before the last capital of a run that is followed by a lower-case letter (`XMLHttpClient` becomes `xml_http_client`). `Self`, and a name whose module would be a keyword, are rejected. |
| C1.6 | **Reserved names**, for a name that becomes a method: a child, or an optional input (its setter). It may not have the name of a method that its receiver already has. The exact names: on a call, `send`, `send_full`, `send_raw`, `send_if_none_match`, `request`, `into_request`, `edit_request`, `read_response`, `pages`, `at_url`, `into_future`, `clone`; on a client or a handle, `call` (reserved for later) and `clone`; on a client, `new`. Anywhere: a name that starts with `with_`. **Concord adds no name to a call, a handle or a client in a minor version, unless it starts with `with_`.** A required input is an argument, and may have any name. In the module of a client: `Call`, `Endpoint`, `Error`, `Result` and `Retry`. A name that clashes is a compile error, and the message says to rename it. **Every name that the macro makes for itself that could shadow the author's types or expressions starts with `__`** (a method, a field, a type or a generic parameter), so no name that the author writes can collide with it. The macro puts no helper item with a name derived from an author's name in that scope (a free function named after a setter). |
| C1.7 | **An optional input is marked: `count?: u32`.** With `?` the input is not an argument: it is a setter with its own name, on the call, or on the client or the handle for an input of a client or a scope. It is not sent when it was not set. The declared type is the type of the value when one is set; in the block, the name is a `&Option<T>`. The setter takes a `T`, a `&T`, what an argument of type `T` takes, or an `Option<T>` (`None` unsets it). `milestone?: Option<u64>` keeps "not set" apart from "set to nothing": a body made of entries in JSON leaves the first out and writes the second as `null` (C2.14), and the author's own code can tell them apart; a query, a header and a form send nothing for both. Its setter: `.milestone(5)` and `.milestone(Some(5))` set the number, `.milestone(None::<u64>)` sets "nothing", and a bare `None` does not compile. The setter of `name?: Option<String>` accepts a string. A setter converts through two levels, `name?: T` and `name?: Option<T>`, and no more: a deeper type (`n?: Option<Option<u64>>`) takes its exact value. `x: Option<T>` without `?` is a required argument that may be `None`. An alias changes nothing. An optional input cannot fill a placeholder of a path or of a `base`, nor be the input of `base x;`. **After the arrow**, the macro recognizes `Option` and `Result` by their spelling, from a closed list: `Option<…>`, `std::option::Option<…>`, `core::option::Option<…>`; `Result<…, …>`, `std::result::Result<…, …>`, `core::result::Result<…, …>`. `Result<…>` spelled with one argument (the author's own alias, `type Result<T> = std::result::Result<T, MyError>;`) is the same wrapper, read as its `T`; `riot::Result<T>` is another spelling, and is not. A leading `::` and parentheses around the type are ignored. It is the spelling and nothing but the spelling: an author's type with one of these names is written with another path (`model::Option<T>`). What such an arrow reads is C5.2. |
| C1.8 | An input type cannot borrow. It is `Clone + Send + Sync + 'static`. A `concord::Body` is `Clone` too: bytes can be copied, a one-shot stream is taken once, and a repeatable source opens a fresh stream for each attempt. |
| C1.9 | Every input is used at its node or below: in a placeholder, an entry, or as a variable in an expression. This is a check of the text: an identifier among the tokens of an expression counts, also inside a macro call, and so does a name inside a string of a macro call (`format!("{n}")`); letters inside another string do not. An input that is never used is a compile error. |
| C1.10 | An input of a node above is named `client.x` or `scopename.x`. An owner's name is visible in its own node and below (`client.key` in a statement of the client is valid). A scope cannot be named `client`, a scope name cannot repeat on one chain, and an input cannot have the name of an enclosing owner (`client`, or a scope above it). `client.x;` is not a short entry: write `"x" = client.x;`. The macro checks such a reference only where it reads it itself: in a template placeholder, a `name;` entry, a `base`. Inside an expression, a name that does not exist is `rustc`'s error (the macro, [The author's names in the author's Rust](../internals/macro.md#the-authors-names-in-the-authors-rust)). |
| C1.11 | **A handle or an endpoint type is defined at its place in the tree, and has no other name** (`riot::matches::Ids`): in a module of the client, made by the macro. The endpoint's type has no value of its own. The `impl` blocks that use the author's Rust are placed where the macro is invoked, so every type and every expression of the author resolves there. No code of the author is ever pasted inside a generated module, and a generated module has no `use super::*;`. An author's type reaches the fields through **one hidden trait for each client**, with one associated type for each input, each non-endpoint node and the problem type, implemented once where the macro is invoked. The trait has the visibility of the client, so an input type must be at least as visible as the client. Before an expression, each enclosing owner is one hidden view whose fields are references to the inputs of its level: `client.region` is a `&Region`, as `region` is (the macro, [Where the generated items live, and how they reach the author's types](../internals/macro.md#where-the-generated-items-live-and-how-they-reach-the-authors-types) and [The author's names in the author's Rust](../internals/macro.md#the-authors-names-in-the-authors-rust)). A call holds each of its inputs, and **its fields are not public**: a pager reads an input through its slot (C8.6), never as `call.page`. **`api!` generates items:** like every Rust item, they cannot name a generic parameter of an enclosing function (`rustc` reports E0401). `Self` in a type of a description is rejected by the macro: replace `Self` with the path of the intended type. Concord cannot see a `Self` that the author's own macro produces inside an expression, and the generated type it names may change between versions, so do not rely on it. |
| C1.12 | The visibility written on the client holds for every generated item that a user can name: the client, the handles, the endpoint types, `Call`, `Endpoint` and the aliases. A visibility that is relative (`pub(super)`) is written again for each depth of the generated modules, so that it means what the author wrote. `///` (or `#[doc = "…"]`) on a node goes to what is generated for it; on a required input, to the method that takes it; on an optional input, to its setter. For an endpoint, the node's docs go on its type and its method, the required inputs also appear on the type's page, and an optional input's docs also go on its associated function. `#[cfg]` appears on a node only (a client, a scope, an endpoint) and goes on everything that depends on it, the associated types of the hidden trait too; the description is still checked in full. `#[deprecated]` and `#[doc(hidden)]` appear on a scope or an endpoint. On a scope they go on its module, its handle type and the method that returns the handle. Inside generated code, a use of a deprecated item of its own does not warn. On an endpoint, `#[deprecated]` and `#[doc(hidden)]` go on its type, on the method that returns its call, on its setters on `Call<E>` and on its setter functions on the type; `#[cfg]` goes on those and on the hidden items of the endpoint. An input and a part take doc comments, and no other attribute. |
| C1.13 | `override` and `remove` apply to what has a key: an entry of `query` or `headers`, and an arm. `override` or `remove` of a key that is not set above is a compile error (one exception: `override 2xx` with no `2xx` above is accepted when exact arms of that class are above, and takes their place; each of them is still overridden or removed in the same node, below), and so is either word before a statement that is not an entry or an arm (`path`, `base`, `read`, `idle_timeout`, `body`, `paginate`, `idempotent`, `problem`, `middleware`) or before a whole block (`override headers { … }`): the message names the statement. A key set above, written again without one of them, is a compile error. For `base`, `read` and `idle_timeout` the nearest statement is used, and no keyword is needed; `base` may appear on a client, a part, a scope or an endpoint, and the `path` lines above it still apply. An endpoint with no `base`, its own or inherited, does not compile. `path` only adds. Header names are compared without case, query keys exactly. **Arms are compared by the statuses they match:** a class arm from above (`2xx`, `4xx`) matches every status of its class. So an exact status under an inherited class arm is written with `override` (`override 404 => None` under a client's `4xx { body } => …`): it takes that status away from the class arm. And `override 2xx => …` over inherited exact arms of that class is rejected until each one is overridden or removed. A class arm written under an inherited exact arm of its class (`2xx => …` under a `200` from above) is written plainly: the exact arm keeps its status. In one node, a class and an exact status of that class may both be written; the exact one wins. An arm is still written, overridden and removed by its key: the statuses it matches decide only when `override` is needed. So `remove 4xx` takes away the arm written `4xx`, and nothing else (an exact arm set on the way stays), and `remove 404` when only a `4xx` is set above is a compile error: to take `404` away from the class arm, write `override 404 => …`. A status key is one token: three digits from 100 to 599, or a digit from 1 to 5 and `xx`. |
| C1.14 | "Set above" means the state after every level above, removals included. After a `remove`, a level below sets the key again plainly, and cannot `override` it. `read` cannot be removed, only named again. Inside one node, a key is written once, with the parts that the node names (C1.17). |
| C1.15 | Path text is not empty, has no leading `/` (it may end with one: C2.3), no empty segment, no segment that is `.` or `..`, no space, `?`, `#` or `%`, no `\` (the URL would read it as `/`), and no ASCII control character (a tab, a line end: the URL would lose it); the fixed text of a `base` has neither, and a `Base` made at run time rejects both (a Build error). A `{*x}` placeholder appears in a path only, and is a whole segment. `{{` and `}}` are braces. |
| C1.16 | **The macro knows no item of `concord-extras`, and no format, authentication scheme or pager.** What follows `body`, `read`, `paginate`, `idempotent`, `idle_timeout` and `middleware`, after `read` on the `problem` line, as the value of an entry and as the expression of an arm is a Rust expression that it copies as written, where the macro is invoked. In it, an input, bare or with its owner (`client.x`), is a reference to the input (in `paginate`, a bare name is its slot: C8.6), so the core takes references where it takes values: `Value` for `&Secret`, `Reader<T>` for `&R`, and `idempotent` takes a `bool` or a `&bool`, and nothing else. An input shadows an item with its name in the statements of its node, by Rust's own rule: the item is then written with its path (`concord::form(form)`). The `f` of `body f { … }` is not an expression and is not shadowed: it is a path (C1.21). A bare name that is not an input of the node is whatever Rust finds there, with no message. No expression is awaited. `read` and `idempotent` run inside a closure that is not `async` and does not return a `Result`, so `.await` does not compile there, nor `?` in `idempotent`; `?` in `read` is not promised either way ([when an expression runs](grammar.md#when-an-expression-runs)). **`return` is allowed** in an expression that appears in a closure. In `read { … }`, `idempotent { … }` and a pager it returns the value of that expression, of the type the author would write there, and the macro adapts that value outside the closure. In a status arm and in `body`, where `?` works, the closure returns a `Result`, so `return` takes one, as `?` does: `return Ok(17)`, `return Err(…)`. **The author's expression sees only the names that this page lists** (the inputs, the owners, and in an arm `body`, `headers` and `status`): every local of the generated code has mixed-site hygiene, so the expression cannot read it, change it or collide with it. A `const` or a `static` of the author's module is read by Rust as a pattern in a `let` of the same name (E0530), and hygiene does not prevent it: so the author declares, in the module of `api!`, no item whose name begins with `__` (nor a trait with a method of such a name), and none with the name of an input. What `read` returns goes through a hidden helper that carries the type that is read, so that Rust finds the type of a problem, and `?` cannot be used on it. `?` in `paginate` or `idle_timeout` is rejected by `rustc` too. `?` in an entry or a `body` ends the call with a Build error whose `source()` is the failure: the expression runs in a closure that returns `Result<_, Box<dyn Error + Send + Sync>>`. `?` in an arm ends it with the API's problem or a Mismatch (C5.8). When each one runs, and in which order for a send, is C10.3 ([when an expression runs](grammar.md#when-an-expression-runs)). A crate that holds a description needs `concord` and `serde` among its dependencies, and nothing else of Concord's. |
| C1.17 | **Parts.** `part name(inputs) { statements }` appears in the block of the client. Its signature names no other part. It may hold a `base` (the input that goes in the host, with the line that places it); it holds no `path`, no `problem`, no `middleware` and no child. A scope or an endpoint names parts at the end of its inputs: `..a, ..b`. It then has the inputs of each part after its own, in the order written, and the statements of each part before its own, as if it had written them. So inside one node a key (an entry, an arm) or a statement that holds one value (`base`, `read`, `body`, `paginate`, `idempotent`, `idle_timeout`) is written once: written by a part and again by the node, or by two parts of one node, it is a compile error. One exception: bodies made of entries (C1.21) in the parts that a node names and in the node itself are put together, the parts' entries first (in the order in which the node names the parts), when all call the same function, written the same way (a path, so the same spelling is the same function: C1.21); another function, the other form of `body`, or a key that two of them write is a compile error. An entry or an arm of a part may say `override` or `remove`: it is checked where the part is named, as if written there. `override` is for a key from a level above, not for a part (C1.13). A part that holds `body`, `paginate` or `idempotent` cannot be named by a scope. Inside a part, a bare name is an input of the part, and `client.x` an input of the client, and nothing else; in the node, an input of the part is an input of the node. A name after `..` that is no part, a part that no node names, an input of a part with the name of an input of the node, a part named twice by one node (`..page, ..page`), and two parts with one name are compile errors. The `///` of a part is for the author and goes nowhere; the `///` of its inputs go to every node that names it. A part generates nothing by itself (the macro, [The steps](../internals/macro.md#the-steps) and [What the macro generates](../internals/macro.md#what-the-macro-generates)). |
| C1.18 | The macro reports errors with the compile-time messages of [the messages](messages.md), each at the location that the page names. All the mistakes of one build are shown together, and the macro still generates every item that is sound (the macro, [The steps](../internals/macro.md#the-steps) and [Where a message points](../internals/macro.md#where-a-message-points)). Below a node, a block or an arm that an earlier step marked as damaged or rejected, no message is raised whose truth depends on what was dropped. A help line never leads to another message (the messages, [3. Three rules for every message](messages.md#3-three-rules-for-every-message)). |
| C1.19 | **`middleware m;`** appears on the client only: in a part, or anywhere else, it is a compile error. It may be written several times. `m` is a Rust expression, copied as written, that produces a value implementing `concord::Middleware` (C9.6). It is evaluated once, in `new`, in the order written. It sees the required inputs of the client, as references, bare or as `client.x`, and nothing else: an optional input of the client named in it is rejected by the macro. `new` cannot fail, so `?` in it is rejected by `rustc`; what can fail is done in `handle`. No node below and no caller takes a middleware away. A `///` above `middleware` goes to the documentation page of the client; the text of the expression is never printed (it could hold a literal key). The order in which the middleware runs is C3.4. |
| C1.20 | **The grammar of [grammar.md](grammar.md) is exact**, with what the grammar alone cannot say: a template is read after Rust has decoded the string, and a raw string is a template too. A placeholder holds a reference (a name, or an owner, a `.` and a name) and nothing else: no space, no comment. As the value of an entry, a bare string literal is a template, and anything else is an expression. The client and a part take inputs and no `..name`; a scope and an endpoint take inputs, then parts. |
| C1.21 | **A body made of entries:** `body f { entries }`. **`f` is a path to a function, resolved from where `api!` is invoked** (`json`, `form`, the author's own function): an input of the same name does not shadow it, so the same spelling in a part and in the node is the same function. An entry is as in `query`, `name;` or `"key" = value;`. A body inherits nothing from a level above, so `override` and `remove` there have no target: a compile error. The entries are one value of the core (C2.14), and `body f { … }` is `body f(entries)`: any function that takes something that `serde` can serialize fits, and the macro still knows no format. A part may hold `body f { … }`; the node that names it writes `body f { … }` with the same `f`, or no body. Another function, or the other form of `body`, is a body written twice: a compile error. A `Secret` may be an entry, short or as a value (`body form { grant_type; client_id; client_secret; }`): C2.14. |
| C1.22 | **`idle_timeout <expression>;`** appears on the client, a part, a scope or an endpoint; the nearest one is used. The expression is Rust with the inputs as variables, and returns a `std::time::Duration`: the idle timeout of the calls below (C7.6 for its order with the caller's settings). |

## C2. Building a request

| # | Contract |
|---|---|
| C2.1 | `base "…";` is `http://` or `https://`, a host, an optional port, and an optional path prefix whose segments are held to C1.15: no user, no query, no fragment. A placeholder in the host fills a label, or part of one (`"https://api-{label}.example"`); the finished label is checked: 1 to 63 characters, ASCII letters, digits and `-`, not at the ends. A name that is not ASCII is rejected: an international name is written in its ASCII form. An empty value in a host placeholder is the Build error of a host placeholder (`input <name> cannot be used in this host label`); an empty value in a port placeholder is the Build error of the base. A placeholder after `:` fills the port, with digits. After the URL is parsed, the host must be the host that was written, each label compared without case; a number that a parser reads as an address is rejected. Anything else is a Build error. |
| C2.2 | `base x;` takes one input of the type `concord::Base`. A `Base` is parsed from a string: a scheme, a host, an optional port, and an optional path prefix. No user, no query, no fragment. **A `Base` is accepted only when the URL library returns what was written, part by part:** the scheme, case aside; the host as the library reads a host on its own (upper case, a longer spelling of an IPv6 address, an international name are the same host); the port, or none when the default one was written; the path once both are decoded (an empty path is the root: a bare host, `https://api.example.com`, is a legal base). Any other difference is rejected. So nothing that the library would silently change is ever sent: a `\`, a control character, a user found in what looked like a path, a dot segment. A trailing `/` of a base is kept only when no `path` follows it (C2.3): the URL ends with `/` when the last `path` does, or the base itself when no `path` follows. Each segment of the prefix is held to C1.15 and is decoded once. The prefix comes first in the path. `with_base(…)` takes the same string; a string that is not a `Base` makes the next send a Build error, `the base is not a usable URL (with_base)`. |
| C2.3 | The path is the prefix of the base, then the segments of every `path`, root first, joined with one `/`. **The URL ends with `/` when the last of them does:** the last `path`, or the `base` when no `path` follows. Fixed text is sent as written (a parser may encode a character of it). The value of a `{x}` placeholder is percent-encoded: every byte outside `A-Z a-z 0-9 - . _ ~` becomes `%XX` with upper-case hex digits (`%2F`), `%` too, so that it cannot add a `/`, a `?` or a `#`. It is a Build error when it is empty. A finished segment that is `.` or `..` is a Build error: `v{x}` with `x = ".."` produces `v..`, which is sent. A `{*x}` placeholder is split at each `/`, and each segment is encoded. **A segment of `{*x}` may be empty:** a final `/` and `//` are sent as they are. Its whole value may not be empty, and a segment that is `.` or `..` is a Build error. The built URL has as many segments as were written, or it is a Build error. |
| C2.4 | **The string form of a value.** A value in a path, a host, a query, a header or a template is serialized by `serde`, with Concord's own serializer, which accepts three shapes. *Nothing:* `None`, the unit. *One string:* a string, a `char`, a `bool` (`true`, `false`), a number (a float that is not finite is a Build error; a float is written as `serde_json` writes a number: the shortest string that parses back to the same number, with `.0` for a whole number, `1.0`), a variant with no data (its `serde` name), a newtype or a `Some` around one of these. *Several:* a sequence or a tuple of strings. Any other shape (a map, a struct, a variant with data, bytes, a list inside a list) is a Build error. So is a value nested more than 128 levels deep, wherever it is placed and in a body of entries (`input <name> cannot be serialized into a <place>`): no input can overflow the stack while it is written. **`Secret` has no `Serialize`**, so `json(x)` of a type that holds one does not compile: `body json(task)` with a secret field is rejected. The generated code passes every value that it places through one adapter of the hidden module, which recognizes `Secret` and `Option<Secret>`, and references to them, before it requires `Serialize`; an optional input `key?: Option<Secret>` can be placed too. The entries of a body go through the same adapter, so a `Secret` there is written as its text, as in a query (C2.14). With a template that has a `Secret` in a placeholder, these are the only shapes of a value that holds a `Secret`: a list of secrets does not compile. |
| C2.5 | Where each shape may go. A value that is a whole entry of a query or of headers: nothing (the entry is not sent), one, several. A whole entry of a body is C2.14. A placeholder in a template of an entry, of a query, of headers or of a body: one; nothing leaves the entry out (C2.8), and an empty list counts as nothing; several is a Build error. A placeholder in a path or in a host: one; nothing or several is a Build error. |
| C2.6 | Query pairs are in the order of the declaration, root first; the items of a list in their order. Keys and values are percent-encoded: every byte outside `A–Z a–z 0–9 - . _ ~` becomes `%XX`, with upper-case hex digits. A request with no query pair has no `?`; a URL given to `at_url` (a next page, C8.6) keeps its query as given, an empty one (`?`, `?&&`) included. An empty string as a value writes `k=`. An `override` keeps the position of the pair or pairs it replaces. |
| C2.7 | A header name is checked at compile time and sent in lower case. `host` cannot be a key of `headers`: the host is the `base`. A short entry (`name;`) in `headers` whose name has `_` is rejected: write `"user-agent" = user_agent;`. (In `query` the short entry is unchanged.) A header value is never percent-encoded. A value may hold the bytes 0x20 to 0x7E and a tab: a space is legal (`Bearer {token}`). Another control character (a line break) or a byte over 0x7E is a Build error, unless a level below replaces or removes that header. `Draft::header` receives the name as written, and compares and stores it without case. A list sends one field line for each item. A header whose value holds a `Secret` (the value that `basic` returns is one) is marked sensitive. **The content type of a body is a header value:** the content type given to `Body::new(bytes, label)` or to `Body::stream(…).content_type(label)` is sent as `content-type`, under the same rule; one that is not legal is the Build error of that header, `the value of header content-type is invalid`. |
| C2.8 | A template that reads a `None` leaves its entry out; every placeholder of the template is checked before the entry is left out. An `override` whose value is `None` sends nothing for the key. A `content-type` entry whose value is `None` sends nothing, and the body's own content type is then sent. |
| C2.9 | `body <expression>;`. The expression is evaluated when the request is built, with the inputs in scope as references. It returns a `concord::Body`, a `&Body` (it is cloned), or a `Result` of one of these whose error is any error that `Box<dyn Error + Send + Sync>` takes: an `Err` is a Build error with that error as its `source()`. `request(&self)` never consumes the call: on a call whose body holds a one-shot stream it is a Build error, and no part of the body is touched (C2.15). `into_request(self)` returns the request and takes the stream with it. A `Body` is bytes or a stream, or a body made of bodies (C2.15), with an optional content type. The content type is written to the request unless a `content-type` entry that applies sets a value (C2.8). `json(x)` writes with `serde_json` and sets `application/json`; `form(x)` writes with `serde_urlencoded` and sets `application/x-www-form-urlencoded`. `multipart()` (feature `multipart`) builds a multipart body: `body multipart().text("chat_id", id).file("photo", "a.jpg", "image/jpeg", photo).finish();` (C2.16). The other form of `body` is C1.21. |
| C2.10 | `with_base(x)` replaces the whole base: the scheme, the host, the port and the path prefix of the `base` line. The `path` lines stay. |
| C2.11 | A Build error always means that nothing was sent. **A URL that cannot be sent is a Build error:** a URL longer than 65,534 bytes, the most the HTTP layer can hold, counted once the path and the query are encoded (C2.3, C2.6) and after `at_url` and the edits of `edit_request`, is `build error: the URL is too long to be sent`, before any middleware sees the request, with zero attempts. |
| C2.12 | **A `content-length` that the description writes** (`"content-length" = size;`). For a body in memory it must be the length of the body, or the request is a Build error. For a one-shot stream, which has no length of its own, it is sent as written; a mismatch is handled by the HTTP library and server. For a `Body::repeatable`, a final `content-length` header after edits, when present, must be a valid length with no conflicting values; every opening must yield exactly that many bytes (C12.13), or the attempt fails as Other. |
| C2.13 | **A Build error names its value.** Each value that the generated code passes to the request comes with a name, `Piece::Val("region", &value)`: for a placeholder and for a `name;` entry, the input (`region`, `client.tenant`); for an entry written `"key" = value;`, the key, also when the value is a bare input. The text is always `input <name>` (the engine, [How a value is written](../internals/engine.md#how-a-value-is-written)). An entry of `query` or `headers` whose expression fails prints `input <name> could not be evaluated`, with the author's error as `source()`; only a `body` prints `the body could not be constructed`. |
| C2.14 | **`concord::body::Entries`**, the value of a body made of entries (C1.21), is serialized by `serde` as a map, in the order written: any `serde` serializer sees a plain map, with no wrapper and no hidden name. **A `None` writes nothing**, as in a query and in headers: one level of `Option` is presence, and what is inside is written as the format writes it. So `x;` with `x?: T` or `x: Option<T>` writes no key, or the value. `milestone;` with `milestone?: Option<u64>` writes no key, `null` or a number (in JSON). `"k" = value;` whose value is an `Option` (`"x" = client.x;`, `"ids" = ids.as_ref().map(join);`) writes no key when it is `None`. `"k" = Some(x);` with `x: Option<T>` writes `null`, or the value: it is the way to write a `None` as `null`. **A form has no `null`:** there an inner `None` writes no pair either, and a list or a struct as a value is a Build error (`the body could not be constructed`). The macro knows no type for this: `Entries` asks `serde` whether a value is a `None`, when the body is written. So each value is serialized twice, once to ask whether it is a `None` and once to write it, and its `Serialize` must produce the same result both times. A `Secret`, short or as a value, is written as its text, through the adapter that writes it in a query (C2.4). A template as a value (`"note" = "by {name}";`) is as in `query`: its text is written, a placeholder that reads nothing leaves the entry out, and a placeholder that reads several is a Build error (C2.5). The unit (`()`) is not a `None`: in a body it is written as the format writes it (`null` in JSON; a form cannot write it, which is a Build error, `the body could not be constructed`); in a query and a header it writes nothing (C2.4). |
| C2.15 | **A body made of bodies: `Body::concat(parts)`**, in the core, joins bodies in order. A one-shot stream inside is taken with the whole, when the request is built for a send (before any middleware). So a stream that was already sent is a Build error before anything goes out, also inside a `multipart` body. One-shot is a property of a `Body`, a value: a clone of a call shares the stream of an input, and the first send takes it; a second send of that same `Body`, through a clone or by the next page of a paginated call, is that Build error (`the one-shot body stream cannot be used in this request`), and nothing is sent. An expression that makes a new stream each time it runs (`body fresh();`) gives each send its own. `request()` rejects a body that holds a one-shot stream without touching a part. `Body::as_bytes()`, `Body::concat`, `Body::map_stream` and `Body::is_repeatable` are public, and the multipart writers are built with them; so is `Body::into_stream()`, for an author's writer that takes a stream apart. |
| C2.16 | **`multipart`** (`concord-extras`, feature `multipart`): `multipart().text(name, value).file(name, file_name, content_type, body).finish()`. `text` and `file` return the builder. `finish()` returns a `Result` of a `Body`: a content type that is not a legal header value is its error, and so is a field name or a file name that holds a control character (a NUL, a CR, a LF, a tab); nothing panics. A `"` in a name is written `%22`, and nothing else is changed: a `%` is written as it is, as browsers do (WHATWG, "multipart/form-data encoding algorithm"). So two names can be written the same: `"` and `%22`. Concord does not check that the names of one body differ. **The boundary is not random when every part is in memory:** it is the first of a fixed list that no part holds, so the same inputs produce the same bytes (G6 of [what Concord promises](../guide/promises.md), and "the same request" of pages, C8.4). With a part that is a stream, the boundary is random (128 bits), chosen once by `finish()`. A one-shot part (`Body::stream`) makes the whole body go out once; a repeatable part (`Body::repeatable`) leaves it repeatable, and each opening gives the same bytes (C12.12). |

## C3. One call

| # | Contract |
|---|---|
| C3.1 | The request is built once (C2). `.edit_request(f)` runs once on each request that is built: once for a call, once for each page (C8.4). `f` is `Fn(&mut reqwest::Request) + Send + Sync + 'static` and cannot fail. Each `.edit_request` adds a function; they run in the order written. A header value that `f` marks sensitive is left out of "the same request" of pages, as a secret is (C8.4). |
| C3.2 | For each attempt, a copy is made with `try_clone`. A request whose body is a one-shot stream (`Body::stream`, `Body::map_stream` over bytes in memory or over a one-shot stream, or a body made of bodies that holds one) cannot be copied: it is used as it is and gets one attempt, so such a stream is sent once. A request whose body is repeatable (`Body::repeatable`, alone or with bytes) keeps its head, and each later attempt sends a copy of that head with a stream opened again from the first byte (C12.12). |
| C3.3 | **After `blocked`.** A middleware or a transport that will not send returns `TransportError::blocked()`: no further attempt is made, and the result is the blocked error (a Transport error of the class `blocked`). |
| C3.4 | **The way out.** The copy goes first through the middleware that a caller added (`with_middleware`), then through the middleware of the description, in the order written, then to the transport, with its `TryInfo` (C9.5, C9.6). The response comes back the same way. **The author's middleware runs last before the wire:** nothing changes a request after it was signed. The author declares the signing middleware last, and a transport must not change what was signed. (the engine, [The way out: middleware, then the transport](../internals/engine.md#the-way-out-middleware-then-the-transport)) |
| C3.5 | **An attempt is the whole exchange:** the send, the head, the choice of the arm, the body when an arm binds it and the reader reads it whole, and the arm. It ends in one outcome: a value; a Refused error; a Transport error; a Mismatch. With `read Stream`, and for `send_raw()`, the attempt ends at the head (the engine, [One attempt](../internals/engine.md#one-attempt)). |
| C3.6 | Retry looks at the outcome (C4). A value, a Mismatch and a Build error are final. For `send_raw()`, a head below `400` is final, like a value; a head of `400` or above is evaluated by the policy, as an error response is. |
| C3.7 | not used |
| C3.8 | One loop in the core's hidden module runs the attempts (C3.2 to C3.6, C4) around a function for the rest of each attempt (the engine, [The attempts](../internals/engine.md#the-attempts)). `Prepared::send` and `Prepared::send_raw` both use `exchange_loop` and differ only in the function that reads each response. |
| C3.9 | **One `Run` for a send.** A send starts one `Run` before the request is built. It holds the timeouts of the call (C7.6) and the name of the endpoint. The engine holds it while an attempt runs, a `ByteStream` that is handed over holds a clone, `TryInfo` carries it, and `refused` writes into it what it knows of an error response (C7.6). An attempt is counted when the engine hands it to the middleware (C4.4). No request is handed to the transport after `timeout` has expired. (the engine, [The values](../internals/engine.md#the-values), [The attempts](../internals/engine.md#the-attempts) and [The two timeouts](../internals/engine.md#the-two-timeouts)) |
| C3.10 | **`read_response`.** Every call has `read_response(response)`: the arms, the reader and the problem type of the endpoint, applied to a `reqwest::Response` that came from anywhere, as in an attempt after its send (C3.5). No retry, no timeout, no page; on its error, `tries()` is 0. (the engine, [Reading a response that you obtained yourself](../internals/engine.md#reading-a-response-that-you-obtained-yourself)) |

## C4. Retry

| # | Contract |
|---|---|
| C4.1 | **Three conditions**, all needed for another attempt. *It can be sent again:* C3.2 produces a copy whose body is bytes, or a copy of the head with the repeatable body opened again; a one-shot stream cannot be sent again. *It may be repeated*, in one of three ways: by its mark, when the endpoint says `idempotent <expression>;` and the expression is `true` for this call (`idempotent;` alone is `true`; the expression runs once for a send); by its method, when the endpoint has no `idempotent` and the method of the request as it was built (after `.edit_request(…)`, before any middleware) is `GET`, `HEAD`, `OPTIONS`, `PUT` or `DELETE`; or by its status, when the outcome is an error response (kind Refused) whose status the policy lists with `not_applied_on(status)` (a `429` on a `POST` that is not marked: `idempotent;` would also retry it after a lost connection). A body that broke, or a timeout that expired, after a head with that status does not open this gate. `not_applied_on(n)` never panics: a number outside 100 to 999 is kept and matches no response. A `POST` that is not marked is not retried after a failed connection: its caller gets the error (`e.class()` says Connect) and decides, also when `e.request_not_sent()` is `true`, which the policy does not read (C9.5). With `concord::Http` and only the middleware that Concord ships, nothing below the engine repeats a request (C4.4, C7.1): with no policy, a call makes at most one attempt (none when its request cannot be built), so a `GET` can fail with a Connect error after an HTTP/2 refusal; `Retry::standard()` permits another counted attempt when the request may be repeated, within its number of attempts and the call's `timeout`. *The failure is worth another attempt:* no `unless` rule returns `true`, and either the standard table (C4.2) or a `when` rule asks for another attempt (C4.7). The order of the checks is described in the engine, [The decision to retry](../internals/engine.md#the-decision-to-retry). |
| C4.2 | `Retry::standard()`: at most 3 attempts; `tries(n)` is held to at least 1, which means no further attempt. Outcomes it names: a Transport error of class connect, timeout or body; `408`, `429`, `502`, `503`, `504`. |
| C4.3 | **The waits are fixed.** Before attempt `n+1`, a random time up to `2^(n−1)` seconds: up to 1 second, then 2, then 4; never more than 60 seconds. A wait is never less than a `Retry-After`, nor than the wait that a `when` rule requested (C4.7). A `Retry-After`, or a requested wait, over 60 seconds means no further attempt: the error is the result, and `e.retry_after()` returns how long to wait. **`e.retry_after()` returns the longer of two waits:** the `Retry-After` of the response, and the wait that a `when` rule requested for the attempt that did not happen. No rule is consulted twice: the decision returns the requested waits together with its verdict. A wait that would not end before the `timeout` of the call also means no further attempt. A wait has one deadline, taken once: past the end of `timeout`, the wait is not started; if the timeout still cuts a wait that was started, the caller gets the last outcome, unchanged, and not a timeout. `Retry-After` is read as seconds or as a date, by Concord itself: the three forms of RFC 9110, section 5.6.7, and a two-digit year by its fifty-year rule. A value that is neither a number of seconds nor an HTTP date is taken as absent. A date in the past is a wait of zero. A date is compared with the system clock; one more than 60 seconds ahead means no further attempt, in whatever year. |
| C4.4 | When the attempts run out, the last outcome is the result, unchanged. `tries()` on the error returns how many attempts the engine handed to the middleware: an attempt is counted when it is handed over, so a timeout before any head counts that attempt. What happens below that is not counted: what a middleware sends again with `next.send` inside one attempt; what a transport of the caller's own sends on its own; with `concord::Http`, which lets `reqwest` resend nothing (C7.1), the connection pool's resend of a request that an unusable reused connection handed back unwritten, which never puts a request on the wire twice; and with a caller's own `reqwest::Client`, what it resends as its retry policy is configured (by default, up to twice and whatever the method, a request whose body is in memory or empty, after a remote HTTP/2 `REFUSED_STREAM` reset or a `GOAWAY` with `NO_ERROR`), and the requests that it sends to follow a redirect (by default up to ten; after a `307` or a `308`, the same method and a body that can be copied) ([what can send a request twice](../guide/retries.md#what-can-send-a-request-twice)). |
| C4.5 | The response of an attempt that is given up is dropped before the next one is sent. |
| C4.6 | `.with_retry(…)` on a call replaces the whole policy of the client for that call, `tries` and rules: that is the caller's own decision. An author ships the API's policy (`slack::retry()`, with its `not_applied_on`), and a caller keeps it by passing it on: `with_retry(slack::retry().when(mine))`. |
| C4.7 | `Retry<E>::when(f)`, with `f: Fn(&Tried<E>) -> Option<Duration>`, and `Retry<E>::unless(f)`, with `f: Fn(&Tried<E>) -> bool`. **Rules add up inside one policy:** every `unless` rule is consulted, and the `when` rules are consulted in the order they were added; the first that returns a wait wins, and the rules after it are not consulted. A rule is consulted only when another attempt is still possible: after C3.6, the number of attempts, the copy of C3.2 and the gate of C4.1; the `unless` rules first. `Tried` provides the status, the headers, the class, the number of the attempt, and `problem()`. With a rule set, the body of an error response (at most 64 KiB) is read and `problem()` is tried before the rule is consulted. An `unless` that returns `true`: no further attempt. A `when` that returns `Some(wait)`: another attempt, after at least `wait` (C4.3). No `when` returns a wait: C4.2 decides. For `send_raw()` the attempt ends at the head, and only a head of `400` or above is evaluated (C3.6): a rule receives the status and the headers, `problem()` is `None`, and nothing of the body is read. A failure of class blocked is never retried (C3.3). |

## C5. The response

| # | Contract |
|---|---|
| C5.1 | The status picks the arm before any byte of the body is read. An exact status wins over a class (for an inherited class arm, C1.13). |
| C5.2 | **Arms add up.** The applicable arms are the ones written at the node and above, and in the parts that they name. A status that none of them matches: a 2xx is the body, read into the type after the arrow (with an arrow), or `()` (without); anything else is a Refused error. **An `Option<T>` or a `Result<T, E>` after the arrow** (C1.7): a 2xx that no arm matches is read as `T`, and returned as `Some` or as `Ok`; the arms produce the rest (`404 => None`, `409 { body } => Err(body)`). An empty body is up to the reader: `Text` returns an empty string, `Binary` no bytes, and `Json` a Mismatch, so a `204` under `-> T` with `read Json` needs an arm (`204 => None`). **A `HEAD` with an arrow** writes its arm for a 2xx (an exact status or the class): there is nothing to read. A 2xx that no arm matches is then a Mismatch: the hidden helper `no_arm(response, &info)` produces it, and keeps the evidence (the status, the headers, at most 64 KiB) as an error response does. **An endpoint with no arrow, under an applicable arm that would read its body, does not compile:** it gets an arrow (`-> Ignored`, a type that the author defines to read anything), or it removes the arm. |
| C5.3 | **An arm binds what it uses:** `key => EXPR` or `key { fields } => EXPR`. The fields are `body`, `headers` and `status`, each at most once, each with another name if wanted (`body: task`). A field that is not named is not there. `body` is the body, owned, read by the reader that applies before `EXPR` runs; Rust infers its type from the arm. When Rust cannot infer it, the arm states it: `4xx { body } => { let odd: UploadError = body; Err(odd.into())? }`. Naming `body` is what reads it: no keyword inside `EXPR` starts a read. `headers` is a `&concord::Headers`, `status` an `http::StatusCode`. `EXPR` runs as `Ok({ EXPR })` in a function that returns `Result<A, concord::Fail<E>>`. A field that is not one of the three is a compile error. **On a status that is not a 2xx, an arm's `body` that cannot be read produces a Refused error**, with the status, the headers and the bytes kept; `problem()` is `None`. (A Mismatch stays for a 2xx whose body does not read, and for `mismatch(…)` and `require(…)` in an arm. An arm that decodes the body itself and returns `Fail::from_read(…)` gets the same two outcomes: C5.8.) For a `HEAD`, the edits (`override`, `remove`) are resolved first; then an inherited arm that binds `body` is left out, and an arm of its own that binds `body` (also one of a part that it names) is a compile error. Its arrow is C5.2. **An inherited arm that matches a 2xx and binds `body` does not reach an endpoint whose arrow is spelled `Option<T>` or `Result<T, E>`:** a compile error at the arrow, until the endpoint writes that arm itself (`override`) or removes it. The order is: the edits, then for a `HEAD` the leaving out, then this check on what is left; so a `HEAD` never meets it. (Under such an arm Rust would infer `Option<T>` as the type of what is read, and a `null` would silently become a `None`: the gap that C5.2 closes for the simple rule.) (the macro, [The author's names in the author's Rust](../internals/macro.md#the-authors-names-in-the-authors-rust)) |
| C5.4 | Reading a body whole: an announced size over the limit is a Mismatch before anything is read. **The announced size** is the `Content-Length` header of the response when it has one, else what the transport reports of the size of the body; this holds for a `fake`, a `tower` service and a middleware that replays a response. It is used only inside the reader's limit, and it never decides how much memory is reserved at once: the engine never reserves more than what has arrived, doubled, with a floor of 64 KiB, however large the limit. When the announced size is inside the limit, it is the ceiling of the buffer: an honest body of 100 MiB ends in a buffer of 100 MiB, not 128. An allocation that fails is a Transport error of class body, never an abort. Bytes are counted as the transport delivers them (`concord::Http` does not decompress unless its closure turns that on: C7.1). A chunk that would pass the limit is not kept. A body that breaks, or ends before its announced size, is a Transport error that keeps the status and the headers; it is never a shorter value. |
| C5.5 | A body that no arm names is not wanted. It is dropped, and nothing that happens to it changes the result. |
| C5.6 | **Everything that an error keeps from a response is bounded:** a Refused error and a Mismatch keep up to 64 KiB of the body, in a buffer of their own, and up to 1 KiB of a reader's own message (C6.3), its mark included: the kept text and ` … [cut]` are 1024 bytes or less, and a text that was already cut is not cut again. The cut at 1 KiB bounds the memory too, also for a short text in a large allocation. `kept()` says complete, cut or interrupted, and is `None` when no byte of a body was kept (for example, after an announced size over the limit). For a Refused error from a status, `problem()` is tried from a complete body, into `E`, by the reader of the `problem` line: the `read` of the client node, or the one named after `read` on that line (C5.11). When it does not decode, it is `None`. This never produces another error. It is not tried for a Mismatch: a body is never read to see what it is. With no `problem` line there is no problem type, and `problem()` is always `None`. |
| C5.7 | A failure that is known stays: a Refused error whose body then breaks, or never ends, is still that Refused error. |
| C5.8 | `?` in an arm, on the API's error type, produces a Refused error with that problem and the status of the response (it can be 200). It keeps the typed problem and no bytes. `concord::mismatch(text)` returns a `concord::Fail<E>`, and so does `headers.require(name)` when the header is missing; returned as the `Err` of an arm or of a pager, it ends the call with a Mismatch whose `reason()` is the text. `Fail::from_read(error)` returns one from a `ReadError` (C5.11), for an arm or a pager that decodes a body itself (`Json::decode`): it ends the call with the error that a reader that failed with that `ReadError` gives at that status. On a 2xx, a Mismatch with the reader's location in its text and in its `source()`, its details behind `details()` (C6.3), the bytes that the `ReadError` kept, and no `reason()`; on another status, a Refused error with those bytes and no problem, as C5.3 says of an arm's `body`. A pager's `Fail::from_read` gives the same Mismatch, not the text of a page that cannot be requested. **The `Fail` keeps only the evidence of the decode:** the location, the reader's message (1 KiB at most) and the bytes (64 KiB at most); the status, the headers, the endpoint and the attempt are always those of the response that the arm or the pager is running on. A `ReadError` that is not a decode failure (a body that broke while it was read, or a stream error forwarded with `?`) belongs to another moment of another response: none of it is kept, and it ends the call, on any status, with the Mismatch of an arm that rejected the response (of a pager: the page that cannot be requested), with no `reason()`, no bytes and no `source()`. **`body()` and `kept()` of that error are the decoder's input** (at most 64 KiB) and its state, not the body of the response: Concord does not verify that the arm decoded the body that it was given, rather than a part of it or bytes kept from another call, so `details()` names them `decoder input (…)` (`decoder input (cut, 3 bytes)` with the length kept when a reader's limit cut them), never `body (…)`, and every text of this path is said of the decoder's input: a fault at a location prints as under a reader, and the four other texts are those that [the messages](messages.md) list for a decoder's input (`the decoder's input could not be decoded`, `the decoder's input is empty`, `the decoder rejected the content type of its input`, `the decoder's input exceeds the decoder's size limit`), in the error's line and in its `source()`. Nor does the error say that a content type was unexpected: that was a fact about the response that a reader read. `Fail<P>` is `Send`, `Sync`, `UnwindSafe` and `RefUnwindSafe` when `P` is. |
| C5.9 | `send_full()` takes the same path as `send()` and keeps the head. |
| C5.10 | `read Stream`: a success ends the attempt at the head. The status rule runs on the head, then the body is handed over unread. An error response is read like any error response (64 KiB, the problem type). What fails later is a `concord::read::StreamError` from `try_next()`: its kind is Transport, with the status, the headers, the endpoint and the attempts; with `?` it becomes any `concord::Error<P>`, and a `ReadError`. A `ByteStream` may read ahead of what the caller asked for. |
| C5.11 | A reader is a value with the trait `concord::Reader<T>`; `read` takes a Rust expression, copied as written. **The core has none, and there is no default:** an endpoint in which a body is read (by the rule of C5.2, or by an arm that binds `body`) needs a `read`, its own or inherited, or it is a compile error at what reads. `HEAD exists() -> bool { status { 2xx => true, 404 => false } }` needs none. `problem E;` is read by the `read` of the client node, or by the expression after `read` on its line (`problem E read Xml;`); with neither, a compile error. ## C11. A credential that is renewed, limits, records, a returned URL

These are items of `concord-extras`, re-exported by `concord`: `concord::auth` (feature `auth`), `concord::limit` (feature `limit`), the readers of records of `concord::read`, and `concord::transfer`. Each is built with the public traits of the core, and the macro knows none of them (C1.16).

| # | Contract |
|---|---|
| C11.1 | **A renewed credential stays where it belongs.** `concord::auth::Renewed` is a middleware. Its token is never printed: not by `Debug` (`Renewed(..)`, `AccessToken(..)`), not by an error, and the payload of a panic in the author's code is dropped; `RenewalError` prints one sentence for its variant and no cause, and its `source()` returns the cause that the author's renewal gave (what the author puts in an error of their own is the author's). | C11.2 | **`Renewed` never sends a request twice.** A `401` marks the token that the request carried as rejected, so that the next call renews, and the response is returned as it is. Each call of `Renewed`'s `handle` passes the request on at most once (none when it blocks it); what the transport sends again below an attempt is C4.4. With no retry rule, that is after one attempt. With `after_401`, the engine can send a second attempt, with the new token, and returns its response (the credential's own test shows a second `401` returned after two attempts). The response is returned unchanged; `rejected_when` schedules no retry, but a retry rule of the call that applies to the response can send it again, with the renewed token; nothing is renewed at once: each later attempt that needs the token, of any call, joins the renewal in flight or starts one, and the retry setting of each call bounds its attempts; `f` is never called for a `401`, a panic in it rejects nothing, and the credential keeps and prints nothing of the body. | C12.6 | **`Rotating` keeps the order that protects a refresh token.** The marker that a renewal began (`Stored::Refreshing`) is saved before the exchange.
